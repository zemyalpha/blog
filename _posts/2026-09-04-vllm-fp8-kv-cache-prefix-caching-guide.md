# vLLM FP8 KV 캐시 실전 가이드: 디코드 비용 절반으로 줄이는 조건 3가지

롱컨텍스트 LLM 서빙에서 GPU 메모리의 주인은 더 이상 모델 가중치가 아니다. 128k 토큰이 넘는 컨텍스트에서는 KV 캐시가 GPU 메모리 대부분을 차지하고, 디코드 스텝마다 이 캐시를 다시 읽어야 한다. 즉 추론이 compute-bound가 아니라 memory-bound로 넘어가는 순간, 캐시를 얼마나 작게 유지하느냐가 곧 처리량과 동시성을 결정한다.

vLLM은 이 문제에 대한 가장 직접적인 답으로 `--kv-cache-dtype fp8` 플래그를 제공한다. BF16에서 FP8(e4m3)으로 캐시 정밀도를 낮추면 저장 크기가 절반으로 줄고, 어텐션 연산(QK·ScoreV matmul)도 FP8으로 실행된다. 문제는 "무조건 켜면 빨라진다"가 아니라는 점이다. 2026년 4월 vLLM 팀이 공개한 검증 결과에는 성능을 좌우하는 조건과, 켜면 안 되는 경우가 명확하게 나와 있다. 이 글은 그 원문을 기준으로, 실무자가 FP8 KV 캐시를 도입할 때 무엇을 확인해야 하는지 정리한다.

## 1. 먼저 이해할 것: 왜 KV 캐시가 병목인가

오토회귀 디코딩에서 모든 토큰 생성 스텝은 이전 토큰들의 K·V 상태를 다시 읽는다. 컨텍스트가 길어질수록 이 읽기 비용은 선형으로 늘어나고, HBM 대역폭이 한계에 도달하면 GPU는 연산을 하지 않고 데이터를 기다린다. 여기에 배치까지 겹치면 KV 캐시가 메모리를 점유하는 양 자체가 동시 접속 가능한 요청 수의 상한이 된다.

FP8 캐시는 이 두 가지를 동시에 공격한다. 절반 크기의 캐시는 읽어야 할 바이트 수를 줄여 토큰당 디코드 비용을 낮추고, 같은 GPU에 더 많은 요청을 packed하게 만든다. vLLM 공식 벤치마크에서 Llama-3.1-8B는 단일 요청 기준 디코드 ITL(Inter-Token Latency) 기울기가 BF16 대비 54%까지 떨어졌고, 동시성 8·약 20k 토큰 입력 조건에서 출력 처리량이 14.9% 증가했다.

## 2. 적용 방법: 플래그 두 개면 충분하다

기본 사용법은 한 줄이다.

```bash
# 모든 레이어에 FP8 KV 캐시 적용
vllm serve meta-llama/Llama-3.1-8B --kv-cache-dtype fp8

# 하이브리드 어텐션 모델은 sliding-window 레이어 제외 권장
vllm serve gpt-oss-20b --kv-cache-dtype fp8 --kv-cache-dtype-skip-layers sliding_window
```

두 번째 플래그가 핵심이다. gpt-oss-20b처럼 글로벌 어텐션과 sliding-window(윈도우 크기 128) 레이어가 섞인 모델에서, sliding-window 레이어의 KV 캐시는 크기가 윈도우 크기에 묶여 있다. 이런 레이어를 양자화하면 긴 컨텍스트에서 얻는 메모리 이득은 없으면서 양자화 오버헤드만 떠안는다. 실제로 vLLM 팀의 초기 측정에서 gpt-oss-20b의 FP8 ITL 기울기는 BF16의 96%에 불과해 손익분기점이 70만 토큰을 넘겼다. 개선 후 skip-SW 변형(윈도우 레이어는 BF16 유지)에서 기울기가 BF16 대비 71%까지 내려왔다.

정확도가 걱정되면 캘리브레이션도 지원한다. 기본값은 캘리브레이션 없는 per-tensor 스케일(최악의 경우에 해당)이지만, 타깃 데이터로 스케일을 캘리브레이션하고 per-attention-head 단위까지 세분화할 수 있다. 공식 검증이 per-tensor 최악 조건에서도 이뤄졌다는 점이 중요하다. 캘리브레이션을 하면 결과는 이보다 더 좋아질 수밖에 없다.

## 3. 반드시 알아야 할 함정 3가지

### 함정 1: 긴 컨텍스트에서의 정확도 붕괴 (수정됨)

Hopper GPU의 FP8 Flash Attention 3 커널은 긴 컨텍스트에서 accumulation 정밀도를 잃었다. 128k needle-in-a-haystack 태스크에서 FP8 정확도가 BF16 baseline 91%에서 13%까지 추락한 것. 원인은 Tensor Core의 FP32 accumulation이 contraction 차원(=컨텍스트 길이)이 커지면 정밀도를 잃는 하드웨어 특성으로, DeepSeek-V3 훈련 당시에도 같은 문제가 보고된 바 있다.

vLLM 팀은 SageAttention2에서 착안한 two-level accumulation(부분 누적을 실제 FP32 레지스터에 기록)으로 정확도를 89%까지 복구했고, 이 수정은 현재 기본 적용되어 있다. 즉 최신 vLLM을 쓰면 이 문제는 대부분 해결되지만, 구버전에서 FP8 캐시를 쓰고 있다면 롱컨텍스트 정확도를 반드시 재검증해야 한다.

### 함정 2: sliding-window 레이어 (앞서 설명)

하이브리드 어텐션 모델에서 `--kv-cache-dtype-skip-layers sliding_window` 없이 전체 FP8을 쓰면 메모리는 절약되지만 디코드 속도 이득이 거의 사라진다. 메모리가 급하면 전체 FP8, 속도가 목표면 skip-SW가 정답이다.

### 함정 3: head_dim 256 모델의 prefill 역전

head 차원이 큰 모델(gemma-4-E2B, head_dim=256)은 two-level accumulation으로 레지스터 압력이 커져 prefill TTFT가 BF16보다 느려질 수 있다. head_dim 64·128 모델은 prefill과 디코드 모두 이득이지만, 256은 디코드 이득과 prefill 손실을 저울질해야 한다. 자기 모델의 head_dim을 먼저 확인하라.

## 4. prefix caching과 결합하면 진가가 드러난다

FP8 캐시와 함께 쓸 수 있는 두 번째 레버가 automatic prefix caching이다. vLLM v1의 프리픽스 캐싱은 KV 캐시를 블록 단위로 관리하며, 각 블록의 해시는 부모 블록 해시 + 블록 내 토큰 + 추가 해시(LoRA ID, 멀티모달 입력 해시, cache salt)로 계산된다. 시스템 프롬프트처럼 매 요청마다 반복되는 접두부의 KV를 재계산 없이 재사용하는 구조다. 참고로 v0.11부터 기본 해싱 알고리즘이 sha256으로 바뀌어 이전 버전의 해시 충돌 우려가 해소됐다.

멀티테넌트 환경이라면 보안 옵션도 확인하자. 요청에 `cache_salt`를 넣으면 해당 값이 첫 블록 해시에 섞여, 같은 salt를 공유하는 요청끼리만 캐시를 재사용한다. 타이밍 기반 공격(캐시 히트 여부를 레이턴시 차이로 추론)을 차단하는 기능이니, 신뢰 그룹이 다른 사용자가 같은 서버를 쓰는 경우엔 필수다.

```json
{
  "messages": [
    {"role": "system", "content": "You are a helpful assistant."},
    {"role": "user", "content": "긴 문서 내용..."},
    {"role": "user", "content": "이 문서에서 X를 찾아줘"}
  ],
  "cache_salt": "tenant-a-only"
}
```

## 5. 숫자로 보는 요약

| 항목 | H100 (Llama-3.1-8B) | B200 (Llama-3.1-8B) | gpt-oss-20b (H100) |
|------|--------------------|--------------------|--------------------|
| ITL 기울기 (BF16→FP8) | 4.37e-05 → 2.37e-05 (54%) | 1.80e-05 → 9.72e-06 (54%) | 8.94e-06 → 6.34e-06 (skip-SW, 71%) |
| 디코드 손익분기점 | 약 7k 토큰 | 약 4k 토큰 | 초기 버전 700k+ (개선 후 원문 참조) |
| 처리량 (동시성 8) | +14.9% | — | +4.8% |
| 정확도 영향 | 최대 1~2포인트 (추론 벤치마크) | 유사 | 유사 |

손익분기점이 수천 토큰 수준이라는 게 실무적으로 중요하다. 챗봇이나 에이전트 워크로드처럼 대화가 몇 턴만 이어져도 컨텍스트가 수천~수만 토큰에 도달하는 경우, FP8 캐시는 사실상 항상 유리하다. 반면 짧은 프롬프트·짧은 응답 위주라면 intercept 페널티 때문에 이득이 미미하다.

## 결론

- FP8 KV 캐시는 롱컨텍스트·디코드 헤비 워크로드에서 ITL 기울기를 BF16의 54~71%까지 낮추고, 처리량을 최대 15% 가까이 올린다 (vLLM 공식 벤치마크 기준).
- 하이브리드 어텐션 모델(gpt-oss 계열)은 반드시 `--kv-cache-dtype-skip-layers sliding_window`를 함께 쓸 것.
- head_dim 256 모델은 prefill이 느려질 수 있어 자기 모델의 구성을 먼저 확인할 것.
- 구버전 vLLM의 긴 컨텍스트 정확도 붕괴(91%→13%)는 two-level accumulation 수정으로 해결됐으니, 최신 버전 유지가 전제 조건이다.
- 시스템 프롬프트가 고정된 서비스라면 prefix caching과 결합하고, 멀티테넌트면 `cache_salt`로 캐시 격리까지 설정하라.

당장 시도할 첫 단계는 간단하다. 현재 서빙 중인 모델에 `--kv-cache-dtype fp8` 하나만 붙여 재시작하고, 실제 트래픽 패턴(평균 컨텍스트 길이, 동시성)에서 ITL과 처리량을 비교하는 것. 정확도는 자기 도메인의 평가셋으로 spot check하면 된다. 나머지 최적화는 그 결과를 보고 결정해도 늦지 않다.
