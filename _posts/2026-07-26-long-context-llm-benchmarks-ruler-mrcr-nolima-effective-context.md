# 1M 토큰 컨텍스트의 거짓말: RULER와 MRCR v2가 드러내는 장문 컨텍스트 LLM의 진짜 성능

"우리 모델은 1M 토큰을 처리합니다." 2026년, 프론티어 LLM의 사양표에서 이 문장을 빠뜨리는 모델은 거의 없다. Gemini 3.1 Pro, Claude Opus 4.7, GPT-5.5, DeepSeek V4 Pro — 어느 것이나 백만 토큰을 광고한다. 하지만 여기에 함정이 있다. **처리할 수 있다는 것과 제대로 검색·추론할 수 있다는 것은 완전히 다른 문제다.**

NVIDIA의 RULER, Google DeepMind의 MRCR v2, Adobe Research의 NoLiMa 벤치마크는 모두 같은 방향을 가리킨다. 핵심은 두 가지로 요약된다. 첫째, 멀티팩트 검색 작업에서 200K 토큰 이후부터 정확도가 눈에 띄게 하락한다(모델과 태스크에 따라 점수 하락폭이 크게 벌어진다). 둘째, RULER가 측정하는 **'유효 컨텍스트(effective context)'는 광고 길이의 50~65% 수준**에 그친다. 즉, 1M 토큰을 넣을 수는 있지만, 그 안의 사실을 정확히 찾아내는 능력은 광고 수치의 절반 수준이다.

이 글은 왜 그런 격차가 발생하는지, 어떤 벤치마크가 무엇을 측정하는지, 그리고 2026년에 장문 컨텍스트 모델을 프로덕션에 쓸 때 실제로 무엇을 기준으로 골라야 하는지를 정리한다.

## 왜 "광고된 컨텍스트"가 신뢰할 수 없는가

광고된 컨텍스트 길이는 **하드웨어 한계**다. 모델이 입력으로 받아들일 수 있는 최대 토큰 수를 의미할 뿐, 그 길이에서 얼마나 정확하게 동작하는지는 말해주지 않는다. 디지털 카메라의 메가픽셀 경쟁과 같다: 모든 사양표에 숫자가 있지만, 실제 사진 품질은 센서 크기와 렌즈에 달려 있다.

문제는 벤더들이 단일 바늘 검색(Needle-in-a-Haystack, NIAH) 점수를 인용한다는 것이다. 긴 문서에 사실 하나를 숨겨놓고 찾게 하는 테스트다. 대부분의 프론티어 모델은 1M 토큰에서도 90% 이상을 기록한다. 이 점수가 "1M 토큰에서 완벽한 리콜"이라는 마케팅 문구의 근거가 된다.

하지만 실제 작업은 이렇게 단순하지 않다. 계약서 200페이지에서 여섯 개의 관련 조항을 찾아 교차 검증하거나, 코드베이스 전체에서 여러 파일에 흩어진 버그 원인을 추적하는 작업은, 단일 바늘 검색과는 구조적으로 다른 문제다. 단일 바늘 점수가 높다고 해서 이런 멀티팩트 검색에서도 높을 것이라는 보장은 없다.

## 장문 컨텍스트를 측정하는 네 가지 벤치마크

장문 컨텍스트 평가는 단일 테스트가 아니다. 작업 유형에 따라 네 가지 범주로 나뉘며, 각각 다른 실패 모드를 포착한다.

### 1. RULER — NVIDIA의 위치 기반 리콜 스트레스 테스트

NVIDIA가 개발한 RULER(arXiv 2404.06654)는 단일 바늘부터 멀티키 집계까지 합성 태스크의 계층을 구성해, 토큰 깊이별로 정확도가 어디서 무너지는지를 격리한다. 핵심 발견은 대부분의 프론티어 모델이 멀티홉 작업에서 **광고된 컨텍스트의 50~65%만 실제로 신뢰 가능하게 사용**한다는 것이다. 1M 토큰을 광고해도 멀티니들 작업에서 유효한 범위는 200K~400K에 그친다.

```python
# RULER 핵심 태스크 카테고리 (논문 기준, arXiv 2404.06654)
# 1. NIAH (single/multi): 문서에 숨겨진 사실 검색
#    - MK-NIAH: Multi-Key 변형, 여러 키로 집계하는 태스크
# 2. VT (Variable Tracking): 변수 간 할당 추적
# 3. CWE (Common Words Extraction): 빈도 기반 추출
# 4. FWE (Frequent Words Extraction): 다중 빈도 단어 추출
# 각 태스크를 4K, 8K, ..., 1M 토큰에서 반복 실행해
# 토큰 깊이별 정확도 저하 패턴을 측정
```

### 2. MRCR v2 — Google DeepMind의 멀티라운드 검색

MRCR v2(Multi-round Coreference Resolution)는 Google DeepMind의 eval_hub에서 공개한 평가로, 기반 방법론은 Michelangelo 연구(arXiv 2409.12640)에서 비롯되었다. 대화형 검색에 가깝다. 모델이 수십만 토큰 이전에 도입된 사실을 여러 턴에 걸쳐 추적해야 한다. 에이전트 파이프라인이나 긴 채팅 세션을 시뮬레이션하므로, 단일 프롬프트 테스트보다 실제 워크로드를 잘 반영한다. **8개 바늘을 1M 토큰에 흩어놓는 8-needle 변형에서 점수가 급격히 하락**하는 것이 핵심 관찰 지점이다(llm-stats.com에서 리더보드를 공개 중).

### 3. NoLiMa — Adobe Research의 '표면 매칭' 제거

많은 모델이 바늘 테스트에서 강해 보이는 이유는 질문과 정답 텍스트가 문자적으로 겹치기 때문이다. NoLiMa(arXiv 2502.05167, ICML 2025 게재)는 이 단축키를 제거한다. 질문을 바꾸어 말하고(paraphrase), 증거를 문서 전체에 분산시켜, 모델이 근접 매칭이 아니라 **추론**으로 답을 찾아야 하게 만든다. 결과는 충격적이다: GPT-4o가 기준선 99.3%에서 32K 컨텍스트에서 69.7%로 떨어진다. 대부분의 벤더가 NoLiMa 결과를 조용히 공개하지 않는 이유가 여기에 있다.

### 4. HELMET — Princeton의 다운스트림 작업 평가

Princeton NLP의 HELMET(arXiv 2410.02694)는 128K 컨텍스트에서 RAG, 인컨텍스트 학습(ICL), 재순위, 요약, 지시 준수를 종합 평가한다. HELMET의 가장 중요한 발견은 **합성 태스크(NIAH)가 다운스트림 성능을 예측하지 못한다**는 것이다. 바늘찾기에서 완벽한 모델도 같은 건초더미를 요약하라 하면 환각을 일으킨다. 이는 합성 벤치마크 점수만 믿고 프로덕션에 투입하면 안 되는 이유다.

## 핵심 개념: 유효 컨텍스트 (Effective Context)

이 네 가지 벤치마크가 공통으로 가리키는 개념이 **유효 컨텍스트(effective context)**다. 정의는 단순하다: 모델이 광고하는 최대 길이가 아니라, **실제로 신뢰할 수 있는 정확도를 유지하는 길이**를 의미한다.

예를 들어 모델이 1M 토큰을 광고하지만 RULER 멀티니들에서 400K 이후 정확도가 70% 밑으로 떨어진다면, 그 모델의 유효 컨텍스트는 약 400K로 봐야 한다. 프로덕션에서 800K 토큰을 입력에 넣으면, 마지막 400K에 있는 정보는 절반 가까이 놓칠 수 있다.

## 2026년 모델별 실제 성능: 컨텍스트 길이별 선택 가이드

여러 벤치마크를 종합하면, **모델이 강한 구간이 다르다**는 것이 핵심 통찰이다. 단일 바늘 검색에서 1M을 버티는 모델이 멀티바늘 128K에서 무너지고, 그 역도 성립한다.

**32K 토큰 이하:** 모든 프론티어 모델이 문제없다. 추론 품질, 지연, 가격으로 고르면 된다. 장문 벤치마크는 이 구간에서 차별화 요소가 아니다.

**32K~128K 토큰:** 에이전트 단일 루프와 중간 규모 문서 분석의 최적점이다. Claude Opus 4.6(또는 후속 모델)이 MRCR v2 8-needle 128K에서 선두를 유지하는 것으로 보고되며, 멀티니들 교차 추론 작업에 적합하다. 단, 토큰당 비용이 높다.

**128K~256K 토큰:** 멀티문서 분석 구간. 이 영역에서는 Gemini 계열이 비용 대비 검색 품질에서 유리한 것으로 평가된다. 멀티니들 정확도 하락이 상대적으로 완만하기 때문이다.

**256K~1M 토큰:** 단일 바늘 검색에서는 여러 모델이 90% 이상을 유지하지만, 멀티팩트 검색에서는 대부분 급격히 하락한다. 이 구간에서 신뢰 가능한 검색이 필요하다면, 벤치마크 데이터를 직접 확인해야 한다. 경험적으로 약 500K 토큰 부근을 넘기면 **RAG + 리랭커 조합이 순수 장문 컨텍스트보다 비용과 정확도 양면에서 실질적으로 유리**해지는 경향이 관찰된다(토큰당 비용이 선형 증가하는 반면, 멀티니들 정확도는 비례해 올라가지 않기 때문이다).

> **주의:** 모델 벤치마크 점수는 버전과 측정 시점에 따라 빠르게 변한다. 위 등급은 2026년 중반 기준 공개된 데이터를 종합한 것이며, 특정 수치를 인용할 때는 최신 리더보드(llm-stats.com, Hugging Face 등)를 반드시 직접 확인하라.

## 실전: 유효 컨텍스트를 직접 측정하는 방법

벤치마크 점수만 믿지 말고, 자신의 실제 워크로드로 간단한 위치 기반 평가를 직접 수행할 수 있다. 핵심은 "lost in the middle" 효과를 확인하는 것이다.

```python
import json, random

def build_position_test(context_tokens, target_facts, model_client):
    """
    실제 워크로드와 비슷한 긴 컨텍스트에 사실을
    시작/중간/끝 세 위치에 배치하고 정확도를 측정한다.
    """
    results = {"start": 0, "middle": 0, "end": 0}
    for pos in ["start", "middle", "end"]:
        correct = 0
        for fact in target_facts:
            # fact를 지정 위치에 삽입한 긴 프롬프트 생성
            prompt = insert_fact_at_position(
                filler_text=context_tokens, fact=fact, position=pos
            )
            # 모델에게 fact와 관련된 질문
            resp = model_client.complete(
                prompt=prompt,
                question=fact["question"]
            )
            if fact["answer"].lower() in resp.lower():
                correct += 1
        results[pos] = correct / len(target_facts)
    return results

# 중간 위치 점수가 시작/끝보다 현저히 낮으면
# "lost in the middle" 문제가 있는 것
```

이 테스트의 핵심은 **중간에 배치된 사실의 정확도가 시작과 끝보다 얼마나 낮은지**를 보는 것이다. Liu et al.(2023, "Lost in the Middle", arXiv 2307.03172)이 문서화한 이 효과는 2026년에도 여전히 존재하며, 컨텍스트가 길어질수록 심화된다.

## 장문 컨텍스트 vs RAG: 실제 선택 기준

"1M 토큰이 되면 RAG가 필요 없어지나?"라는 질문이 자주 나온다. 답은 **작업 유형과 토큰 깊이에 달려 있다**.

단일 문서 깊이 분석(계약서, 논문 등)에서 128K 이하라면, RAG 없이 전체 컨텍스트를 넣는 것이 더 정확할 수 있다. 문서 내 문맥을 온전히 유지할 수 있기 때문이다.

하지만 여러 문서를 크로스 참조하거나, 컨텍스트가 256K를 넘어가면 상황이 바뀐다. 멀티니들 정확도 하락과 비용이 동시에 문제가 된다. 이 경우 하이브리드 패턴이 현실적인 해법이다: RAG로 관련 청크를 먼저 검색하고, 리랭커로 상위 N개를 선별한 뒤, 그것들만 장문 컨텍스트 모델에 넣어 심층 분석하는 방식이다.

```python
# 하이브리드 라우팅 패턴 (개념)
def hybrid_long_context(query, document_store):
    # 1단계: 벡터 검색으로 후보 청크 추출 (저비용)
    candidates = document_store.search(query, top_k=50)

    # 2단계: 리랭커로 상위 청크 선별 (정확도 향상)
    ranked = reranker.score(query, candidates)[:8]

    # 3단계: 선별된 청크만 장문 컨텍스트 모델에 전달
    context = "\n\n".join(chunk.text for chunk in ranked)
    # 8개 청크 × 평균 4K = ~32K 토큰 → 유효 컨텍스트 내
    return frontier_model.complete(prompt=context, question=query)
```

이 패턴은 전체 문서를 1M 토큰에 채우는 것보다 비용을 획기적으로 줄이면서, 유효 컨텍스트 내에서 모델의 추론 능력을 최대한 활용한다.

## 프로덕션 적용 시 주의사항

**첫째, 비용이 선형이 아니다.** 장문 컨텍스트 작업에서는 입력 토큰이 출력보다 압도적으로 많다. 256K 입력 한 건이 프론티어 모델에서 1달러를 넘을 수 있다. 프롬프트 캐싱(Anthropic의 1시간 캐시, Google의 컨텍스트 캐싱 등)을 쓰면 같은 긴 컨텍스트를 재사용할 때 읽기 비용을 크게 줄일 수 있다. 재사용 빈도가 높은 워크로드에서는 캐싱이 모델 선택보다 비용에 더 큰 영향을 미친다.

**둘째, 단일 벤치마크에 의존하지 마라.** NIAH 점수만 보고 모델을 고르면, 멀티팩트 작업에서 실패한다. 자신의 작업 유형에 맞는 벤치마크(RULER의 멀티키, MRCR v2의 멀티니들, NoLiMa의 추론)를 확인하라.

**셋째, 벤더 공시 수치를 맹신하지 마라.** 벤치마크 환경(프롬프트 형식, 측정 도구, 토크나이저)에 따라 점수가 달라진다. 가능하면 독립 제3자 리더보드(llm-stats.com, Hugging Face 리더보드)를 교차 확인하라.

## 결론: 핵심 요약

- **광고된 1M 토큰 ≠ 유효 1M 토큰.** 멀티팩트 검색에서 실제 신뢰 가능한 범위는 광고 길이의 50~65%에 그친다(RULER).
- **벤치마크는 작업 유형별로 다르게 봐야 한다.** 단일 바늘(NIAH), 멀티바늘(MRCR v2), 추론(NoLiMa), 다운스트림(HELMET)이 각각 다른 실패 모드를 포착한다.
- **모델이 강한 구간이 다르다.** 128K 이하 멀티홉은 Claude 계열, 128K~256K 비용 효율은 Gemini 계열, 극장문 단일 검색은 모델별 확인이 필요하다.
- **약 500K 토큰이 분기점이다.** 이를 넘기면 RAG + 리랭커 하이브리드가 순수 장문 컨텍스트보다 비용과 정확도 양면에서 유리해진다.
- **직접 측정하라.** 위치 기반 평가(start/middle/end)로 자신의 워크로드에서 "lost in the middle" 효과를 확인하는 것이 벤치마크 점수보다 신뢰할 수 있다.

다음 단계로 당장 시도할 것: 현재 프로덕션에서 쓰는 모델로 간단한 위치 기반 테스트를 돌려보라. 중간 위치 정확도가 시작과 끝보다 20점 이상 낮다면, 입력 길이를 줄이거나 RAG 청크 크기를 조정해야 할 신호다.
