# vLLM, SGLang, TensorRT-LLM: 2026년 LLM 추론 엔진을 고르는 6가지 질문

LLM을 학습시키고 나면 진짜 싸움은 서빙에서 시작된다. 같은 모델이라도 어떤 추론 엔진(inference engine) 위에 올리느냐에 따라 초당 처리량이 수십% 달라지고, GPU 비용이 그만큼 움직인다. 2026년 현재 프로덕션에서 가장 많이 쓰이는 오픈소스 엔진은 vLLM, SGLang, TensorRT-LLM 세 개로 압축된다.

문제는 이 셋의 "기능 체크리스트"가 거의 같아졌다는 점이다. 연속 배치(continuous batching), 페이지드 KV 캐시(paged KV cache), 프리픽스 캐싱, FP8 양자화, 추론 디코딩(speculative decoding)까지 세 엔진 모두 지원한다. 표면적 기능 비교로는 결정을 내릴 수 없다. 결국 **아키텍처의 근본 차이**와 그것이 당신의 워크로드에 어떤 영향을 주는지를 이해해야 한다.

이 글은 그 근본 차이를 세 가지 메모리/실행 모델로 정리하고, 실제 선택을 위한 6가지 질문을 제공한다.

## 세 엔진이 근본적으로 다른 지점: 메모리와 실행 모델

기능은 수렴했지만, KV 캐시를 관리하고 GPU 명령을 실행하는 방식은 완전히 다르다. 이것이 모든 성능·운영 차이의 출발점이다.

### vLLM — PagedAttention (운영체제식 가상 메모리)

vLLM은 2023년 PagedAttention 논문(Kwon et al., arXiv:2309.06180)으로 현대 추론 엔진 카테고리를 사실상 정의했다. 핵심 통찰은 단순하다: **KV 캐시를 운영체제의 가상 메모리처럼 다루어라.**

기존 방식은 요청 하나당 연속된 VRAM 버퍼를 미리 할당했다. 컨텍스트 길이가 2048이면 2048 슬롯짜리 버퍼를 통째로 잡는 식이다. 이렇게 하면 단편화가 심해진다. 요청이 짧아도 긴 길이만큼 예약해 두어야 하고, 요청이 끝나면 그 빈 공간을 재활용하기 어렵다. 단편화로 낭비되는 VRAM이 ~40%에 달한다는 추정도 있다.

PagedAttention은 이 버퍼를 16 토큰(설정 가능) 단위의 '페이지'로 쪼갠다. 요청이 오면 필요한 만큼만 페이지를 할당하고, 끝나면 회수한다. 운영체제의 페이지 테이블과 같은 블록 테이블(block table)로 매핑을 관리한다. 결과적으로 단편화가 4% 이하로 떨어지고, 같은 VRAM에 훨씬 많은 동시 요청을 끼워 넣을 수 있다.

```bash
# vLLM 서빙 — pip install 한 줄로 시작
pip install vllm

# OpenAI 호환 서버 구동 (Llama 3.1 8B, 단일 GPU)
vllm serve meta-llama/Llama-3.1-8B-Instruct \
  --tensor-parallel-size 1 \
  --quantization fp8 \
  --max-model-len 8192
```

vLLM의 실질적 강점은 폭이다. 모델 레지스트리에 400개 이상의 아키텍처가 등록되어 있고, 새로운 HuggingFace 모델을 추가하려면 보통 50~200줄짜리 Python 클래스 하나면 충분하다. 하드웨어도 넓다: NVIDIA(CUDA), AMD(ROCm, MI300X에서 특히 성숙), Google TPU, Intel Gaudi, CPU 폴백까지. 스케줄러가 Python으로 작성되어 있어 고동시 환경에서는 단계당 200~500μs의 오버헤드가 생기지만, 대부분의 워크로드에서는 GPU 연산과 스케줄링이 비동기로 겹쳐 숨겨진다.

### SGLang — RadixAttention (접두사 트리 캐시)

SGLang(Zheng et al., 2024)은 두 가지 목표로 설계됐다. (1) 다중 턴·조건부·병렬 생성을 표현하는 구조화 생성 언어, (2) 그것을 효율적으로 실행하는 런타임. 여기서 아키텍처를 가르는 핵심은 **RadixAttention**이다.

vLLM의 프리픽스 캐시가 요청당 단일 공유 접두사(주로 시스템 프롬프트)를 재사용한다면, RadixAttention은 **모든 요청의 캐시된 KV 페이지 전체에 대해 라딕스 트리(트라이)를 구축**한다. 새 요청이 들어오면, 시스템 프롬프트뿐 아니라 이전에 처리한 모든 시퀀스 중 가장 긴 공통 접두사 경로를 트리에서 찾아 그 페이지를 재사용한다.

이것이 빛을 발하는 대표 워크로드가 퓨샷 프롬프팅이다. 예시 N개를 앞에 붙이는 패턴에서, N개 예시의 KV 계산 중 상당 부분을 첫 요청 이후로 생략할 수 있다. 접두사 중복이 높은 워크로드에서는 프리필(prefill) 연산의 70~90%를 제거할 수 있다고 보고된다.

```python
# SGLang 구조화 생성 — 접두사 공유가 자동으로 최적화되는 패턴
import sglang as sgl

@sgl.function
def multi_choice_qa(s, question, choices):
    s += sgl.system("당신은 도움이 되는 비서입니다.")
    s += sgl.user(question)
    # N개 분기(fork)가 동일한 접두사를 공유 → RadixAttention이 자동 캐시 히트
    with s.fork(len(choices)) as forks:
        for i, fork in enumerate(forks):
            fork += f"정답은 {choices[i]}: "
            fork += sgl.gen("verdict", max_tokens=20)
```

SGLang의 두 번째 강점은 **대규모 MoE 모델**이다. 전문가 병렬(expert parallelism, EP) 구현이 깊고, DeepSeek-R1/V3(671B 매개변수) 같은 풀스케일 MoE를 GB200 NVL72 클러스터에서 서빙할 때 경쟁력 있는 성능을 낸다. DeepSeek과 Qwen이 originated한 중국 ML 커뮤니티의 기여가 집중되어 있어 이 모델군이 일급 지원을 받는다. 또한 구조화 출력(JSON 스키마, 정규식, 문법)을 스케줄러 수준에서 통합해, 사후 토큰 필터 방식보다 오버헤드가 낮다.

고동시(100+ 동시 요청) 환경에서는 Python 스케줄러 오버헤드가 더 많은 작업을 C++/CUDA로 밀어내는 SGLang이 유리한 구간이 있다. 단, RadixAttention 트리 탐색 자체는 요청당 약간의 오버헤드를 더하므로, 모든 요청이 서로 다른(캐시 히트가 없는) 워크로드에서는 이점이 사라진다.

### TensorRT-LLM — 컴파일드 엔진 (하드웨어 특화 실행 계획)

TensorRT-LLM은 접근 자체가 다르다. Python 스케줄러가 PyTorch 순전파를 구동하는 대신, **모델을 TensorRT 엔진으로 컴파일**한다. 결과물은 융합된 연산, 커널 자동 튜닝, 전 단계 CUDA 그래프 캡처가 적용된 직렬화된 하드웨어 특화 실행 계획이다.

파이프라인은 세 단계다:

```bash
# 1단계: 체크포인트 변환 (양자화 + 가중치 레이아웃 변환)
python convert_checkpoint.py --model_type llama \
  --output_dir ./llama-8b-fp8 --use_fp8

# 2단계: 엔진 빌드 — 실제 GPU에서 커널 벤치마크를 돌려 최적 variant 선택
trtllm-build --checkpoint_dir ./llama-8b-fp8 \
  --output_dir ./llama-8b-engine \
  --max_batch_size 32 --max_seq_len 8192

# 3단계: 빌드는 5분(소형) ~ 2시간+(대형/다중 GPU). 모델·시퀀스 길이·GPU 종류가
#        바뀔 때마다 재빌드해야 한다.
```

왜 더 빠른가. 첫째, 연산자 융합이 적극적이다. 어텐션, 레이어 정규화, 선형 레이어가 단일 커널로 융합되어 GPU에 맞춰 보정된다. 둘째, CUDA 그래프가 순전파 전체를 덮어 CPU 측 커널 런치 오버헤드를 없앤다(Python에서 커널 하나를 런치할 때마다 ~5~10μs; 32레이어 모델에서 저배치 시 의미 있는 차이). 셋째, 빌드 단계에서 여러 커널 구현을 실제 하드웨어에서 벤치마크해 각 형태(shape)마다 가장 빠른 것을 고른다.

운영 비용은 여기서 나온다. **모델(양자화 수준, 최대 시퀀스 길이, 최대 배치 크기, GPU 종류)이 바뀔 때마다 엔진을 다시 빌드**해야 한다. 설정 변경이 아니라 수시간의 컴파일이다. TensorRT-LLM을 쓰는 팀은 엔진 빌드를 중심으로 CI 파이프라인을 구축하고 `.engine` 파일을 모델 산출물과 함께 버전 관리한다. 실질적인 엔지니어링 부담이다.

하드웨어는 NVIDIA 전용(A100, H100/H200, B200/GB200)이다. 모델 지원 폭은 vLLM보다 좁지만 핵심 계열(Llama, Mistral, Qwen, DeepSeek, GPT, T5)은 커버한다. 새 아키텍처를 추가하려면 TensorRT-LLM 플러그인 연산을 구현해야 하는데, vLLM의 Python 클래스 추가보다 훨씬 어렵다.

## 성능: 무엇을 기대할 수 있는가

정확한 수치는 하드웨어·배치 크기·시퀀스 길이·양자화에 따라 크게 달라지므로, 아래는 **대표적인 H100 SXM 80GB 배포에서 보고되는 경향**으로 읽어야 한다(출처: 추론 엔지니어링 커뮤니티 벤치마크 및 각 엔진 문서).

- **밀집(dense) 모델 최대 처리량**: TensorRT-LLM이 vLLM 대비 약 15~25% 높은 것으로 보고된다. 컴파일드 커널과 CUDA 그래프 경로가 고배치에서 유리하다.
- **고동시 + 접두사 공유**: SGLang의 RadixAttention이 유리 구간이 있다. 100개 이상 동시 요청에 공통 접두사가 많은 워크로드에서 SGLang이 vLLM과 경쟁적이거나 앞선다.
- **대형 MoE (DeepSeek-R1 671B)**: SGLang의 EP 구현이 강점이다.
- **저배치(지연에 민감한 단일 사용자)**: 세 엔진 격차가 좁아진다. 메모리 대역폭이 병목이라 컴파일 이점이 사라진다.

한 가지 주의: 엔진 간 벤치마크는 **서로 다른 하드웨어나 서로 다른 워크로드로 돌린 결과를 비교하면 무의미**하다. 당신의 실제 워크로드로 직접 측정해야 한다.

## 선택 프레임워크: 순서대로 물어보고 첫 번째 매칭에서 멈춘다

엔진 선택을 하나의 수치(예: "가장 빠른 처리량")로 환원하면 잘못된 결정을 한다. 다음 질문들을 순서대로 적용하라.

**질문 1 — 하드웨어가 비 NVIDIA인가?** → vLLM(또는 AMD ROCm이라면 SGLang). TensorRT-LLM은 NVIDIA 전용이므로 아예 후보에서 빠진다. MI300X 클러스터라면 vLLM과 SGLang이 후보다.

**질문 2 — 대형 MoE 모델(DeepSeek-R1/V3, Mixtral 8×22B, Qwen-MoE)을 규모 있게 서빙하는가?** → SGLang. 전문가 병렬 구현과 RadixAttention이 이 아키텍처에서 처리량/비용 비율이 가장 좋다.

**질문 3 — 구조화 출력(JSON 스키마, 제약 문법)이 핵심 워크로드 기능인가?** → SGLang. 스케줄러 수준의 네이티브 제약 디코딩이 vLLM의 플러그인 방식보다 의미 있게 효율적이다.

**질문 4 — 성능이 최우선이고, NVIDIA 하드웨어에 안정적으로 고정되어 있으며, 모델 버전이 자주 바뀌지 않고, 운영 복잡도를 흡수할 엔지니어링 여력이 있는가?** → TensorRT-LLM. 밀집 모델에서 15~25% 처리량 이점이 규모에서는 GPU 비용으로 직결된다.

**질문 5 — 아직 모델·아키텍처·프롬프팅 전략을 반복 중인가?** → vLLM. 한 플래그로 어떤 HuggingFace 모델이든 교체할 수 있는 빠른 반복 루프가, 개발 단계에서는 원시 처리량보다 훨씬 가치 있다.

**질문 6 — 기본값** → vLLM. 가장 넓은 커버리지, 가장 낮은 운영 부담, 여전히 우수한 성능. 현재 프로덕션 배포의 다수가 vLLM 위에서 돌아간다.

## 자체 호스팅을 해야 하는가, 아니면 빠져나갈 것인가

이 글 전체의 전제는 "GPU를 직접 굴린다"는 것이다. 그 전제 자체를 먼저 검증하라. 자체 호스팅이 의미 있는 경우는 한정적이다: 대량에서의 비용 통제, 데이터 거주지(data residency) 요구, 커스텀 모델, 이미 보유한 하드웨어. 이런 조건이 아니라면 호스팅 API나 NIM 같은 패키지형 마이크로서비스가 운영 오버헤드를 감안하면 더 나을 수 있다.

## 엔진 사이의 마이그레이션 비용

vLLM에서 TensorRT-LLM로 중간에 갈아타는 것은 만만치 않다. 1~2스프린트를 투자해야 한다:

- 엔진 빌드 CI 파이프라인 구축(빌드, 캐시, `.engine` 파일 버전 관리)
- 양자화 + 컴파일이 출력을 바꿀 수 있으므로 평가 벤치마크 대비 출력 품질 검증
- vLLM 고유 API 기능에 의존했다면 요청 처리 로직 수정

팀이 작거나 빠르게 움직이는 중이라면, 이 마이그레이션 비용만으로 규모가 요구하기 전까지 vLLM에 머무는 이유가 충분하다.

## 핵심 요약

- **세 엔진의 기능 격차는 사실상 닫혔다.** 연속 배치, 페이지드 KV 캐시, 프리픽스 캐싱, FP8 양자화를 모두 지원한다. 결정은 아키텍처와 운영 복잡도로 갈린다.
- **근본 차이는 세 가지**: vLLM의 PagedAttention(운영체제식 페이지 메모리), SGLang의 RadixAttention(접두사 트리 캐시 + MoE 강점), TensorRT-LLM의 컴파일드 엔진(하드웨어 특화 실행 계획).
- **기본 선택은 vLLM이다.** 가장 넓은 모델·하드웨어 커버리지에 가장 낮은 운영 부담. 80% 팀에 정답이다.
- **SGLang으로 가는 신호**: 대형 MoE, 고동시 + 접두사 공유 워크로드, 구조화 출력이 핵심.
- **TensorRT-LLM으로 가는 신호**: NVIDIA 고정, 안정적인 모델 버전, 프로파일된 증거가 있는 처리량 병목, 엔진 빌드 파이프라인을 유지할 여력.
- **섣부른 최적화를 피하라.** 합성 벤치마크가 아니라 당신의 실제 워크로드로 측정하고, 엔진이 병목이라는 프로파일 증거가 있을 때만 마이그레이션하라.

**당장 시도할 첫 단계**: vLLM으로 프로토타입을 서빙하라(`pip install vllm && vllm serve <model>`). 그리고 실제 트래픽 패턴을 측정하라—접두사 중복률, 동시 요청 수, 지연 민감도. 그 측정 결과가 두 번째 엔진으로 갈아탈지를 판단한다.
