# AI 에이전트가 대화를 기억하지 못하는 진짜 이유: LoCoMo·LongMemEval 벤치마크로 배우는 메모리 설계

LLM 기반 에이전트가 실서비스에서 가장 먼저 무너지는 지점은 추론 능력이 아니라 기억이다. 사용자가 어제 말한 취향을 오늘 잊어버리고, 3주 전에 취소한 약속을 여전히 유효하다고 답하고, 긴 대화가 이어지면 초반에 받은 정보를 조용히 놓친다. 컨텍스트 윈도우가 수십만~수백만 토큰으로 커진 지금도 이 문제는 사라지지 않았는데, 이유는 단순하다. **컨텍스트에 넣는 것과 기억하는 것은 다른 능력**이기 때문이다.

이 글에서는 에이전트 메모리를 측정하는 두 표준 벤치마크인 LoCoMo와 LongMemEval이 실제로 무엇을 측정하는지 분해하고, LongMemEval 논문이 실험으로 검증한 메모리 설계 원칙을 실무 코드 관점에서 정리한다. 메모리 프레임워크를 고르는 것보다 먼저, "무엇을 어떻게 저장하고 언제 꺼내 읽을지"의 설계를 이해하는 것이 지금 시점의 에이전트 개발에서 훨씬 높은 레버리지를 가진다.

## 1. 왜 긴 컨텍스트가 메모리 문제를 해결하지 못하는가

"컨텍스트 윈도우만 길면 전부 넣으면 되지 않나"라는 생각은 두 지점에서 깨진다.

첫째, 비용과 지연이다. 매 요청마다 전체 대화 히스토리를 다시 토큰으로 밀어 넣는 구조는 트래픽이 늘수록 선형으로 비용이 증가한다. 대화가 수개월씩 쌓이는 개인 비서 시나리오에서는 아예 물리적으로 불가능해진다.

둘째, 그리고 더 본질적인 문제는 **롱컨텍스트 모델도 지속적인 상호작용 속에서는 정확도가 크게 떨어진다**는 점이다. LongMemEval 논문(ICLR 2025)은 상용 챗 어시스턴트와 롱컨텍스트 LLM이 지속적인 상호작용에서 정보를 기억하는 데 있어 최대 30%의 정확도 하락을 보인다고 보고한다. 즉 모델이 "읽을 수는 있지만" 경쟁하는 정보 사이에서 과거 사실을 안정적으로 붙잡아두지 못한다. 최신 사실이 이전 사실을 덮어쓰는 지식 업데이트 실패, 시간 순서를 뒤섞는 시간 추론 실패가 대표적이다.

## 2. 두 벤치마크가 측정하는 것

### LoCoMo: 아주 긴 대화 자체를 만들어내는 벤치마크

LoCoMo(Evaluating Very Long-Term Conversational Memory of LLM Agents, TMLR)는 Snap Research와 UNC Chapel Hill, USC가 만든 데이터셋으로, **평균 300턴, 약 9K 토큰, 최대 35개 세션에 이르는 초장기 대화**를 수집했다는 특징이 있다. 기존 장기 대화 연구가 5개 세션 이내를 다뤘던 것과 대비된다.

흥미로운 점은 데이터 생성 방식이다. 두 LLM 에이전트에 각각 서로 다른 페르소나와 시간 순서로 배열된 삶의 사건 그래프(temporal event graph)를 부여하고 대화를 시뮬레이션한 뒤, 사람 어노테이터가 장기 일관성과 그라운딩을 검수했다. 그 위에 질의응답, 이벤트 요약, 멀티모달 대화 생성이라는 세 과제를 얹어 기억 능력을 측정한다.

### LongMemEval: 기억을 다섯 개 능력으로 쪼개는 벤치마크

LongMemEval(arXiv 2410.10813)은 접근을 달리한다. 자유롭게 확장 가능한 사용자-어시스턴트 대화 히스토리 안에 **정성적으로 큐레이션된 500개 질문**을 심고, 장기 기억을 다섯 가지 핵심 능력으로 분해해 측정한다.

1. **정보 추출** — 과거 세션에서 언급된 사실을 정확히 꺼내오는 능력
2. **멀티세션 추론** — 여러 세션에 흩어진 정보를 연결해 답하는 능력
3. **시간 추론** — "지난달에", "3주 전부터" 같은 시간 관계를 올바르게 처리하는 능력
4. **지식 업데이트** — 이후 세션에서 수정된 정보를 반영해 이전 정보를 무효화하는 능력
5. **기권(abstention)** — 기억에 없는 질문에 지어내지 않고 모른다고 답하는 능력

이 분류가 실무적으로 중요한 이유는, 실제 서비스 장애의 원인이 능력별로 다르기 때문이다. "엉뚱한 답변"이라는 증상 뒤에는 검색 실패(추출), 연결 실패(멀티세션), 순서 혼동(시간), 낡은 사실(업데이트), 환각(기권)이라는 서로 다른 병이 숨어 있다. 벤치마크 점수만 보지 말고 어떤 능력이 무너졌는지 분해해야 처방이 가능하다.

## 3. 논문이 검증한 설계 원칙: 인덱싱 · 검색 · 리딩

LongMemEval의 가장 실용적인 기여는 장기 기억 설계를 **인덱싱 → 검색 → 리딩** 3단계로 나누고, 각 단계의 최적화를 실험으로 검증한 것이다. 프레임워크 선택 이전에 이 구조를 이해하는 것이 핵심이다.

### 인덱싱: 세션을 통째로 저장하지 말고 분해하라

첫 번째 최적화는 **세션 분해(session decomposition)** 다. 대화 로그를 세션 단위로 통째로 임베딩해 저장하면 검색 단위가 너무 굵어져서, 한 세션 안에 섞여 있는 여러 주제의 사실이 하나의 벡터로 뭉개진다. 논문은 세션을 finer-grained 값 단위로 쪼개 저장할 것을 권고한다.

```python
from pydantic import BaseModel
from datetime import datetime

class MemoryFact(BaseModel):
    """세션 분해의 결과로 저장되는 단일 기억 단위"""
    content: str                    # "사용자는 아랫배 통증으로 병원 예약을 취소했다"
    session_id: str                 # 출처 세션 추적
    captured_at: datetime           # 언제 알게 되었는지
    valid_until: datetime | None = None  # None이면 현재 유효 (지식 업데이트용)
    supersedes: str | None = None   # 이 기억이 대체하는 이전 기억의 id

def decompose_session(session_log: list[dict]) -> list[MemoryFact]:
    """세션 로그를 사실 단위로 분해하는 프롬프트 파이프라인의 골격.
    LLM에게 '대화에서 독립적으로 참조 가능한 사실 단위만 추출'하라고 지시하고,
    결과를 MemoryFact로 파싱한다."""
    ...
```

여기서 `supersedes`와 `valid_until` 필드가 지식 업데이트 능력의 뼈대다. "나 커피 끊었어"라는 새 사실이 들어오면 이전의 "매일 아메리카노 마신다" 기억을 삭제하지 않고 무효화 표시만 하면, "언제부터 커피를 끊었는지"라는 시간 추론 질문에도 답할 수 있다.

### 인덱싱 두 번째: 팩트 증강 키 확장

두 번째 최적화는 **팩트 증강 키 확장(fact-augmented key expansion)**이다. 사용자 발화("그때 그 거래 처분했어")를 그대로 임베딩하면, 나중에 "주식"이라는 질문과는 벡터 공간에서 만나지 못한다. 저장 시점에 사실에 관련된 개체·주제 키를 붙여두는 것이 검색 회수율을 끌어올린다.

### 검색: 시간 인지 쿼리 확장

세 번째 최적화는 **시간 인지 쿼리 확장(time-aware query expansion)**이다. "작년 여름에 내가 뭐 했지?"라는 질문을 날것 그대로 임베딩 검색에 던지면 시간 조건이 무시된다. 질의의 상대 시간 표현을 절대 날짜 범위로 변환해 검색 범위를 좁히는 것이다.

```python
from datetime import datetime, timedelta

def expand_query_with_time(query: str, now: datetime,
                           memory_index) -> list[MemoryFact]:
    """상대 시간 표현을 절대 범위로 바꿔 검색 범위를 좁히는 예시.
    실제로는 LLM으로 query 안의 시간 표현을 파싱한다."""
    time_filters = parse_relative_time(query, now)  # "작년 여름" -> (start, end)

    candidates = memory_index.search(
        query=query,
        date_range=time_filters,   # 시간 필터를 검색에 주입
        k=20,
    )
    return rank_and_dedupe(candidates)
```

### 리딩: 기억을 컨텍스트에 어떻게 올릴 것인가

마지막 단계는 검색된 기억을 프롬프트에 어떻게 배치할지 결정하는 것이다. 이 단계의 실무 요점은 두 가지다. 최신 기억 우선(시간 역순 정렬로 최신 사실이 오래된 사실을 덮어쓰게)과, 기억에 없는 질문에 대한 기권 지시를 시스템 프롬프트에 명시하는 것이다. LongMemEval의 다섯 능력 중 기권이 별도 항목으로 존재한다는 사실 자체가, 검색된 것이 없을 때 지어내는 행동이 얼마나 흔한 실패 모드인지 보여준다.

## 4. 서베이가 제시하는 bigger picture: 기억의 세 축

2025년 말 arXiv에 공개된 서베이 "Memory in the Age of AI Agents"(arXiv 2512.13564)는 파편화된 에이전트 메모리 연구를 세 축으로 정리한다.

- **형태(forms)**: 토큰 레벨 기억(컨텍스트에 텍스트로 존재), 파라메트릭 기억(모델 가중치에 각인), 래텐트 기억(압축된 은닉 표현)
- **기능(functions)**: 사실 기억(factual), 경험 기억(experiential), 작업 기억(working)
- **동역학(dynamics)**: 기억이 형성되고 → 진화하고 → 검색되는 수명 주기

이 분류가 주는 통찰은 "장기/단기 기억"이라는 전통적 이분법이 실제 시스템 설계를 설명하기에 부족하다는 것이다. 예컨대 위의 3단계 파이프라인은 토큰 레벨·사실 기억의 설계에 해당하고, 에이전트가 과거 실패에서 교훈을 뽑아 절차를 개선하는 것은 경험 기억의 영역이라 설계 패턴이 완전히 달라진다. 자사 서비스의 메모리 요구사항을 이 세 축 위에 먼저 배치해보면, 어떤 프레임워크가 맞는지 자연스럽게 좁혀진다.

한편 업계 현황 수치는 이 흐름의 규모를 보여준다. Gartner는 2025년 8월 보도자료에서 2026년 말까지 업무별 AI 에이전트를 통합한 기업 애플리케이션이 2025년의 5% 미만에서 40%로 증가할 것으로 전망했고, McKinsey 2025 글로벌 AI 서베이는 조직의 23%가 최소 하나의 업무 기능에서 에이전틱 AI를 스케일링 중이며 39%는 실험 단계에 있다고 집계했다. Mem0의 2026년 리포트는 이러한 채택 곡선 뒤에서 메모리가 벤치마크로 측정 가능한 독립 계층으로 부상했음을 지적하며, 크로스 세션 사용자 식별, 대규모 시간 추상화, 기억의 낡음(staleness) 처리가 여전히 열린 문제라고 정리한다. 이는 곧 지금 설계 단계에서 스스로 판단해야 할 영역이 남아 있다는 뜻이기도 하다.

## 5. 실무 체크리스트와 흔한 실수

위 분석을 실무 적용 가능한 체크리스트로 압축한다.

1. **세션 통째 임베딩 금지** — 저장 단위는 사실(fact) 단위로 분해한다. 검색 정밀도의 절반은 인덱싱에서 결정된다.
2. **시간을 스키마에 넣어라** — `captured_at`, `valid_until`, `supersedes` 없이는 지식 업데이트와 시간 추론을 구현할 수 없다.
3. **기권 경로를 설계하라** — 검색 결과가 비었을 때의 행동을 정의하지 않으면 환각이 디폴트가 된다.
4. **롱컨텍스트를 메모리 대안으로 쓰지 마라** — LongMemEval의 30% 정확도 하락 보고는 컨텍스트 전체 투입이 검색 기반 메모리를 대체할 수 없음을 시사한다.
5. **다섯 능력별로 따로 측정하라** — 통합 점수가 아니라 어떤 능력이 무너지는지 분해해야 개선 우선순위가 나온다.

## 결론

- 에이전트 메모리는 컨텍스트 윈도우 확장으로 해결되지 않는 독립된 설계 문제다. 롱컨텍스트 LLM조차 지속 상호작용에서 최대 30% 정확도가 하락한다(LongMemEval, ICLR 2025).
- LoCoMo는 300턴·최대 35세션의 초장기 대화로, LongMemEval은 500문항·5개 능력 분해로 기억을 측정한다. 장애 원인 분석은 능력별 분해에서 시작해야 한다.
- 검증된 설계 골격은 3단계다: 인덱싱(세션 분해 + 팩트 증강 키), 검색(시간 인지 쿼리 확장), 리딩(최신 우선 정렬 + 기권 지시).
- 프레임워크를 고르기 전에 형태·기능·동역학 세 축으로 자신의 요구사항을 먼저 배치하라.
- 당장 할 수 있는 첫 단계는 간단하다. 기존 대화 로그에서 세션을 사실 단위로 분해하는 프롬프트를 만들고, `captured_at`/`supersedes` 필드가 있는 스키마로 저장한 뒤, LongMemEval 공식 GitHub의 평가 스크립트로 자기 데이터에 맞게 변형해 측정해보는 것이다.
