# 2026년에도 LLM 파인튜닝을 해야 할까: LoRA와 QLoRA를 고르기 전에 점검할 6가지

오픈소스 대형 언어 모델(LLM)이 2026년에 이르러 눈에 띄게 좋아졌다. 상용 API 없이도 로컬에서 쓸 만한 품질이 나오는 시대다. 그런데 "우 회사 도메인에 맞게 모델을 튜닝해야 하나?"라는 질문은 여전히 매주 누군가의 회의실에 등장한다. 문제는 대부분의 팀이 **파인튜닝을 시작하기도 전에 가장 비싸고 가장 피하고 싶은 단계를 건너뛴다**는 점이다. 평가를 정의하지 않은 채 GPU를 빌리는 일이 다반사다.

이 글은 2026년 7월 기준으로 LoRA와 QLoRA가 어떻게 동작하는지, 언제 파인튜닝이 정말로 정당화되는지, 그리고 실제 GPU에서 어디까지 돌아가는지를 정리한다. 핵심 질문은 하나다. **"프롬프트 엔지니어링으로 안 되는 것을, 정말로 파인튜닝이 해결해 주는가?"**

## 섹션 1: 파인튜닝이 남은 단 한 가지 이유

파인튜닝을 둘러싼 논의에서 가장 흔한 오해는 "더 똑똑해진다"는 믿음이다. 감독 학습 파인튜닝(Supervised Fine-Tuning, SFT)이 하는 일은 모델의 능력을 키우는 게 아니라 **행동을 고정**하는 것이다. 일관된 JSON 스키마를 뱉게 하거나, 특정 업계 용어를 자연스럽게 쓰거나, 긴 시스템 프롬프트를 학습된 가중치 안으로 압축하는 데 효과적이다. 반면 새로운 사실 지식을 주입하는 데는 본질적으로 약하다 — 그런 역할은 검색 증강 생성(RAG)이 더 싸고 더 유지보수하기 쉽다.

그래서 파인튜닝을 결정하기 전에 반드시 이 순서로 점검해야 한다.

1. **퓨샷 프롬프트를 먼저 시도했는가?** 시스템 프롬프트에 3~5개의 입출력 예시를 넣는 것만으로 90% 가까운 효과가 나는 경우가 많다.
2. **지식 부족인가, 형식 부족인가?** 지식이 문제면 RAG. 형식·어조·용어가 문제면 파인튜닝 후보다.
3. **500개 이상의 깨끗한 학습 예시가 있는가?** 이 임계값 아래에서는 잘 만든 프롬프트가 LoRA를 이기는 경우가 대부분이다. 실용적인 스위트스팟은 1,000~5,000개다.
4. **이 모델을 10,000번 이상 호출하는가?** 파인튜닝은 500토큰짜리 시스템 프롬프트를 가중치로 압축해 추론 비용을 깎는다. 호출량이 적다면 섣부른 투자다.
5. **개선을 측정할 지표가 있는가?** 이 항목을 비워두면 "느낌상 더 좋아진 것 같다"는 감상에 갇힌다. 분류라면 정확도/F1, 생성이라면 LLM-as-Judge, 구조화 출력이라면 스키마 준수율처럼 작업 특화 지표를 정의하라.
6. **베이스 모델을 훼손하지 않았는지 확인할 수 있는가?** 좁은 데이터로 파인튜닝하면 모델이 원래 갖고 있던 일반 능력을 치명적으로 잊는다(catastrophic forgetting). 학습 전후로 일반 벤치마크를 돌려 회귀를 잡아내야 한다.

이 여섯 가지 중 하나라도 "아직"이라면, 파인튜닝은 다음 달로 미뤄도 된다. 답답하겠지만, 가장 경제적으로 옳은 결정이다.

## 섹션 2: LoRA와 QLoRA가 메모리를 어떻게 줄이는가

전체 파라미터 파인튜닝은 메모리 관점에서 거의 현실성이 없다. 옵티마이저 상태와 그래디언트까지 합치면 모델 크기의 약 12배에 해당하는 VRAM이 필요하다. 7B 모델 하나에 80GB가 넘는다. 여기서 파라미터 효율적 파인튜닝(PEFT) 기법이 등장한다.

**LoRA(Low-Rank Adaptation)** 의 핵심 아이디어는 단순하다. 사전학습된 가중치 행렬 $W$를 얼려두고(freeze), 그 옆에 가벼운 두 행렬 $A$와 $B$만 학습한다. 업데이트량 $\Delta W$를 $\Delta W = A \times B$로 저랭크 분해하는 것이다. 여기서 랭크 $r$이 어댑터의 표현력을 결정한다. 원 논문(GPT-3 175B 기준)에 따르면, 학습 가능한 파라미터를 최대 10,000배 줄이고 GPU 메모리를 3배 절약한다. 학습이 끝나면 어댑터를 베이스 가중치에 다시 합칠 수 있어(merge), 추론 시 추가 지연이 전혀 발생하지 않는다.

**QLoRA**는 여기에 4비트 양자화를 한 층 더 얹는다. 세 가지 기술이 겹쳐 동작한다.

- **4-bit NormalFloat(NF4):** 정규분포를 따르는 신경망 가중치에 정보이론적으로 최적인 데이터 타입.
- **이중 양자화(Double Quantization):** 양자화 상수 자체를 다시 양자화해 메모리를 추가 절약.
- **페이징 옵티마이저(Paged Optimizers):** NVIDIA 통합 메모리를 활용해 그래디언트 계산 중 메모리 스파이크가 발생해도 OOM(Out-Of-Memory)으로 죽지 않게 함.

결과적으로 48GB GPU 한 장으로 65B 파라미터 모델을 파인튜닝할 수 있게 된다 — 전체 16비트 파인튜닝과 거의 같은 품질을 유지하면서.

정리하면 선택 기준은 VRAM 예산으로 귀결된다.

| 상황 | 추천 기법 |
|------|-----------|
| VRAM 40GB 이상, 12B 이하 모델, 최고 품질 필요 | LoRA(16-bit) |
| VRAM 16~24GB, 12B~70B 모델, 소비자 하드웨어 | QLoRA(4-bit) |
| 대부분의 실무 상황(2026년) | QLoRA가 사실상 기본값 |

LoRA와 QLoRA 사이의 품질 격차는 대부분의 실용적 작업에서 무시할 수 있을 정도로 작다. 양자화로 손실되는 정보가 있지만, NF4는 현대 트랜스포머 가중치 분포를 잘 다루도록 설계되어 있다.

## 섹션 3: GPU 요구량 — 모델 크기 × 기법 × VRAM

가장 자주 묻는 질문은 "내 GPU에서 어디까지 돌아가나요?"다. 시퀀스 길이 2048, 배치 크기 1, 그래디언트 체크포인팅 켠 조건에서의 현실적 VRAM 요구량을 정리한다. Unsloth 최적화가 적용된 수치는 괄호로 표시했다.

| 모델 크기 | 전체 파인튜닝 | LoRA(16-bit) | QLoRA(4-bit) | QLoRA + Unsloth |
|----------|--------------|--------------|--------------|-----------------|
| 1B | ~12 GB | ~6 GB | ~4 GB | ~3 GB |
| 7~8B | ~80 GB | ~20 GB | ~10 GB | ~6 GB |
| 12B | ~144 GB | ~32 GB | ~16 GB | ~10 GB |
| 27B | ~324 GB | ~72 GB | ~28 GB | ~22 GB |
| 70B | ~840 GB | ~180 GB | ~48 GB | ~36 GB |

실용적 결론: RTX 4090(24GB) 한 장이면 QLoRA로 12B까지는 편하게, Unsloth 최적화를 얹으면 27B까지도 가능하다. 무료 Colab T4(16GB)는 QLoRA + Unsloth 조합으로 약 12B까지 커버하지만 배치 크기가 타이트해진다.

## 섹션 4: 실제 학습 코드의 뼈대

Unsloth + TRL의 `SFTTrainer`를 쓰면 코드는 놀라울 정도로 짧다. Gemma 4 12B를 QLoRA로 파인튜닝하는 핵심 흐름만 보이면 이렇다.

```python
from unsloth import FastLanguageModel
from trl import SFTTrainer, SFTConfig

# 1) 4비트 양자화로 모델 로드
model, tokenizer = FastLanguageModel.from_pretrained(
    model_name="google/gemma-4-12b-it",
    load_in_4bit=True,
)

# 2) LoRA 어댑터 설정 — 핵심은 target_modules="all-linear"
model = FastLanguageModel.get_peft_model(
    model,
    r=16,
    target_modules="all-linear",   # attention뿐 아니라 모든 선형층에 적용
    lora_alpha=32,                 # alpha = 2 * r
    lora_dropout=0.05,
    learning_rate=2e-4,            # 코사인 스케줄링 권장
)

# 3) 데이터셋은 모델의 채팅 템플릿에 맞춰 포맷
# 4) 학습
trainer = SFTTrainer(
    model=model,
    tokenizer=tokenizer,
    train_dataset=dataset,
    args=SFTConfig(
        output_dir="./outputs",
        num_train_epochs=2,
        per_device_train_batch_size=1,
        gradient_accumulation_steps=8,   # 유효 배치 크기 8
        max_seq_length=2048,
        gradient_checkpointing=True,      # VRAM 절약 필수
        warmup_ratio=0.05,
        lr_scheduler_type="cosine",
    ),
)
trainer.train()
```

여기서 가장 많이 간과되는 설정이 `target_modules="all-linear"`다. HuggingFace PEFT의 기본값은 어텐션의 Q, V 행렬만 타겟으로 삼는데, Sebastian Raschka의 실험에 따르면 **모든 선형층에 LoRA를 적용할 때 다운스트림 성능이 일관되게 더 좋다**. 같은 학습 예산으로 공짜로 얻을 수 있는 성능이다.

하이퍼파라미터 출발점도 정해져 있다. 랭크 $r=16$, $\alpha=32$($=2r$), 드롭아웃 0.05, 학습률 $2 \times 10^{-4}$에 코사인 스케줄링. 랭크를 올리면 표현력은 늘지만 메모리도 늘고, $r=16\sim64$ 구간이 실용 범위다.

## 섹션 5: 어댑터 병합 vs 분리 서빙 — 배포 분기점

학습이 끝나면 두 가지 배포 전략이 갈린다.

**병합해서 단일 모델로 내보내기:** `merge_and_unload()`로 어댑터 가중치를 베이스 가중치에 접어 넣는다. 추론 지연이 0이고, GGUF로 내보내면 Ollama나 llama.cpp에서 단일 파일로 실행된다. 하나의 파인튜닝 작업만 있다면 이게 정답이다. 운영이 가장 단순하다.

**어댑터를 분리한 채 다중 서빙:** 베이스 모델은 한 번만 올려두고 요청마다 다른 LoRA 어댑터를 교체한다. 고객별·태스크별로 여러 파인튜닝 변형이 있을 때 유리하다. 어댑터는 보통 10~100MB에 불과해, 수 기가바이트짜리 모델 N개를 따로 저장할 필요가 없다. vLLM은 단일 베이스 모델에서 여러 LoRA 어댑터를 오버헤드 없이 서빙한다.

## 결론: 핵심 요약과 첫 단계

파인튜닝을 시작하겠다고 결심하는 순간, 가장 먼저 해야 할 일은 GPU를 빌리는 게 아니라 **평가 지표를 정의하는 것**이다. 측정 없는 파인튜닝은 비싼 프롬프트 엔지니어링에 불과하다.

- **파인튜닝은 능력이 아니라 행동을 고정한다.** 지식은 RAG, 형식·어조는 파인튜닝의 영역이다.
- **대부분의 프로젝트는 프롬프트부터 시작해야 한다.** 퓨샷 예시와 RAG로 안 되는지 먼저 증명하라.
- **QLoRA가 2026년의 기본값이다.** VRAM 절약이 압도적이고 품질 손실은 미미하다.
- **`target_modules="all-linear"`를 잊지 마라.** 같은 비용으로 일관되게 더 좋은 결과가 나온다.
- **평가 없이 배포하지 마라.** 학습 전후로 일반 벤치마크(lm-evaluation-harness 등)를 돌려 회귀를 잡아내야 한다.

지금 당장 시도해 볼 첫 단계: 현재 쓰고 있는 시스템 프롬프트가 500토큰을 넘는다면, 그 프롬프트를 1,000개 정도의 입출력 예시로 바꿔 QLoRA로 학습해 보라. 동일한 호출량이라면 추론 비용이 눈에 띄게 내려가는 첫 경험이 될 것이다.
