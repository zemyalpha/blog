# LLM 라우팅이 API 비용의 절반을 결정한다: RouteLLM과 캐스케이드의 실전 설계

대부분의 AI 애플리케이션은 같은 실수로 비용 관리에 실패한다. 프론티어 모델 하나를 배포하고, 모든 요청을 거기로 보낸 뒤, API 청구서가 트래픽에 비례해 선형으로 폭발하는 것을 지켜본다. 그러고 나서 뒤늦게 캐싱을 추가하거나 컨텍스트 윈도우를 줄이는 식으로 땜질한다.

근본적인 해결책은 더 단순하다. **각 쿼리를 그 쿼리가 실제로 필요로 하는 수준의 모델로 보내는 것.** "주문 상태 조회" 같은 단순한 질문에 GPT-4급 모델을 쓸 이유가 없고, 반대로 다단계 추론이 필요한 복잡한 요청을 소형 모델에 맡기면 품질이 무너진다.

이 글에서는 LLM 라우팅과 모델 캐스케이드가 실제로 어떻게 동작하는지, RouteLLM이 증명한 비용 절감의 조건은 무엇인지, 그리고 프로덕션에서 라우터가 조용히 품질을 갉아먹는 지점은 어디인지를 분석한다.

## 라우팅과 캐스케이드: 이름이 비슷하지만 패턴이 다르다

두 용어가 자주 혼용되지만, 서로 다른 아키텍처 패턴을 가리킨다.

**라우팅(Routing)**은 단일 결정이다. 쿼리가 들어오면 라우터가 이를 분류해 정확히 하나의 모델로 보낸다. 분류 기준은 인텐트("이건 코딩 질문이니 코드 특화 모델로"), 복잡도("짧은 사실 확인이니 소형 모델로"), 또는 과거 쿼리와의 의미적 유사도가 될 수 있다. 결정이 한 번, 실행이 한 번이다.

**캐스케이드(Cascading)**는 순차적 에스컬레이션이다. 쿼리가 가장 저렴한 모델로 먼저 간다. 그 모델의 출력 신뢰도가 임계값 미달이면, 다음 단계의 더 강력한 모델로 올린다. 충분히 확신 있는 답이 나오거나 가장 강력한 모델에 도달할 때까지 반복한다. 항상 저렴한 곳에서 시작하고, 저렴한 모델이 처리 못 할 때만 비싼 컴퓨팅 비용을 지불한다.

```python
# 캐스케이드의 핵심 로직 (의사코드)
def cascade_answer(query, models, threshold=0.7):
    """
    models: [weak_model, mid_model, strong_model] — 저렴한 순
    threshold: 신뢰도 임계값. 이 미만이면 다음 단계로 에스컬레이션
    """
    for i, model in enumerate(models):
        response, confidence = model.generate(query)
        if confidence >= threshold or i == len(models) - 1:
            return response  # 충분히 확신하거나 마지막 모델이면 반환
        # 아니면 다음(더 강력한) 모델로 에스컬레이션
    return response
```

두 패턴의 차이는 구현과 튜닝 방식에 직접 영향을 미친다. 라우팅은 생성 전에 동작하는 정확한 분류기가 필요하므로 추론 전에 지연이 추가된다. 캐스케이드는 좋은 신뢰도 보정(calibration)이 필요하며, 여러 모델을 순차로 실행할 수 있는 지연을 감수한다. 프로덕션에서는 라우팅으로 명백히 어울리지 않는 단계를 먼저 걸러내고, 단계 내에서 캐스케이드를 도는 하이브리드가 자주 최선이다.

## RouteLLM이 증명한 것: 85% 비용 절감의 조건

라우팅이 이론적으로 좋다는 건 누구나 안다. 문제는 "실제로 얼마나 절감되느냐"다. 이 질문에 가장 엄밀하게 답한 연구가 RouteLLM이다.

RouteLLM은 LMSYS Org(UC Berkeley, Anyscale 소속 연구진)가 2024년 6월에 발표하고 2025년 ICLR에 게재된 논문이다. 핵심 설정은 단순하다: 강모델(GPT-4)과 약모델(Mixtral 8x7B) 사이에서 각 쿼리를 라우팅하는 시스템을 설계한다.

결과는 명확했다. MT Bench 벤치마크에서 GPT-4 성능의 95%를 달성하면서, GPT-4 호출을 전체 쿼리의 **14%**로 줄였다. 무작위 라우팅 기준선 대비 약 **85%**의 비용 절감에 해당한다. 다른 벤치마크에서는 MMLU 45%, GSM8K 35% 절감을 기록했다.

```python
# RouteLLM 프레임워크 사용 예시 (오픈소스, MIT 라이선스)
# pip install routellm
from routellm.controller import Controller

# 강모델과 약모델 사이를 라우팅하는 컨트롤러
controller = Controller(
    routers=["mf-mixtral-8x7b"],  # matrix factorization 라우터
    strong_model="gpt-4o",
    weak_model="mixtral-8x7b",
)

# routing_threshold가 낮을수록 강모델을 더 자주 호출 (비용 ↑, 품질 ↑)
response = controller.chat.completions.create(
    model="router-mf-mixtral-8x7b",
    messages=[{"role": "user", "content": "파이썬으로 퀵소트 구현해줘"}],
    routing_threshold=0.5,  # 0.0 = 항상 강모델, 1.0 = 항상 약모델
)
```

여기서 주의할 점이 있다. 85%는 **MT Bench라는 특정 벤치마크에서의 수치**이지, 모든 워크로드에 대한 보장이 아니다. RouteLLM 논문 자체가 이를 명시하고 있다. MMLU에서는 절감률이 45%로 떨어졌고, 라우터를 Arena 데이터로만 학습했을 때는 MMLU에서 거의 무작위 수준의 성능을 보였다. 즉, **라우팅 효율은 트래픽 분포와 라우터 학습 데이터에 크게 의존한다.**

왜 이런 절감이 가능한가? 쿼리의 복잡도 분포 때문이다. 대부분의 프로덕션 트래픽은 단순하다 — 요약, 분류, 짧은 정보 추출, 루틴한 질문 응답. 이런 요청은 소형 모델이 프론티어 모델과 체감할 수 없는 품질 차이를 보이지 않는다. 라우터의 역할은 이 "단순한 다수"를 걸러내어 저렴한 모델로 보내고, 진짜로 복잡한 소수만 비싼 모델로 올리는 것이다.

가격 격차도 극적이다. RouteLLM 논문은 백만 출력 토큰당 Haiku 1.25달러, Opus 75달러 — **약 60배** 차이를 예시로 든다. 2026년 8월 현재 Anthropic 공식 가격표를 확인해 보면 최상위 Claude Opus 5는 출력 토큰당 25달러, Claude Haiku 4.5는 5달러로 같은 제품군 내 스프레드는 5배로 줄었다. 하지만 시장 전체를 보면 — 가장 저렴한 오픈소스 모델(DeepSeek 등)부터 최고가 클로즈드 모델까지 — 여전히 수십 배의 가격 차이가 존재하며, 이 차이가 라우팅의 경제적 동기가 된다.

## 인텐트 라우팅: 가장 실용적인 시작점

신뢰도 기반 캐스케이드는 세련돼 보이지만, 대부분의 팀이 먼저 해야 할 것은 더 단순한 인텐트 라우팅이다. 들어오는 쿼리를 카테고리로 분류하고, 각 카테고리를 그에 가장 적합한 모델로 보낸다.

```python
# 간단한 인텐트 라우팅 (룰 + 소형 분류기 하이브리드)
import re

MODEL_MAP = {
    "simple_factual":  "cheap-model",    # 주문 조회, FAQ
    "code_generation": "code-model",     # 코드 작성, 디버깅
    "complex_reasoning": "frontier-model", # 다단계 추론, 분석
    "creative_writing":  "mid-model",     # 마케팅 카피, 요약
}

# 1단계: 빠른 룰 기반 분류 (< 1ms)
def classify_intent_fast(query):
    if re.search(r"(주문|배송|상태|조회|faq)", query, re.I):
        return "simple_factual"
    if re.search(r"(코드|버그|함수|api|컴파일)", query, re.I):
        return "code_generation"
    if re.search(r"(분석|전략|비교|설계|아키텍처)", query, re.I):
        return "complex_reasoning"
    return None  # 룰로 못 걸러내면 2단계로

# 2단계: 0.5B 파라미터 소형 모델로 분류 (~90% 정확도, ~50ms)

def route_query(query):
    intent = classify_intent_fast(query)
    if intent is None:

```

고객 지원 시스템이라면: 주문 상태나 배송 기간 같은 단순 사실 조회는 소형 모델로, 정책 해석은 중급 모델로, 판단이 필요한 복잡 민원은 프론티어 모델로 보낸다. 분류기 자체는 매우 작을 수 있다 — 잘 정의된 인텐트 카테고리에 대해 0.5B 파라미터 모델이 약 90%의 라우팅 정확도를 달성하면서 밀리초 단위의 지연만 추가한다.

핵심은 카테고리가 단순히 주제(topic)가 아니라 **필요한 모델 능력과 상관관계가 있는 것**이어야 한다는 점이다. "스포츠", "기술", "건강" 같은 주제 분류는 라우팅에 쓸모가 없다. "단일 팩트 조회", "다단계 추론", "창의적 생성" 같은 능력 기반 분류가 의미 있다.

## 라우터 오버헤드: 레이턴시 병목이 아니다

라우팅 도입을 망설이게 하는 흔한 오해가 있다. "라우터가 지연을 추가하지 않을까?" RouteLLM 논문과 여러 프로덕션 사례가 보여주는 바에 따르면, 답은 "무시할 수준"이다.

| 라우터 유형 | 추가 지연 | 비고 |
|---|---|---|
| 룰 기반 | < 1 ms | 정규식 / 키워드 매칭 |
| 임베딩 기반 | ~5 ms | 벡터 유사도 분류 |
| ML 분류기 | 50–100 ms | fine-tuned 소형 모델 |
| **LLM 추론** | **500–2,000 ms** | 실제 생성 시간 |

라우터 지연은 LLM 추론 시간의 10%에도 미치지 못한다. 라우터가 결코 레이턴시 병목이 되지 않는다. 병목은 항상 모델 생성 자체다.

## 침묵의 품질 저하: 라우터가 무너지는 지점

비용 절감 수치가 인상적이라 해서 무조건 도입하면 안 된다. 라우팅의 진짜 위험은 **조용한 품질 회귀(silent quality regression)**다.

저렴한 모델로 라우팅된 쿼리에서 품질이 떨어지면, 그게 대시보드에 즉시 나타나지 않는다. 고객 불만 티켓이 며칠 뒤에 쌓이기 시작해서야 발견된다. 온라인 메트릭(응답 시간, 에러율)은 정상인데, 정작 답변 품질은 떨어져 있는 상황이다.

이 문제를 방어하려면 **품질을 측정하는 수단**이 라우터와 함께 있어야 한다:

1. **오프라인 평가 셋** — 도메인별 대표 케이스 50~500개를 라벨링해서 보관. 라우팅 설정을 바꿀 때마다 이 셋으로 회귀 테스트.
2. **온라인 LLM-as-Judge** — 샘플링한 응답을 강모델로 평가. 단, LLM 평가자의 편향(position bias 등)은 별도로 보정해야 한다.
3. **비즈니스 메트릭 A/B** — 라우팅 도입 전후의 해결률, 재문의율, 만족도를 비교. 기술 메트릭이 아니라 비즈니스 임팩트로 검증.

캐스케이드에서는 추가 위험이 있다. **에스컬레이션율이 실시간 비용 변수**라는 점이다. 신뢰도 검증기(verifier)가 드리프트되면 모든 쿼리를 상위 모델로 올려버려 비용이 폭발하거나, 반대로 과도하게 하위 모델에 머물러 품질이 무너질 수 있다. 검증기 자체의 캘리브레이션을 정기적으로 점검해야 한다.

## 라우팅은 페일오버가 아니다

마지막으로 자주 발생하는 혼동 하나. 라우팅과 페일오버(failover)는 기계장치를 공유하지만 목적이 다르다.

- **라우팅**은 비용/품질 최적화가 목적이다. "가장 저렴하면서도 충분한 모델"을 고른다.
- **페일오버**는 가용성 확보가 목적이다. 한 모델이 장애 나면 다른 모델로 살아남는다.

"가장 저렴한 걸로 보내라"는 라우팅 정책과 "장애 나면 살아남아라"는 페일오버 정책을 같은 코드로 처리하면 사고가 난다. 페일오버 체인의 후보 모델은 품질이 보장되어야 하지만, 라우팅의 후보는 비용 최적화가 기준이기 때문이다. AI Gateway를 도입한다면 이 두 정책을 분리된 레이어로 설계해야 한다.

## 핵심 요약

- **대부분의 프로덕션 트래픽은 단순하다.** 단일 프론티어 모델이 모든 요청을 처리하는 것은 비용 낭비의 가장 큰 원인이다.
- **RouteLLM은 MT Bench에서 85% 비용 절감을 입증했다.** 단, 이는 특정 벤치마크 수치이며 실제 절감률은 트래픽 분포와 라우터 학습 데이터에 의존한다.
- **인텐트 라우팅부터 시작하라.** 신뢰도 기반 캐스케이드보다 구현이 단순하고 즉각적인 효과가 있다. 능력 기반 카테고리(주제가 아닌)로 분류할 것.
- **라우터 오버헤드는 무시할 수준이다.** 룰 기반 1ms, ML 분류기 100ms — LLM 추론 500~2000ms에 비하면 병목이 아니다.
- **침묵의 품질 회귀가 진짜 위험이다.** 라우팅 도입과 함께 오프라인 평가 셋, LLM-as-Judge, 비즈니스 메트릭 A/B를 설계 없이 배포하면 품질 저하를 뒤늦게 발견한다.

당장 시도해볼 첫 단계는 단순하다. 현재 프로덕션 트래픽의 로그를 열어, 상위 80%를 차지하는 쿼리 유형을 분류해 보라. 그 중 얼마나 많은 것이 정말로 프론티어 모델을 필요로 하는지 세어보면, 라우팅의 잠재적 절감액이 보인다.
