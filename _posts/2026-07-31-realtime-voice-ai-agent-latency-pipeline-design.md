# 실시간 Voice AI Agent 지연 최적화: 1400ms를 600ms로 줄이는 스트리밍 파이프라인 설계

전화를 걸었을 때 상대가 1.2초 동안 침묵하면 우리는 "여보세요?"라고 다시 묻는다. 사람의 대화에서 턴과 턴 사이의 간격(turn gap)은 일반적으로 200~250밀리초 수준으로 짧다. 이 간격이 500밀리초를 넘기면 대화가 끊겼다고 느끼거나, 어색한 정적으로 인식하기 시작한다. 2026년 실시간 음성 AI 에이전트(Voice AI Agent)가 텍스트 챗봇과 근본적으로 다른 이유가 바로 여기에 있다. 텍스트는 입력 완료를 기다려도 되지만, 음성은 사용자가 말을 끝내는 순간 즉각 반응해야 한다.

문제는 음성 에이전트가 통과해야 하는 파이프라인이 길다는 것이다. 마이크 입력 → 패킷화 → VAD(음성 활동 감지) → 스트리밍 ASR → LLM 추론 → 도구 호출 → 스트리밍 TTS → 재생 버퍼. 각 단계를 직렬로 실행하면 첫 오디오 프레임이 나오기까지 1,400ms 가까이 걸린다. 이 글에서는 이 직렬 파이프라인을 어떻게 중첩시켜 600ms 수준으로 압축하는지, 프로덕션 환경에서 실제로 적용하는 기법들을 정리한다.

## 텍스트 챗봇과 음성 에이전트의 근본적 차이

먼저 오해를 하나 짚고 넘어가야 한다. 음성 에이전트는 "마이크가 달린 챗봇"이 아니다. 아래 표는 두 시스템의 설계 제약을 비교한 것이다.

| 설계 축 | 텍스트 챗봇 | 실시간 음성 에이전트 |
|---------|------------|---------------------|
| 입력 완료 시점 | 명확 (전송 버튼) | 불명확 (말 끝 감지 필요) |
| 핵심 지표 | 전체 응답 시간 | 첫 오디오까지의 시간 (TTFA) |
| 중단 처리 | 불필요 | 필수 (barge-in) |
| 출력 방식 | 한 번에 렌더링 | 청크 단위 스트리밍 |
| 실패 모드 | 답이 늦음 | 침묵, 끊김, 기계적 목소리 |

텍스트 챗봇은 사용자가 "전송"을 누른 시점에 입력이 완료된다. 하지만 음성에서는 사용자가 말을 끝냈는지, 잠시 쉬는 것인지, 생각하는 것인지를 시스템이 판단해야 한다. 이것이 **턴 감지(turn detection)** 문제이며, 너무 민감하면 말을 자르고(premature cutoff), 너무 보수적이면 어색한 정적(silence)이 생긴다.

가장 중요한 차이는 핵심 메트릭이다. 텍스트는 "전체 답변이 얼마나 빨리 나오는가"가 중요하지만, 음성에서는 **"첫 오디오 프레임이 얼마나 빨리 나오는가(Time-To-First-Audio, TTFA)"** 가 체감 품질을 결정한다. 사용자는 AI가 말을 시작하면 기다려준다. 시작 자체가 늦으면 이미 대화가 끊긴 것으로 인식한다.

## 레이턴시 예산: 파이프라인의 각 단계가 얼마나 걸리는가

최적화를 논하려면 먼저 어디서 시간이 소모되는지 측정해야 한다. 아래는 프로덕션 환경에서 관찰되는 전형적인 레이턴시 예산의 참고치다. 실제 값은 디바이스, 코덱, 리전, 네트워크, 모델, 동시 접속 수에 따라 달라지므로, 이것은 출발점이지 보편적 목표치가 아니다.

| 구성 요소 | 참고 범위 | 비고 |
|----------|----------|------|
| 오디오 패킷화 | 20–40ms | WebRTC 또는 WebSocket 프레임 |
| VAD 결정 | 100–250ms | 무음 임계값에 따라 변동 |
| ASR 부분 전사 안정화 | 100–300ms | 부분 전사를 일찍 활용 가능 |
| LLM 첫 토큰 | 200–700ms | 모델·컨텍스트 의존 |
| TTS 첫 청크 | 100–300ms | 스트리밍 TTS 필요 |
| 재생 버퍼 | 40–120ms | 언더런 방지 |

이 모든 단계를 직렬로 합치면 최악의 경우 1,400ms에 근접한다. 하지만 핵심 트릭은 **각 단계의 작업을 중첩(overlap)시키는 것**이다. 최종 ASR 전사가 완료될 때까지 기다리지 말고, 부분 전사로 LLM 준비를 시작하고, LLM 첫 토큰이 나오면 즉시 TTS로 보내는 식이다.

## 핵심 기법 1: 스트리밍 ASR와 부분 전사 라우팅

가장 큰 절감을 가져오는 첫 번째 기법은 스트리밍 ASR(자동 음성 인식)을 사용하고, **부분 전사(partial transcript)를 기다림 없이 LLM에 전달**하는 것이다.

전통적인 접근은 사용자 발화가 끝난 후 전체 문장을 전사한 뒤 LLM에 넘긴다. 하지만 스트리밍 ASR는 말하는 도중에도 부분 전사를 계속 내보낸다. 이 부분 전사가 일정 이상 안정화되면(예: 마지막 2개 부분 전사가 동일하면) 최종 전사를 기다리지 않고 LLM 호출을 시작할 수 있다. 이것만으로 200–400ms를 절약할 수 있다.

```python
# 의사 코드: 부분 전사 기반 조기 라우팅
class StreamingASRHandler:
    def __init__(self):
        self.last_partial = ""
        self.stable_count = 0

    def on_partial(self, partial_text):
        if partial_text == self.last_partial:
            self.stable_count += 1
            # 부분 전사가 2회 연속 동일하면 의미가 안정화된 것으로 판단
            if self.stable_count >= 2 and self._is_complete_intent(partial_text):
                self.llm_orchestrator.prefetch(partial_text)
        else:
            self.stable_count = 0
        self.last_partial = partial_text
```

여기서 `_is_complete_intent`는 단순한 휴리스틱일 수도 있다. 예를 들어 "예약해 줘", "주문할게" 같은 종결 어미가 감지되면, 최종 전사가 나오기 전에 미리 LLM 요청을 준비하는 식이다. 단, 잘못된 조기 트리거를 방지하려면 신뢰도 임계값을 함께 사용해야 한다.

## 핵심 기법 2: LLM 토큰을 TTS에 즉시 파이프하기

LLM이 응답을 완성할 때까지 기다렸다가 TTS에 넘기면 LLM 생성 시간 전체가 지연에 더해진다. 대신 **LLM이 첫 문장 경계(마침표, 물음표, 쉼표)를 생성하는 순간 그 텍스트를 TTS로 보낸다.** 이렇게 하면 LLM이 다음 문장을 생성하는 동안 TTS가 이미 이전 문장을 합성하고 재생한다.

이 기법은 200–500ms의 절감을 가져온다. 단, 한 가지 주의점이 있다. LLM이 문장 중간에 방향을 바꾸거나(backtrack), 앞서 생성한 텍스트를 취소하는 경우, 이미 TTS로 보낸 텍스는 취소할 수 없다. 따라서 문장 경계에서만 TTS로 커밋하는 것이 안전하다.

```python
# 의사 코드: 문장 경계 기반 TTS 커밋
class TokenToSpeechPiper:
    def __init__(self, tts_stream):
        self.buffer = ""
        self.tts = tts_stream

    def on_llm_token(self, token):
        self.buffer += token
        # 문장 종결 부호가 나오면 버퍼를 TTS로 커밋
        if any(punct in token for punct in [".", "?", "!", "다.", "요."]):
            self.tts.send(self.buffer.strip())
            self.buffer = ""
```

OpenAI의 Realtime API, LiveKit, Vapi 같은 플랫폼은 이런 중첩 처리를 네이티브로 지원한다. 직접 구축할 때는 LLM 제공자가 스트리밍 토큰을 지원하는지(SSE 또는 WebSocket) 확인이 필수다.

## 핵심 기법 3: 프롬프트 프리픽스 캐싱과 KV 캐시 재사용

음성 에이전트의 프롬프트는 시스템 지시사항, 페르소나 설명, 도구 정의, 대화 히스토리 등으로 구성된다. 이 중 시스템 프롬프트와 도구 정의는 매 턴마다 동일하게 반복된다. 이 부분을 매번 다시 계산하면 LLM 첫 토큰(TTFT)에 200–400ms가 추가된다.

**프롬프트 프리픽스 캐싱**은 변경되지 않는 프롬프트 앞부분의 KV 캐시를 보관하여, 후속 요청에서 재사용하는 기법이다. 대부분의 주요 LLM 제공자(OpenAI, Anthropic, Google)가 2025–2026년에 이 기능을 추가했다. API 레벨에서는 프롬프트 구조를 안정적으로 유지하는 것만으로 자동 적용되는 경우가 많다.

대화 히스토리도 부분적으로 재사용할 수 있다. 이전 턴의 KV 캐시를 보관했다가, 새 턴에서 히스토리 끝에 사용자 발화 하나만 추가하면 이전 캐시를 그대로 활용할 수 있다. 이를 **KV 캐시 재사용**이라고 하며, OpenAI, Anthropic의 API에서 prompt caching 기능으로 노출된다. 단, 히스토리가 너무 길어지면 캐시 효율이 떨어지므로, 정기적인 요약(summarization)으로 히스토리 길이를 관리해야 한다.

## 핵심 기법 4: 높은 신뢰도 인텐트에서 도구 호출 선페치

사용자가 "내일 날씨 어때?"라고 말하는 경우, ASR 부분 전사만으로도 "날씨" 인텐트를 높은 신뢰도로 분류할 수 있다. 최종 전사와 LLM 추론을 기다리지 말고, **미리 날씨 API를 호출(pre-fetch)** 해두는 것이다. LLM이 정식으로 도구를 요청할 때 이미 결과가 준비되어 있으면 200–400ms를 절약할 수 있다.

```python
# 의사 코드: 인텐트 기반 도구 선페치
INTENT_TOOL_MAP = {
    "weather": "get_weather",
    "reservation": "check_availability",
    "order": "get_menu",
}

def maybe_prefetch_tool(partial_text):
    intent = classify_intent_fast(partial_text)  # 경량 분류기
    if intent and intent.confidence > 0.85:
        tool_name = INTENT_TOOL_MAP.get(intent.label)
        if tool_name:
            tool_cache.prefetch(tool_name, intent.params)
```

물론 잘못된 선페치는 API 호출 비용과 캐시 오염을 초래한다. 따라서 신뢰도 임계값을 보수적으로 설정하고(0.85 이상), 선페치 결과를 짧은 TTL의 캐시에만 보관하는 것이 안전하다. LLM이 실제로 도구를 요청하면 캐시에서 즉시 반환하고, 요청하지 않으면 캐시를 폐기한다.

## 핵심 기법 5: 바지인(Barge-in)과 취소 처리

자연스러운 대화에서 사용자는 AI가 말하는 도중에 끼어든다. "아 아니, 그게 아니라—" 하면서 정정하거나, 새 질문을 던진다. 이것을 **바지인(barge-in)**이라고 하며, 실시간 음성 에이전트에서 필수적으로 지원해야 한다.

바지인이 감지되면(사용자가 말하기 시작하면) 시스템은 세 가지를 동시에 해야 한다:

1. **TTS 출력 중단** — 현재 재생 중인 오디오를 즉시 멈춘다.
2. **진행 중인 LLM 호출 취소** — 불필요한 토큰 생성을 중단하여 비용과 지연을 줄인다.
3. **새 입력 처리 시작** — 새로운 ASR 스트림을 시작하고 새 턴을 시작한다.

```python
# 의사 코드: 바지인 처리
class BargeInHandler:
    def on_user_speech_detected(self):
        # 1. TTS 중단
        self.tts_player.interrupt()
        # 2. 진행 중인 LLM 호출 취소
        if self.current_llm_task:
            self.current_llm_task.cancel()
        # 3. 새 턴 시작
        self.asr_handler.start_new_turn()
```

바지인 처리가 없으면, 사용자가 정정하려 해도 AI가 이전 답변을 끝까지 말한 뒤에야 새 입력을 처리한다. 이는 대화를 단절시키는 치명적 실패 모드다. 반면 바지인이 너무 민감하면, AI가 말하는 동안 발생하는 배경 소음이나 사용자의 감탄사("음", "어")에 반응하여 계속 끊긴다. 따라서 VAD 임계값과 바지인 트리거를 별도로 튜닝해야 한다.

## 기법 중첩의 누적 효과

지금까지의 기법을 조합하면 어느 정도 절감이 가능할까? 아래는 각 기법이 개별적으로 기여하는 참고치다. 실제 효과는 파이프라인 구성에 따라 달라지며, 일부 기법은 서로 중복되는 절감을 가져올 수 있다.

| 기법 | 참고 절감치 | 적용 조건 |
|------|-----------|----------|
| 스트리밍 ASR + 부분 전사 라우팅 | 200–400ms | 스트리밍 ASR 지원 필요 |
| LLM 토큰 → TTS 즉시 파이프 | 200–500ms | 스트리밍 토큰·스트리밍 TTS 필요 |
| 프롬프트 프리픽스 캐싱 | 200–400ms (TTFT) | 제공자 캐싱 지원 필요 |
| 도구 호출 선페치 | 200–400ms | 높은 신뢰도 인텐트 분류 필요 |
| 첫 TTS 오디오 프레임 사전 버퍼링 | 80–200ms (체감) | 재생 버퍼 최적화 |
| 비동기 평가 | 100–300ms | 인라인 검증을 백그라운드로 이동 |

이 기법들이 누적되면 직렬 파이프라인의 1,400ms를 600ms 수준까지 압축할 수 있다. 물론 모든 기법을 동시에 적용하는 것은 아니다. 도구를 호출하지 않는 간단한 턴에서는 선페치가 무의미하고, 매우 짧은 응답에서는 토큰-투-스피치 파이핑의 효과가 제한적이다. 턴의 복잡도(단순 응답 vs 도구 호출 다수)에 따라 별도의 P50/P95 SLO를 설정하는 것이 현실적이다.

## 관측성: 오디오 스팬 추적

최적화를 지속하려면 측정이 선행되어야 한다. 음성 에이전트의 관측성(observability)은 텍스트와 다르다. 단순히 "응답 시간"을 재는 것이 아니라, **오디오 스팬(audio span)** 단위로 각 단계를 추적해야 한다.

프로덕션에서 추적해야 할 핵심 스팬은 다음과 같다:

- **ASR 부분 전사 타임스탬프** — 각 partial이 도착한 시점
- **VAD 이벤트** — 발화 시작·종료 감지 시점
- **LLM 토큰 타임스탬프** — 첫 토큰, 각 토큰 도착 시점
- **TTS 청크 타임스탬프** — 첫 청크 생성, 각 청크 전송 시점
- **재생 상태** — 버퍼 언더런, 바지인 발생 시점

이 스팬들을 통합한 트레이스(trace)를 보면, 어느 단계에서 병목이 발생하는지 즉시 파악할 수 있다. 예를 들어 "LLM 첫 토큰이 700ms로 느리다"면 프리픽스 캐싱을 점검하고, "TTS 첫 청크가 300ms로 느리다"면 TTS 제공자나 리전 라우팅을 점검하는 식이다.

## TTS 선택이 지연과 품질을 동시에 결정한다

지연 최적화 관점에서 TTS의 핵심 지표는 **Time-To-First-Audio(TTFA)** 이다. 전체 합성 시간보다 첫 오디오 프레임이 얼마나 빨리 나오는지가 체감 속도를 결정한다. 2026년 기준 주요 TTS 제공자의 참고치를 정리하면 다음과 같다 (벤더 보고 및 서드파티 테스트 혼합 기준, 시점에 따라 변동).

| TTS 모델 | 특징 | 참고 수치 |
|----------|------|----------|
| Cartesia Sonic 3.5 | State Space Model 구조, 빠른 TTFA | ~40ms TTFA (벤더 보고) |
| Inworld Realtime TTS-2 | 실시간 품질 중심 | 서브-250ms 지연 목표 |
| ElevenLabs v3 (Eleven v3) | 다국어 지원(70+ 언어), 다양한 목소리 라이브러리 | 품질은 높으나 실시간 최상위권은 아님 |
| OpenAI Realtime TTS | Realtime API 통합 | 가성비 양호 |
| Kokoro 82M | 오픈 웨이트, 경량 | 로컬·엣지 배포 적합 |

TTFA가 짧은 TTS는 파이프라인 중첩 효과를 극대화한다. LLM 첫 토큰이 나오자마자 TTS 첫 청크가 40ms 만에 생성되면, 사용자가 청감하는 지연이 크게 줄어든다. 반면 TTFA가 300ms인 TTS는 아무리 앞 단계를 최적화해도 체감 한계가 있다.

주의할 점은, 벤더 보고 수치는 이상 조건에서의 측정치라는 것이다. 실제 프로덕션에서는 동시 접속, 네트워크 RTT, 리전 거리에 의해 추가 지연이 발생한다. 따라서 후보 TTS를 선정한 후 실제 트래픽 패턴에서 TTFA의 P95를 직접 측정하는 것이 필수다.

## 주의사항과 안티 패턴

지연 최적화 과정에서 반복적으로 나타나는 실수들이 있다.

**잘못된 조기 트리거.** 부분 전사 기반 라우팅에서 신뢰도 임계값을 너무 낮게 설정하면, 아직 말하는 중인 사용자의 발화에 반응해버린다. "내일 날씨—"에서 "날씨"가 감지되어 날씨 API를 호출했는데, 사용자가 "내일 날씨 아니라 모레 날씨"라고 정정하면 선페치가 무효가 된다. 임계값은 보수적으로, 그리고 정정 시나리오에 대한 테스트를 반드시 포함해야 한다.

**인라인 평가.** 음성 에이전트에서 안전 검사, 의도 검증, 콘텐츠 필터링을 동기적으로(in-line) 실행하면 100–300ms가 추가된다. 이런 평가는 비동기로 백그라운드에서 실행하되, 평가 결과가 부정적일 때 재생 중인 응답을 중단하는 방식으로 처리할 수 있다.

**버퍼 언더런 무시.** TTS 청크가 재생 속도를 따라가지 못하면 오디오가 끊긴다(언더런). 버퍼를 너무 작게 잡으면 언더런이 빈번하고, 너무 크게 잡으면 첫 재생이 지연된다. 40–120ms 범위에서 시작하여 실제 네트워크 지터(jitter)를 측정한 뒤 조정하는 것이 좋다.

**단일 리전 집중.** ASR, LLM, TTS가 모두 같은 리전에 있더라도, 사용자와의 거리가 멀면 네트워크 RTT가 지연의 주요 원인이 된다. 사용자 기반의 지리적 분포에 따라 엣지 노드를 배치하고, 리전 라우팅을 통해 60–150ms의 네트워크 지연을 절감할 수 있다.

## 핵심 요약 및 다음 단계

- **첫 오디오까지의 시간(TTFA)이 핵심 메트릭이다.** 전체 응답 시간이 아니라 사용자가 AI의 목소리를 처음 듣는 시점을 최적화해야 한다.
- **파이프라인을 직렬이 아닌 중첩으로 설계하라.** 스트리밍 ASR의 부분 전사를 일찍 LLM에 보내고, LLM 토큰을 문장 경계에서 TTS로 보내는 식으로 각 단계의 작업을 겹친다.
- **캐싱을 적극 활용하라.** 프롬프트 프리픽스 캐싱, KV 캐시 재사용, 의미적 캐시(semantic cache)로 반복 요청을 줄인다.
- **바지인을 필수로 구현하라.** 사용자가 말하기 시작하면 TTS 중단, LLM 취소, 새 턴 시작을 동시에 처리해야 한다.
- **측정 없는 최적화는 없다.** 오디오 스팬 단위의 트레이싱으로 어느 단계가 병목인지 파악하고, P50/P95 SLO를 턴 복잡도별로 별도 설정하라.

지금 바로 시도해볼 첫 단계는 현재 음성 파이프라인의 각 단계별 지연을 측정하는 것이다. ASR 부분 전사 도착, LLM 첫 토큰, TTS 첫 청크, 재생 시작 시점에 타임스탬프를 찍어 로깅하면, 어디서 1,400ms가 소모되는지 즉시 보일 것이다. 그 다음 가장 큰 병목부터 하나씩 중첩 최적화를 적용해 나가면 된다.
