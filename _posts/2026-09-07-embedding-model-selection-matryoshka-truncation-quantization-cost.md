# 임베딩 모델 선택은 리더보드가 아니라 차원 수로 한다: Matryoshka 잘라내기와 양자화의 실전 비용 계산

RAG 파이프라인을 운영하다 보면 몇 주마다 한 번씩 새 임베딩 모델이 MTEB 리더보드 정상에 오르고, 그때마다 검색 스택을 갈아엎고 싶은 유혹이 밀려온다. 그러나 2026년 현재 MTEB에는 400개 이상의 모델이 등재되어 있고, 상위권 모델들의 점수 차이는 1점 이내로 뭉쳐 있다. 순위표를 만드는 쪽(MTEB 운영진)조차 공개 테스트셋 과적합을 우려해 비공의 평가셋을 포함한 새 벤치마크(RTEB) 논의를 진행 중이다. 순위표 자체가 잘못됐다는 뜻이 아니라, **순위는 후보 좁히기용 필터이지 구매 결정의 근거가 아니라는 뜻이다.**

이 글은 리더보드 대신 실제로 검색·저장 비용을 결정하는 두 번째 축, **차원 수(dimension)** 를 중심으로 임베딩 모델을 선택하는 방법을 다룬다. 핵심은 Matryoshka Representation Learning(MRL)과 양자화(quantization)라는 두 개의 레버인데, 이 둘을 조합하면 품질을 거의 희생하지 않고 저장·검색 비용을 최대 32배까지 줄일 수 있다.

## MRL: 4096차원을 1024차원으로 잘라도 되는 이유

Matryoshka Representation Learning은 러시아 인형 마트료시카에서 이름을 따온 학습 기법으로, Kusupati 외(2022)가 NeurIPS 2022에서 발표했다([arXiv:2205.13147](https://arxiv.org/abs/2205.13147)). 핵심 아이디어는 단순하다. 임베딩 벡터를 학습할 때 **앞쪽 차원에 중요한 정보를 먼저 심고, 뒤쪽 차원에 세부 정보를 담도록** 손실 함수를 설계하는 것이다. 그 결과 원본 벡터의 앞 n개 차원만 잘라내도(트렁케이션) 검색 품질이 크게 떨어지지 않는다.

왜 이것이 실전에서 중요한가. 임베딩의 저장 비용은 차원 수에 정비례한다. 4096차원 벡터 하나는 float32 기준 16KB나 된다. 1억 개 문서를 인덱싱하면 인덱스 구조 오버헤드를 빼고도 순수 벡터만 1.64TB다. 반면 1024차원으로 자르면 같은 문서 수에서 410GB로 줄어든다. HNSW 같은 근사 최근접 이웃 인덱스는 메모리에 상주하는 벡터 크기가 곧 검색 지연과 RAM 비용이므로, 차원 축소는 품질 문제 이전에 인프라 비용 문제다.

주요 모델의 MRL 지원 현황을 정리하면 다음과 같다.

| 모델 | 기본 차원 | MRL 트렁케이션 | 라이선스/형태 |
|---|---|---|---|
| OpenAI text-embedding-3-large | 3072 | 256 등 API `dimensions` 파라미터 | 폐쇄 API |
| Gemini gemini-embedding-001 | 3072 | 1536, 768 등 | 폐쇄 API |
| Qwen3-Embedding (0.6B/4B/8B) | 1024 / 2560 / 4096 | 전 사이즈 MRL 지원 | Apache 2.0, 셀프호스팅 |
| Cohere embed-v4 | 1536 | 256~1536 네스티드 | 폐쇄 API |

Qwen3-Embedding의 경우 공식 GitHub 리포지토리([QwenLM/Qwen3-Embedding](https://github.com/QwenLM/Qwen3-Embedding))의 모델 표에서 세 사이즈 모두 "MRL Support: Yes"로 명시되어 있다. 또한 8B 모델은 2025년 6월 출시 당시 MTEB 다국어 리더보드 1위(70.58점, 100개 이상 언어)를 기록했으며 Apache 2.0으로 공개되어 있다. 한국어처럼 영어 밖의 언어를 다뤄야 한다면 셀프호스팅 가능한 오픈 소스 최상위권 후보로 삼을 만하다.

한 가지 주의할 점. OpenAI API의 `dimensions` 파라미터(공식 문서에서 "Matryoshka representation learning" 기반이라고 설명됨)는 요청 시점에 차원을 지정하는 방식이고, Gemini나 Voyage처럼 결과를 받아서 클라이언트에서 직접 잘라도 되는 모델도 있다. 자르는 시점이 API 안인지 밖인지는 마이그레이션 전략에 영향을 준다. 원본 차원으로 저장하고 나중에 자르는 편이 유연하지만, 그만큼 스토리지를 먼저 감당해야 한다.

## 실전 코드: 트렁케이션 + 양자화

오픈 소스 모델을 sentence-transformers로 쓴다면 트렁케이션은 말 그대로 슬라이싱이다.

```python
from sentence_transformers import SentenceTransformer
import numpy as np

model = SentenceTransformer("Qwen/Qwen3-Embedding-0.6B")  # 기본 1024차원

# 전체 차원으로 임베딩 생성
emb_full = model.encode(["매트료시카 임베딩 테스트"], normalize_embeddings=True)

# MRL 트렁케이션: 앞 256차원만 사용 후 재정규화
emb_256 = emb_full[:, :256]
emb_256 = emb_256 / np.linalg.norm(emb_256, axis=1, keepdims=True)
```

트렁케이션은 잘라낸 뒤 **반드시 재정규화**해야 코사인 유사도가 제대로 동작한다. 이 부분을 빠뜨리면 검색 품질이 이유 없이 나빠지는데, 원인을 찾느라 시간을 낭비하기 쉽다.

양자화는 그 위에 한 겹 더 얹는다. int8 양자화는 차원당 4바이트(float32)를 1바이트로 줄여 약 4배, 바이너리 양자화는 차원당 1비트로 줄여 32배 절약한다. Hugging Face의 공식 실험([embedding-quantization 블로그](https://huggingface.co/blog/embedding-quantization))에 따르면 int8 스칼라 양자화는 메모리·디스크를 크게 줄이면서 리콜 손실이 거의 없고, 바이너리 양자화는 단독으로 쓰면 리콜이 떨어지지만 **리스코어(재순위화) 단계를 붙이면 대부분 회복**된다.

```python
# 저장용 int8 양자화 — 캘리브레이션 벡터로 차원별 min/max 범위를 계산해야 품질이 안정적
from sentence_transformers.quantization import quantize_embeddings

int8_emb = quantize_embeddings(
    emb_full, precision="int8", calibration_embeddings=corpus_sample_emb
)

# 1차 스크리닝용 바이너리 (32배 절약, 해밍 거리로 후보 군 확보)
binary_emb = quantize_embeddings(emb_full, precision="ubinary")
```

리스코어는 별도 함수로 수행한다. `sentence_transformers.util.semantic_search`에 float32 질의 벡터와 int8/float 문서 벡터를 함께 넘기면, 바이너리 스크리닝으로 뽑은 후보를 상위 정밀도로 재정렬하는 2단계 검색이 완성된다(HF 공식 블로그의 실험 코드가 정확히 이 구성이다).

이 패턴의 실무적 의미는 "2단계 검색"이다. 바이너리 벡터로 전체 컬렉션에서 상위 N(예: 20~40배 오버샘플링)을 빠르게 뽑고, 그 후보만 float32(또는 int8) 벡터로 정밀 재순위화한다. RAM에 전체 float 벡터를 상주시키지 않아도 되므로 대규모 컬렉션에서 메모리 예산이 확 풀린다. Qdrant 등 일부 벡터 DB는 이 양자화·리스코어 파이프라인을 인덱스 레벨에서 네이티브로 지원한다.

저장 비용이 어떻게 바뀌는지 2억 5천만 벡터 기준으로 계산해 보면(순수 벡터 바이트, 인덱스 오버헤드 제외):

| 차원 | float32 | int8 | binary |
|---|---|---|---|
| 1024 | 1.02TB | 0.26TB | 0.03TB (32GB) |
| 1536 | 1.54TB | 0.38TB | 0.05TB |
| 4096 | 4.10TB | 1.02TB | 0.13TB (128GB) |

4096차원 풀스펙을 바이너리로 돌리면 4.1TB가 128GB가 된다. 이 표의 절대치는 벡터 수에 따라 달라지지만, 비율(4배/32배)은 어디에나 동일하게 적용된다.

## 그래서 뭘 골라야 하나: 가격표와 결정 트리

임베딩 API 가격(텍스트 100만 토큰당, 각사 공식 문서 기준 2026년 9월):

- **OpenAI text-embedding-3-large**: $0.13 (3-small은 $0.02, 배치 시 절반)
- **Voyage**: voyage-4-large $0.12 / voyage-4 $0.06 / voyage-4-lite $0.02 (계정당 2억 토큰 무료)
- **Cohere embed-v4**: $0.12 (이미지 $0.47, 128K 컨텍스트)
- **Qwen3-Embedding**: 무료(셀프호스팅, GPU 비용만)

이 표에서 바로 알 수 있는 것: 임베딩 API 비용 자체는 토큰당 몇 센트 수준이라 대부분의 서비스에서는 저장·검색 비용보다 영향이 작다. 1억 토큰을 임베딩해도 text-embedding-3-large 기준 $13이다. 진짜 비용은 그 벡터를 몇 년간 저장하고 검색하는 데서 나온다.

결정 트리로 정리하면:

1. **영어 중심, 소규모(<수백만 벡터)**: 트렁케이션·양자화 걱정 없이 MTEB 상위 후보 중 가장 싼 것(text-embedding-3-small, voyage-4-lite 등 $0.02급)을 쓰면 된다. 이 규모에서는 차원 수가 병목이 아니다.
2. **다국어(한국어 포함), 셀프호스팅 가능**: Qwen3-Embedding(0.6B로 시작해 품질 부족 시 4B/8B로) + MRL 트렁케이션. 0.6B는 1024차원이라 CPU 추론도 현실적이다.
3. **대규모(수천만~수억 벡터)**: MRL 트렁케이션(예: 4096→1024)은 필수고, 여기에 바이너리 스크리닝 + int8/float 리스코어 2단계 검색을 얹는다. 임베딩 모델을 바꾸는 것보다 이 레버가 비용에 미치는 영향이 훨씬 크다.
4. **긴 문서(청킹 줄이고 싶을 때)**: Cohere embed-v4의 128K 컨텍스트가 유일하게 차별화된 지점이다.

어떤 경우든 마지막 단계는 같다. 후보 3~4개로 **내 쿼리와 내 코퍼스로 만든 평가셋**에서 리콜@k를 직접 측정할 것. 공개 리더보드의 0.5점 차이는 내 데이터에서의 10점 차이를 예측해 주지 못한다.

## 함정 세 가지

첫째, **트렁케이션 후 재정규화 누락.** 앞서 코드에서 보았듯 잘라낸 벡터는 단위 벡터가 아니므로 반드시 재정규화한다. 코사인 유사도를 내적으로 계산하는 인덱스(대부분의 ANN 라이브러리)에서는 이게 정확도를 갉아먹는 조용한 버그가 된다.

둘째, **MRL 차원으로 검색 품질을 재검증하지 않는 것.** MRL은 "대부분의 태스크에서" 품질 저하가 작다는 것이지, 내 도메인 용어가 뒤쪽 차원에 인코딩되어 있을 가능성까지 보장하지 않는다. 차원을 자르면 반드시 자른 차원으로 리콜을 다시 측정한다.

셋째, **양자화만 하고 리스코어를 안 붙이는 것.** 특히 바이너리 양자화는 단독 사용 시 리콜 손실이 크다. 오버샘플링 + 리스코어 세트로 써야 "32배 절약"이라는 숫자가 실제로 성립한다.

## 결론

- 임베딩 모델 선택에서 리더보드 순위는 후보 좁히기용 필터다. 상위권 점수 차이는 벤치마크 노이즈 수준이며, MTEB 운영진 스스로 과적합을 인정하고 있다.
- 진짜 결정 변수는 차원 수다. MRL 트렁케이션(예: 4096→1024)과 int8/바이너리 양자화를 조합하면 저장 비용을 4~32배 줄일 수 있다.
- 다국어·셀프호스팅 조합이라면 Apache 2.0의 Qwen3-Embedding(전 사이즈 MRL 지원, 32K 컨텍스트)이 2026년의 기본값이 됐다.
- 바이너리 양자화는 오버샘플링 + 리스코어와 세트로 쓰고, 트렁케이션 후에는 재정규화를 잊지 않는다.
- 최종 선택은 언제나 내 쿼리로 만든 평가셋의 리콜@k로 한다. 지금 가진 코퍼스에서 쿼리 50개를 추출해 후보 3개의 리콜을 재는 것이 이 글에서 바로 실행할 수 있는 첫 단계다.
