# MCP 2026-07-28 스펙 해부: 세션을 버린 프로토콜이 에이전트 인프라를 어떻게 바꾸나

2024년 11월 Anthropic가 Model Context Protocol(MCP)을 공개했을 때만 해도 이 프로토콜은 "AI 업계의 USB-C"라는 비유로 소개되는 실험적 표준이었다. 2년도 채 지나지 않은 지금, MCP는 OpenAI, Google DeepMind, Microsoft까지 채택한 사실상의 업계 표준이 되었고, 2026년 7월 28일에는 프로토콜 역사상 가장 큰 전환점이 되는 새 스펙 버전 `2026-07-28`이 릴리스되었다.

이번 릴리스의 핵심은 한 문장으로 요약된다: **MCP가 양방향 상태 유지(stateful) 프로토콜에서 요청/응답 기반의 무상태(stateless) 프로토콜로 재탄생했다.** 공식 블로그에 따르면 이는 MCP 서버의 안정성과 확장성을 개선하고 싶어 했던 개발자들의 요청 중 가장 많았던 사항이다.

이 글에서는 무엇이 바뀌었는지, 왜 바뀌었는지, 그리고 기존 MCP 서버를 운영 중이라면 무엇을 지금 해야 하는지를 정리한다.

## 왜 세션이 문제였는가

기존 MCP의 Streamable HTTP 트랜스포트는 연결 지향적 설계였다. 클라이언트는 서버에 접속한 뒤 `initialize` → `initialized` 핸드셰이크를 수행하고, 서버는 `Mcp-Session-Id` 헤더로 식별되는 세션을 발급한다. 이후 모든 요청은 그 세션에 묶여 있었다.

이 설계는 로컬에서 단일 클라이언트가 단일 서버를 붙잡고 있는 개발 시나리오에서는 잘 동작했다. 문제는 프로덕션이었다.

- **로드밸런싱이 깨진다.** 세션은 특정 서버 인스턴스의 메모리에 살아 있으므로, 라운드 로빈 로드밸런서 뒤에 인스턴스를 여러 개 두면 요청이 엉뚱한 인스턴스로 간다. 스티키 세션이나 외부 세션 저장소를 얹는 우회책이 필요했다.
- **서버가 클라이언트를 호출한다.** sampling이나 elicitation 같은 기능은 서버→클라이언트 방향의 요청을 포함한다. 이를 위해 스트림을 계속 열어둬야 했고, 프록시·방화벽·서버리스 환경에서는 열린 스트림 자체가 장애 지점이 되었다.
- **서버리스에 안 맞는다.** AWS Lambda나 Cloudflare Workers처럼 요청 단위로 실행되는 환경은 상주하는 세션 상태를 가질 수 없다. 그래서 주요 클라우드 벤더들이 이번 stateless 전환을 일제히 환영한 것이다. AWS는 새 스펙의 stateless 코어가 Amazon Bedrock AgentCore에서 바로 활용 가능하다고 밝혔다.

## 바뀐 것 1: 핸드셰이크와 세션의 공식 폐기

`2026-07-28` 스펙에서 `initialize`/`initialized` 교환과 `Mcp-Session-Id` 헤더는 공식적으로 은퇴했다. 각 요청은 자신의 프로토콜 버전, 클라이언트 신원, 클라이언트 기능(capability)을 `_meta` 필드에 스스로 실고 다닌다. 서버의 기능을 미리 알고 싶은 클라이언트를 위해 새로운 `server/discover` RPC가 추가되었지만, 이것은 필수가 아니다.

실제 요청 모습은 이렇다(공식 블로그 예시):

```http
POST /mcp HTTP/1.1
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: search

{"jsonrpc":"2.0","id":1,"method":"tools/call",
 "params":{"name":"search","arguments":{"q":"otters"},
 "_meta":{"io.modelcontextprotocol/clientInfo":{"name":"my-app","version":"1.0"}}}}
```

모든 요청이 자기 자신을 설명하므로, 어떤 요청이든 평범한 라운드 로빈 로드밸런서 뒤의 어떤 인스턴스에도 떨어질 수 있다. 캐싱도 표준 HTTP 캐싱 시맨틱를 그대로 쓸 수 있게 된다.

한 가지 오해하기 쉬운 점: **프로토콜이 stateless가 되어도 애플리케이션이 stateless여야 하는 것은 아니다.** 공식 문서는 상태를 유지해야 하는 서버에게 명시적 핸들(handle) 패턴을 권한다. 도구가 상태 참조를 담은 토큰을 발급하고, 모델이 그것을 다음 호출의 인자로 되돌려주는 방식이다.

```python
# 상태를 명시적 핸들로 다루는 패턴 (개념 예시)
@mcp.tool()
def start_analysis(dataset: str) -> dict:
    handle = state_store.create(dataset)  # 외부 저장소에 상태 생성
    return {"handle": handle, "status": "started"}

@mcp.tool()
def get_result(handle: str) -> dict:
    return state_store.read(handle)  # 핸들을 인자로 받아 상태 조회
```

세션 메모리 대신 Redis 같은 외부 저장소가 그 자리를 대신하는, 웹 개발자에게는 지극히 익숙한 설계로 수렴한 셈이다.

## 바뀐 것 2: MRTR — 열린 스트림 없이 서버가 질문하기

서버→클라이언트 요청(sampling, elicitation, roots/list)은 지속 열린 스트림이 필요했던 마지막 이유였다. Multi Round-Trip Requests(MRTR)는 이를 뒤집는다.

서버가 클라이언트에게 추가 입력이 필요하면 `resultType: "input_required"`와 함께 필요한 질문들을 반환하고, 클라이언트는 답변을 첨부해 원래 호출을 재시도한다. 하나의 논리적 작업이 여러 왕복으로 이어질 뿐, 어느 시점에도 스트림이 열려 있을 필요가 없다.

Supabase의 제품 책임자는 공식 발표에서 이 변화의 실무적 의미를 잘 요약했다. Supabase MCP는 stateless로 운영되는 바람에 기존 설계에서는 elicitation(사용자 확인)을 지원하기 어려웠는데, MRTR 덕분에 "새 프로젝트 생성 비용을 확인받는다"거나 "데이터를 삭제하는 쿼리를 실행 전 승인받는" 흐름을 넣을 수 있게 되었다는 것이다. 파괴적 작업의 사전 승인이라는 에이전트 안전성의 필수 요소가, 확장성을 희생하지 않고 가능해진 셈이다.

## 바뀐 것 3: 헤더 기반 라우팅과 캐시 가능한 목록

Streamable HTTP 요청은 이제 `Mcp-Method`와 `Mcp-Name` 헤더를 반드시 포함해야 한다. 사소해 보이지만 게이트웨이 운영자에게는 큰 변화다. 지금까지는 JSON 본문을 파싱해야 어떤 도구가 호출됐는지 알 수 있었지만, 이제는 헤더만 보고 라우팅·속도 제한·권한 부여를 할 수 있다.

```nginx
# 헤더 기반 접근 제어 예시: delete 계열 도구는 별도 인증 필요
location /mcp {
    if ($http_mcp_name ~ "^delete_") {
        # 읽기 전용 게이트웨이에서 차단, 관리 채널로 위임
        return 403;
    }
    proxy_pass http://mcp_backend;
}
```

또한 도구 목록 응답에 캐시 힌트와 결정적 순서가 포함되어, 클라이언트는 도구 카탈로그를 캐시할 수 있고 재접속 시에도 업스트림 프롬프트 캐시가 안정적으로 유지된다. LLM API 비용에서 프롬프트 캐시 히트가 차지하는 비중을 생각하면, "재접속할 때마다 캐시가 깨지는" 문제의 해결은 비용에 직결된다.

## 바뀐 것 4: 인증 — DCR에서 CIMD로

인증 파트는 겉으로 드러나지 않지만 운영자에게 가장 실제적인 변경이다. CLI 클라이언트로 OAuth 로그인을 하다가 `redirect_uri` 에러를 만난 적이 있다면, 그 원인 중 하나가 이제 명확해졌다.

- 클라이언트 자격 증명이 발급한 issuer에 묶인다. 자격 증명을 여러 인증 서버에서 재사용할 수 없다(RFC 9207 issuer 검증 준수).
- Dynamic Client Registration(DCR)이 공식적으로 비권장(deprecated)되고, Client ID Metadata Documents(CIMD)가 표준 자리를 대신한다. DCR은 하위 호환을 위해 당분간 동작하지만 미래 버전에서 제거된다.

DCR은 사실상 "아무나 인증 서버에 클라이언트를 등록할 수 있다"는 OAuth 생태계에서 오래된 골칫거리였고, MCP가 이를 걷어내는 것은 엔터프라이즈 보안 심사를 통과하기 위한 필수 과정이었다. 참고로 미 국방부 산하 NSA가 2026년 6월 MCP 보안 설계 가이드를 별도로 발간했을 정도로, MCP의 보안 표면은 이미 국가 기관이 주목하는 수준이다.

## 확장 프레임워크와 폐기 정책

이번 버전에서 확장(extension) 프레임워크가 공식화되면서, 장기 실행 작업을 위한 Tasks, UI 임베딩을 위한 MCP Apps, 엔터프라이즈 관리형 인증을 위한 EMA(Enterprise Managed Authorization)가 모두 확장으로 자리 잡았다. Tasks는 실험적 코어에서 `io.modelcontextprotocol/tasks` 확장으로 이동하며 폴링 기반 `tasks/get`과 새 `tasks/update`를 갖게 되었다.

반대 방향도 분명하다. Roots, Sampling, Logging이 비권장되었고(최소 12개월간 동작 보장), 레거시 HTTP+SSE 트랜스포트도 1년의 유예 기간을 두고 폐기된다. 특히 주목할 것은 **공식적으로 12개월 최소 유예를 담보하는 폐기 정책** 자체가 스펙에 명시되었다는 점이다. 이제 업그레이드는 급작스러운 사고가 아니라 계획의 대상이 되었다.

## TypeScript·Python SDK 누적 10억 다운로드가 말해주는 것

생태계 규모의 변화도 짚을 만하다. 공식 발표에 따르면 Tier 1 SDK(TypeScript, Python, Go, C#)의 월 다운로드가 5억에 근접하고, TypeScript와 Python SDK는 누적 10억 다운로드를 넘어섰다. Zuplo가 기술 전문가 약 100명을 대상으로 실시한 설문에서는 공개 등록된 MCP 서버가 17,000개를 넘었고, MCP를 실사용 중인 응답자의 70%가 환경에 2~7개의 MCP 서버를 설정해 두었다고 답했다.

이 숫자들이 시사하는 것은 MCP가 "코딩 에이전트용 편의 도구"를 넘어 에이전트 인프라의 기반 계층이 되었다는 점이다. Microsoft는 MCP를 Foundry의 기반이라 칭하며 "수십 개의 통합에서 수천 개로" 확장 중이라고 밝혔고, Honeycomb은 월간 대화형 쿼리의 약 20%가 이제 에이전트에 의해 수행된다고 발표했다. 관측 가능성(observability) 도메인에서조차 트래픽의 5분의 1이 에이전트라는 뜻이다.

## 마이그레이션 체크리스트

지금 프로덕션에서 MCP 서버를 운영 중이라면, 스펙의 12개월 시계를 의식한 우선순위 정리가 필요하다.

1. **세션 의존성 제거 (지금 시작).** `Mcp-Session-Id`에 의존하는 로직을 찾아 명시적 핸들 패턴으로 옮긴다. 상태가 필요하다면 외부 저장소로.
2. **HTTP+SSE 트랜스포트 점검.** 아직 레거시 SSE를 쓰고 있다면 Streamable HTTP로의 이동이 먼저다. SSE의 유예 기간 역시 1년이다.
3. **헤더 노출 확인.** 게이트웨이·프록시가 `Mcp-Method`/`Mcp-Name` 헤더를 백엔드까지 전달하는지, 그리고 그 헤더로 라우팅 규칙을 재구성할 수 있는지 점검한다.
4. **DCR 사용처 파악.** OAuth 클라이언트 등록에 DCR을 쓰고 있다면 CIMD 전환 계획을 세운다. DCR은 하위 호환으로 당분간 동작하지만 제거 예정이다.
5. **SDK 업그레이드.** 4개 Tier 1 SDK가 모두 `2026-07-28`을 지원하며 상세 마이그레이션 노트를 제공한다. 세션 식별자에 의존하던 코드가 있다면 마이그레이션 비용이 있음을 감안해 일정을 잡는다.

## 결론

- MCP `2026-07-28`의 본질은 **프로토콜 코어의 stateless 전환**이다. 핸드셰이크와 세션 ID가 사라지고, 모든 요청이 `_meta`로 자기 서술한다.
- **MRTR**로 열린 스트림 없이 elicitation/sampling이 가능해져, 확장성과 에이전트 안전성(사전 승인)이 동시에 확보됐다.
- `Mcp-Method`/`Mcp-Name` **헤더 라우팅**은 게이트웨이 운영을 단순화하고, **DCR→CIMD** 전환은 엔터프라이즈 보안 심사의 장애물을 걷어낸다.
- Roots/Sampling/Logging과 레거시 SSE 트랜스포트는 **12개월 유예** 아래 폐기된다. 지금 점검하고 계획에 넣어야 한다.
- 첫 단계는 간단하다: 운영 중인 MCP 서버의 세션 의존성과 SSE 트랜스포트 사용 여부부터 확인해 보자. 스펙 문서와 체인지로그는 modelcontextprotocol.io/specification/2026-07-28 에서 공식적으로 확인할 수 있다.

한 프로토콜이 "성장하는 통증"을 브레이킹 체인지로 정면 돌파했다는 점이 이번 릴리스의 진짜 메시지다. 상태를 프로토콜에서 몰아내는 대신 애플리케이션 계층의 명시적 설계로 넘긴 이 결정이 향후 수년간 에이전트 인프라의 지형을 결정할 것이다.
