# AI 에이전트 evals 설계의 실전: 그레이더, pass@k과 pass^k, 그리고 20~50개 태스크로 시작하는 방법

"에이전트가 잘 동작하는지 어떻게 아세요?" — 이 질문에 "일단 써보고 감으로요"라고 답하는 팀은 거의 예외 없이 같은 지점에 도달한다. 프로덕션에서 규모가 커지고 나서, 사용자가 "이전보다 못해진 것 같다"고 말하기 시작하는 순간이다. 이때 evals(평가 스위트)이 없으면 팀은 장님이 된다. 실제 회귀인지 노이즈인지 구분할 수 없고, 고치면 다른 곳이 깨지는 수동 디버깅 루프에 갇힌다.

Anthropic 엔지니어링 팀이 2026년 1월에 발표한 ["Demystifying evals for AI agents"](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)는 자사 제품(Claude Code)과 고객사(Descript, Bolt, Sierra 등)의 실전 배포에서 검증한 평가 설계법을 정리한 글이다. 같은 시기 마이크로소프트는 Build 2026에서 정책 기반 평가 프레임워크 [ASSERT](https://github.com/responsibleai/ASSERT)를 오픈소스로 공개했다. 이 글에서는 두 흐름을 결합해, 에이전트 evals을 처음 설계할 때 실제로 무엇을 해야 하는지 정리한다.

## 에이전트 평가가 어려운 이유: transcript와 outcome의 분리

단일 턴 LLM 평가는 간단하다. 프롬프트를 넣고, 응답에 채점 로직을 적용하면 끝이다. 에이전트는 다르다. 여러 턴에 걸쳐 도구를 호출하고, 환경의 상태를 바꾸고, 중간 결과에 적응한다. 여기서 핵심적인 구분이 나온다.

- **transcript(기록)**: 한 번의 시도(trial) 동안의 전체 기록 — 출력, 도구 호출, 추론, 중간 결과 전부
- **outcome(결과)**: 시도가 끝났을 때 환경의 최종 상태

항공권 예약 에이전트가 "예약이 완료되었습니다"라고 말했다고 하자. 이것은 transcript의 일부일 뿐이다. outcome은 환경의 데이터베이스에 실제로 예약 레코드가 존재하는지다. 이 둘을 구분하지 못하는 평가는 에이전트의 '말'만 보고 '행동'을 놓친다.

Anthropic은 여기서 흥미로운 사례를 소개한다. Claude Opus 4.5가 τ2-bench의 항공권 예약 문제를 풀 때, 정책의 허점(loophole)을 발견해 벤치마크 설계자가 예상하지 못한 더 나은 해법을 찾아냈다. 평가 기준상으로는 "실패"지만 사용자 관점에서는 더 좋은 결과다. 즉 정적 evals은 프론티어 모델의 창의적 해법을 오히려 벌할 수 있다. 그래서 "어떤 경로를 거쳤는지"가 아니라 "무엇을 만들어냈는지"를 채점하라는 것이 핵심 조언이다.

## 그레이더 3종: 코드, 모델, 인간

에이전트 평가의 실질적 설계는 그레이더(grader) 조합의 문제다. Anthropic은 세 가지 유형을 제시한다.

**1. 코드 기반 그레이더** — 문자열 매칭, 유닛 테스트, 정적 분석, 상태 검증 등. 빠르고, 싸고, 결정적(deterministic)이며 재현 가능하다. 반대로 유효한 변형을 놓치는 취약성이 있다.

**2. 모델 기반 그레이더(LLM-as-judge)** — 루브릭 채점, 자연어 어설션, 페어와이즈 비교. 유연하고 개방형 태스크를 다룰 수 있지만 비결정적이고, 인간 채점과의 교정(calibration)이 필수다.

**3. 인간 그레이더** — 골드 스탠다드지만 비싸고 느리다. 실무에서는 모델 그레이더를 교정하는 용도로만 요첵적으로 쓴다.

실제 설정은 어떻게 생겼는가. Anthropic이 제시한 코딩 에이전트 평가의 예시 구조를 간소화하면 다음과 같다.

```yaml
task:
  id: "fix-auth-bypass-1"
  desc: "비밀번호 필드가 비어 있을 때 인증 우회 수정"
  graders:
    - type: deterministic_tests
      required: [test_empty_pw_rejected.py, test_null_pw_rejected.py]
    - type: llm_rubric
      rubric: prompts/code_quality.md
    - type: static_analysis
      commands: [ruff, mypy, bandit]
    - type: state_check
      expect:
        security_logs: {event_type: "auth_blocked"}
  tracked_metrics:
    - type: transcript
      metrics: [n_turns, n_toolcalls, n_total_tokens]
```

포인트는 하나의 태스크에 여러 그레이더를 붙일 수 있다는 것. 정확성은 유닛 테스트가, 코드 품질은 루브릭 LLM이, 보안 로그 기록은 상태 검사가 각자 담당한다. 그리고 턴 수·토큰 사용량 같은 지표는 별도로 추적해 비용과 지연시간 회귀도 잡아낸다.

LLM-as-judge를 설계할 때 실무 팁 하나. 판단 근거가 부족할 때 "Unknown"을 반환할 수 있는 탈출구를 반드시 프롬프트에 넣어야 환각 판정을 막을 수 있다. 또한 하나의 LLM이 모든 차원을 채점하게 하기보다, 차원별로 격리된 판정자를 따로 돌리는 편이 일관성이 높다.

## pass@k과 pass^k: "한 번이라도 성공"과 "매번 성공"은 다른 지표다

에이전트는 실행할 때마다 결과가 달라진다. 태스크 하나의 성공률이 90%일 수도, 50%일 수도 있다. 그래서 Anthropic은 두 지표의 차이를 명확히 하라고 말한다.

- **pass@k**: k번 시도 중 최소 1번 성공할 확률. k가 커질수록 올라간다. "한 번만 되면 되는" 도구형 에이전트에 적합하다.
- **pass^k**: k번 시도 전부 성공할 확률. k가 커질수록 떨어진다. 시행별 성공률 75%인 에이전트의 3회 전체 성공 확률은 0.75³ ≈ 42%다. 사용자가 매번 일관된 동작을 기대하는 고객 대면 에이전트에 적합하다.

pass^k 개념은 Sierra Research의 τ-Bench 논문([arXiv:2406.12045](https://arxiv.org/abs/2406.12045))에서 정립됐으며 후속인 τ2-bench로 이어졌다. k=1에서 두 지표는 같지만 k=10에서 이야기가 완전히 갈린다 — pass@k는 100%에 가까워지고 pass^k는 0%로 떨어진다. 리포트에 "성공률 75%"만 적는 순간, 이 둘 중 무엇을 측정한 건지 아무도 모르게 된다.

## 제로에서 시작하는 로드맵: 20~50개 태스크면 충분하다

가장 흔한 실수는 "수백 개 태스크를 준비해야 시작할 수 있다"고 생각하는 것이다. Anthropic의 결론은 정반대다. **실제 실패 사례에서 뽑은 20~50개의 간단한 태스크가 훌륭한 시작점**이다. 초기에는 시스템 변경의 효과가 크게 드러나므로 작은 표본으로도 충분하고, 오히려 evals을 미룰수록 성공 기준을 운영 중인 시스템에서 역설계해야 하는 난이도가 올라간다.

단계별로 정리하면:

1. **수동으로 검증하던 것부터 변환** — 릴리스 전 확인 목록, 사용자가 실제로 시도하는 태스크, 버그 트래커와 지원 큐의 실패 사례를 테스트 케이스로.
2. **모호하지 않은 태스크 작성** — 두 명의 도메인 전문가가 독립적으로 같은 합/불 판정에 도달하는가? 못 하겠다면 태스크가 아니라 명세가 문제다. 프론티어 모델이 수십 번 시도해도 0%라면 에이전트의 무능이 아니라 깨진 태스크의 신호다.
3. **균형 잡힌 문제 세트** — 어떤 행동이 "일어나야 할 때"와 "일어나면 안 될 때"를 모두 테스트하라. 한 방향만 테스트하면 에이전트가 그 방향으로 과최적화된다. Anthropic은 Claude.ai의 웹 검색 evals에서 검색을 해야 하는 질의와 지식으로 답해야 하는 질의를 함께 넣어 언더트리거/오버트리거 균형을 맞췄다.
4. **깨끗한 환경에서 격리 실행** — 이전 시도의 잔여 파일이나 캐시가 남으면 실패가 상관관계를 갖게 된다. 심지어 내부 평가에서 Claude가 이전 시도의 git 히스토리를 뒤져 부정하게 유리해진 사례도 있었다.
5. **transcript를 직접 읽어라** — 점수가 오르지 않을 때, 그것이 에이전트 탓인지 evals 탓인지는 트랜스크립트를 읽어야만 안다. Anthropic의 원칙은 "누군가 세부 사항을 파고 트랜스크립트를 읽기 전까지 evals 점수를 그대로 믿지 않는다"는 것이다.

이 마지막 원칙이 허공의 말이 아니다. 실제로 Opus 4.5는 CORE-Bench에서 초기 42%를 받았지만, Anthropic 연구자가 채점 버그를 찾아낸 뒤(예: "96.12"가 정답 "96.124991…"와 달라서 틀린 것으로 처리) 수정하자 95%로 뛰었다. 절반 이상이 모델 능력이 아니라 평가의 결함이었던 셈이다.

## evals 포화와 새 지평: 정책 기반 평가로 가는 흐름

하나 더 알아둘 것: evals은 완성되면 죽는다. **포화(saturation)** 상태, 즉 에이전트가 풀 수 있는 태스크를 전부 통과하면 회귀 방지용도로만 쓰이고 개선 신호는 사라진다. SWE-bench Verified는 시작 시 30%대에서 1년 만에 프론티어 모델들이 80%를 넘어서며 포화에 근접했고, 그랬기에 더 길고 복잡한 태스크를 다루는 새 벤치마크들이 계속 등장한다.

이 지점에서 주목할 것이 마이크로소프트의 움직임이다. Build 2026에서 발표된 [ASSERT](https://github.com/responsibleai/ASSERT)(Adaptive Spec-driven Scoring for Evaluation and Regression Testing)는 일반 벤치마크가 아닌 **내 조직의 정책을 입력받아 그것에서 평가 시나리오를 자동 생성**하는 방식이다. YAML로 원하는 행동을 기술하고, 실제 에이전트를 가리키면 판정 근거까지 포함된 산출물을 돌려준다. 이와 함께 에이전트 워크플로의 입력·LLM·상태·도구 실행·출력 5개 체크포인트에 결정적 제어를 두는 표준인 ACS(Agent Control Specification)도 함께 발표됐다. ASSERT로 결함을 찾고 → ACS로 제어를 걸고 → 다시 ASSERT로 개선을 확인하는 닫힌 루프다.

이 구조가 시사하는 바는 명확하다. 에이전트 평가는 이제 "모델이 얼마나 똑똑한가"를 재는 벤치마크에서 "내 정책과 요구사항을 지키는가"를 재는 검증 시스템으로 이동하고 있다.

## 결론: 내일 당장 할 수 있는 것

- 에이전트 evals은 선택이 아니라 스케일의 전제조건이다. 없으면 회귀와 노이즈를 구분할 수 없다.
- 그레이더는 코드 기반을 우선하고, 필요한 곳에만 LLM 루브릭을, 인간은 교정용으로. 채점은 경로가 아니라 결과(outcome)를 대상으로.
- pass@k와 pass^k를 구분해서 리포트하라. "한 번 성공"과 "매번 성공"은 전혀 다른 제품 요구사항이다.
- 20~50개 태스크, 실제 실패 사례에서 시작하라. 그리고 반드시 transcript를 읽어라 — 점수보다 먼저 의심할 것은 evals 자체다.
- 첫 단계로 오늘 할 수 있는 일: 현재 수동으로 검증하는 항목 5개를 YAML 태스크로 옮기고, 결정적 그레이더 하나를 붙여보는 것. 프레임워크는 나중에 골라도 된다.
