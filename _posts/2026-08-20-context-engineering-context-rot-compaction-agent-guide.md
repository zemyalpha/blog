# 컨텍스트는 부패한다: context rot에서 컴팩션까지, AI 에이전트 컨텍스트 엔지니어링 실전 가이드

"프롬프트를 잘 쓰는 것"에서 "컨텍스트를 잘 설계하는 것"으로 무게중심이 옮겨진 지 이미 오래됐다. Anthropic은 2025년 9월 엔지니어링 블로그에서 이 전환을 명시적으로 선언했다. 언어 모델로 무언가를 만드는 일이란 "어떤 문구를 넣을까"가 아니라 **"어떤 컨텍스트 구성이 원하는 동작을 만들어낼 확률을 최대화하는가"**를 묻는 문제라는 것이다.

왜 이런 전환이 일어났는가. 이유는 간단하다. 챗봇 시대의 LLM 호출은 한 번의 추론으로 끝났지만, 에이전트는 도구를 호출하고 결과를 받아 다시 추론하는 루프를 수십 번, 수백 번 돈다. 매 턴마다 시스템 프롬프트, 도구 정의, MCP 서버가 내려주는 데이터, 대화 이력, 도구 호출 결과가 컨텍스트 윈도우에 쌓인다. 프롬프트는 한 번 잘 쓰면 끝나는 정적 산출물이지만, 에이전트의 컨텍스트는 **매 추론마다 다시 큐레이션해야 하는 동적 상태**다. 이 글에서는 그 상태를 어떻게 관리할 것인가를, Anthropic과 Microsoft가 공개한 1차 문서를 중심으로 정리한다.

## 1. 왜 컨텍스트를 아껴야 하는가: context rot

컨텍스트 윈도우가 100만 토큰, 1000만 토큰으로 커지면 컨텍스트 관리는 불필요해질까. 결론부터 말하면 아니다.

벡터 DB 업체 Chroma가 2025년 7월에 발표한 기술 보고서 "Context Rot: How Increasing Input Tokens Impacts LLM Performance"는 이 질문에 대한 가장 체계적인 답 중 하나다. 연구팀은 GPT-4.1, Claude 4, Gemini 2.5, Qwen3 등 18개 모델을 대상으로, **태스크 난이도를 고정한 채 입력 길이만 늘려가며** 성능을 측정했다. 결과는 명확했다. 모델은 컨텍스트를 균일하게 처리하지 않으며, 입력이 길어질수록 성능이 불안정해진다. 단순 검색만 요구하는 Needle in a Haystack(NIAH) 벤치마크에서는 만점에 가까운 모델들도, 의미적 연관을 추론해야 하거나 유사한 오답 후보(디스트랙터)가 섞이는 조건에서는 길이가 늘 때 성능이 무너졌다.

Anthropic은 이 현상을 **context rot(컨텍스트 부패)**라는 이름으로 부르며, 원인을 두 가지로 설명한다.

첫째, 트랜스포머의 구조적 제약이다. 어텐션은 모든 토큰 쌍이 서로를 참조하므로 n개의 토큰에 대해 n² 개의 관계가 생긴다. 컨텍스트가 길어지면 이 관계들을 포착하는 능력이 얇아진다.

둘째, 학습 데이터 분포다. 학습 코퍼스에는 짧은 시퀀스가 긴 시퍼스보다 훨씬 많으므로, 모델은 긴 범위 의존성에 대해 상대적으로 적은 학습 신호를 받았다. 위치 인코딩 보간 같은 기법으로 학습 길이보다 긴 입력을 다룰 수 있지만, 토큰 위치 이해에는 손실이 따른다.

중요한 뉘앙스는 이것이 **성능 그라디언트지 난벽(cliff)이 아니라는 점**이다. 긴 컨텍스트에서도 모델은 여전히 유능하지만, 정보 검색과 장거리 추론의 정밀도가 떨어진다. Anthropic은 이를 두고 컨텍스트를 "한정된 자원이며 한계 수익 체감이 있는 것"으로 취급하라고 조언한다. 인간의 작업 기억(working memory)에 비유되는 **어텐션 버짓**은 모델 능력과 무관하게 존재하며, 토큰을 하나 더 넣을 때마다 조금씩 소진된다.

따라서 좋은 컨텍스트 엔지니어링의 정의는 이렇게 내려진다. **원하는 결과를 만들 확률을 최대화하는, 최소의 고신호(high-signal) 토큰 집합을 찾는 것.** "최소"가 반드시 "짧게"를 의미하지는 않는다. 필요한 정보는 앞뒤로 모두 넣되, 쓸모없는 토큰은 하나도 넣지 말라는 뜻이다.

## 2. 컨텍스트의 해부학: 무엇을 어떻게 다듬을 것인가

Anthropic은 컨텍스트를 구성하는 요소별로 실무 지침을 제시한다.

**시스템 프롬프트**는 "올바른 고도(altitude)"를 찾아야 한다. 한쪽 극단은 if-else를 하드코딩한 취약한 프롬프트이고, 다른 극단은 구체적 신호 없이 모호하게 남겨둔 지시다. 그 사이, 즉 행동을 유도할 만큼 구체적이면서 모델이 스스로 판단할 여지를 주는 지점이 골디락스 존이다. 구조는 `<background_information>`, `<instructions>`, `## Tool guidance`처럼 XML 태그나 마크다운 헤더로 섹션을 나누는 것을 권장한다. 다만 모델이 좋아질수록 포맷 자체의 중요도는 낮아지는 추세라고 덧붙인다. 실무 전략은 역방향이다. 최고 성능 모델에 **최소 프롬프트부터 시작해** 실패 모드를 관찰한 뒤 그에 맞는 지시와 예시만 추가한다.

**도구 정의**는 가장 흔히 망가지는 지점이다. Anthropic이 관찰한 최다 실패 패턴은 기능이 겹치거나 어느 도구를 쓸지 애매한 **비대한 도구 셋**이다. 인간 엔지니어가 상황을 보고 어느 도구를 써야 할지 확신할 수 없다면, 에이전트는 더 잘할 수 없다. 도구는 잘 설계된 코드베이스의 함수처럼 자기완결적이어야 하고, 입력 파라미터는 모델의 강점에 맞게 서술적이고 모호하지 않아야 하며, 반환값은 토큰 효율적이어야 한다.

**예시(few-shot)**는 여전히 강력한 도구지만, 모든 엣지 케이스를 프롬프트에 쑤셔넣는 방식은 권장하지 않는다. 대신 기대 행동을 대표하는 **다양하고 정규적인(canonical) 예시 집합**을 소수 큐레이션하라. "예시는 천 마디 말의 가치를 지닌 그림"이라는 표현을 쓴다.

## 3. 런타임 전략: 미리 다 넣지 말고, 필요할 때 가져오라

RAG 초기 패턴은 추론 전에 임베딩 검색으로 관련 컨텍스트를 미리 채워 넣는 것이었다. Anthropic은 요즘 현장이 여기에 **저스트 인 타임(just-in-time) 검색**을 결합하는 쪽으로 이동한다고 본다. 즉 에이전트는 파일 경로, 저장된 쿼리, 웹 링크 같은 가벼운 식별자만 들고 있다가, 도구로 실행 시점에 필요한 데이터만 컨텍스트로 불러온다.

Claude Code가 대표 사례다. 대용량 데이터베이스를 분석할 때 전체 데이터를 컨텍스트에 올리는 대신 타겟 쿼리를 작성해 결과를 파일로 저장하고, `head`와 `tail` 같은 Bash 명령으로 필요한 부분만 훑는다. 이는 인간이 전체 코퍼스를 외우지 않고 파일 시스템·북마크·인박스 같은 외부 인덱스를 쓰는 방식과 같다.

여기에 흥미로운 부산물이 있다. 참조의 **메타데이터 자체가 신호**가 된다는 것이다. `tests/` 폴더의 `test_utils.py`와 `src/core_logic/`의 같은 이름 파일은 다른 용도를 암시한다. 폴더 계층, 네이밍 컨벤션, 타임스탬프가 에이전트에게 정보를 주는 단서가 된다. 이런 자율 탐색은 **점진적 공개(progressive disclosure)**를 가능하게 해서, 에이전트가 필요한 것만 작업 기억에 유지하며 이해를 층층이 쌓게 한다.

물론 트레이드오프는 있다. 런타임 탐색은 사전 계산된 검색보다 느리다. 그래서 Claude Code는 하이브리드로 동작한다. `CLAUDE.md`는 미리 통째로 컨텍스트에 넣되(정적, 빠름), 나머지는 `glob`과 `grep` 원시 도구로 실시간 탐색한다(동적, 유연). 법무·재무처럼 내용이 덜 동적인 도메인은 사전 검색 비중을 높이는 편이 낫다. Anthropic의 결론은 소박하다. "돌아가는 가장 단순한 것을 하라."

## 4. 장기 작업의 3대 기법: 컴팩션, 구조화 노트, 서브에이전트

수십 분~여러 시간짜리 작업(대규모 코드 마이그레이션, 심층 리서치)은 토큰 수가 컨텍스트 윈도우를 초과한다. Anthropic은 이를 위한 세 가지 기법을 제시한다.

### 4-1. 컴팩션 (Compaction)

한계에 가까워진 대화를 요약해 새 컨텍스트 윈도우를 여는 기법이다. Claude Code에서는 메시지 히스토리를 모델에 넘겨 요약·압축하는 방식으로 구현하며, 아키텍처 결정, 미해결 버그, 구현 세부사항은 보존하고 중복된 도구 출력은 버린다. 압축 후 에이전트는 요약과 **최근 접근 파일 5개**로 이어서 작업한다.

컴팩션의 달인이 되는 지점은 보존/폐기의 선택이다. 과하게 압축하면 나중에야 중요해지는 미묘한 컨텍스트를 잃는다. Anthropic은 복잡한 에이전트 트레이스로 프롬프트를 튜닝하되, 먼저 **리콜을 최대화**해 모든 관련 정보를 잡게 한 뒤, 그다음 **정밀도를 높여** 잡동사니를 걷어내라고 권한다. 가장 쉬운 성과 개선 지점(low-hanging fruit)은 도구 호출 결과 비우기(tool result clearing)다. 히스토리 깊숙이 있는 도구의 원본 결과를 다시 볼 일은 거의 없다.

의사코드로 나타내면 이런 형태가 된다.

```python
def compact(history: list[Message], model) -> list[Message]:
    # 1단계: 리콜 최대화 — 놓치지 않도록 모든 결정/미해결 항목 요약
    summary = model.summarize(
        history,
        keep=["아키텍처 결정", "미해결 버그", "구현 세부", "사용자 제약"],
        drop=["중복 도구 출력", "이미 소비된 원본 결과"],
    )
    # 2단계: 최근 참조만 곁들이기 (Claude Code는 최근 파일 5개)
    recent = history.recently_accessed_files(k=5)
    return [system_prompt, summary, *recent_context(recent)]
```

### 4-2. 구조화 노트 (Structured Note-taking)

에이전트가 컨텍스트 밖 파일에 정기적으로 메모를 써두고, 나중에 다시 불러오는 기법이다. Claude Code의 to-do 리스트, 커스텀 에이전트의 `NOTES.md`가 이 패턴이다. 여러 번의 도구 호출을 거치며 잃어버릴 진행 상황과 의존성을 파일로 추적한다.

가장 생생한 사례는 **Claude playing Pokémon**이다. 이 에이전트는 수천 게임 스텝에 걸쳐 "최근 1,234스텝 동안 1번 도로에서 포켓몬을 훈련했고, 피카츄가 목표 10레벨 중 8레벨을 올렸다" 같은 정확한 기록을 유지했다. 메모 구조에 대한 지시 없이도 탐험한 지역의 지도를 그리고, 달성한 키 실적을 기억하고, 상대별 유효 공격 전략 노트를 만들었다. 컨텍스트가 리셋된 뒤에도 자기 노트를 읽고 수 시간짜리 훈련이나 던전 탐험을 이어갔다. 컨텍스트 안에 다 담아서는 불가능한 장기 전략의 근간이 된다.

Anthropic은 Sonnet 4.5 출시와 함께 파일 기반 **메모리 도구**를 공개 베타로 내놓았다. 세션을 넘어 프로젝트 상태를 유지하고 축적된 지식 기반을 참조하면서 컨텍스트는 깨끗하게 유지하는 것이 목적이다.

### 4-3. 서브에이전트 (Sub-agent Architectures)

하나의 에이전트가 프로젝트 전체 상태를 들고 있기보다, 전문화된 서브에이전트가 **깨끗한 컨텍스트 윈도우**로 집중 작업을 수행한다. 메인 에이전트는 상위 계획을 조율하고, 서브에이전트는 깊은 기술 작업이나 정보 탐색을 맡는다. 각 서브에이전트는 수만 토큰 이상을 탐색에 쓸 수 있지만, 반환하는 것은 증류된 요약 **1,000~2,000 토큰**뿐이다. 상세 탐색 컨텍스트는 서브에이전트 안에 격리되고, 리드 에이전트는 종합과 분석에 집중한다. Anthropic의 멀티에이전트 리서치 시스템에서 이 패턴은 단일 에이전트 대비 심층 리서치 과제에서 상당한 개선을 보였다고 한다.

세 기법의 선택 기준은 이렇다. 많은 왕복이 필요한 작업엔 **컴팩션**, 명확한 마일스톤이 있는 반복 개발엔 **노트 작성**, 병렬 탐색이 이득인 복잡한 리서치엔 **멀티에이전트**.

## 5. 실패 모드 4형태: 중독·주의분산·혼란·충돌

Microsoft의 AI Agents for Beginners 커리큘럼은 컨텍스트가 잘못됐을 때 나타나는 실패를 4가지 유형으로 정리한다. 진단 체크리스트로 쓰기 좋다.

| 실패 모드 | 증상 | 1차 원인 | 대응 |
|---|---|---|---|
| **Poisoning (중독)** | 할루시네이션이 컨텍스트에 들어와 반복 참조되며 불가능한 목표를 좇음 | 검증 안 된 정보의 장기 기억 유입 | 컨텍스트 검증 + 격리(quarantine), 실패 시 새 스레드로 재시작 |
| **Distraction (주의분산)** | 쌓인 히스토리에 끌려 학습된 능력 대신 과거 맥락을 따라 반복·무응답 | 컨텍스트 과대 | 주기적 요약으로 히스토리 압축 |
| **Confusion (혼란)** | 도구가 너무 많아 엉뚱한 도구 호출. 소형 모델일수록 심함 | 도구 정의 과다·중복 | 도구 설명에 RAG를 적용해 태스크별 로드아웃 구성, 30개 미만 권장 |
| **Clash (충돌)** | 이전 지시와 새 지시가 충돌해 일관성 없는 추론 | 단계별 유입 정보의 모순 | 프루닝(구지침 제거·명시적 오버라이드) + 스크래치패드에서 정합화 후 반영 |

여기에 Microsoft가 강조하는 운영 원칙 하나가 더 있다. 컨텍스트 전략을 적용한 뒤에는 **다음 모델 호출이 실제로 무엇을 받았는지 검사**하라는 것. 원본 프롬프트를 다 로깅할 필요는 없고, 선택·압축·격리가 각각 무엇을 걸러냈는지를 나타내는 작은 기록(카운트, ID, 해시, 정책 라벨)이면 충분하다. "에이전트가 너무 많은 컨텍스트를 로드했는가, 잘못된 컨텍스트를 로드했는가, 필요한 컨텍스트를 놓쳤는가"가 디버깅의 기본 질문이다.

도구 로드아웃 관리는 간단하게 이렇게 구현할 수 있다.

```python
# 도구 설명에 대한 RAG: 태스크별로 관련 도구만 노출
from embeddings import embed, cosine

def select_tool_loadout(query: str, tools: list[dict], k: int = 10) -> list[dict]:
    q = embed(query)
    scored = sorted(
        tools,
        key=lambda t: -cosine(q, embed(t["description"])),
    )
    return scored[:k]  # 컨텍스트에는 이 k개의 스키마만 주입
```

## 6. 정리: 컨텍스트를 자원처럼 예산 쓰라

- **컨텍스트는 한정 자원이다.** Chroma의 context rot 연구는 18개 모델에서 입력 길이가 늘면 성능이 균일하지 않게 저하됨을 보였고, Anthropic은 모델이 강해져도 어텐션 버짓이라는 제약은 남는다고 본다. "최소의 고신호 토큰 집합"이 설계 목표다.
- **정적 큐레이션과 동적 탐색을 섞어라.** 핵심 지시는 미리 넣고(Claude Code의 `CLAUDE.md`), 나머지는 경로·쿼리·링크 같은 식별자만 들고 저스트 인 타임으로 가져온다.
- **장기 작업은 3대 기법으로 무장하라.** 대화 연속성엔 컴팩션(요약 + 최근 파일), 마일스톤 추적엔 구조화 노트(`NOTES.md`, 메모리 도구), 병렬 탐색엔 서브에이전트(탐색은 격리, 요약 1~2천 토큰만 반환).
- **실패는 4형태로 진단하라.** 중독·주의분산·혼란·충돌. 각각 검증·요약·도구 로드아웃·프루닝이 1차 대응이다.
- **관측하라.** 원문 로깅이 아니라 선택/압축/격리의 근거를 남기는 가벼운 검사 기록으로, 다음 호출이 무엇을 받았는지 추적 가능하게 만들어라.

당장 시도할 첫 단계는 작다. 지금 운영 중인 에이전트의 최근 세션 로그 하나를 열어, 마지막 모델 호출이 받은 컨텍스트를 도구 정의·시스템 프롬프트·히스토리·검색 결과로 분해해 보라. 어느 토큰이 실제로 다음 행동에 영향을 줬는지 추적하다 보면, 어텐션 버짓을 어디에서 낭비하고 있었는지 보이기 시작한다.
