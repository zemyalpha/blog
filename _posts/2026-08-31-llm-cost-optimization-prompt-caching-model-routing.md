# LLM API 비용을 구조적으로 줄이는 두 축: 프롬프트 캐싱과 모델 라우팅 실전 가이드

LLM 애플리케이션의 단가는 낮아지고 있지만, 에이전트 시대에는 호출 횟수와 컨텍스트 길이가 폭증한다. 멀티턴 에이전트 하나가 한 번의 작업에 수십 번의 API 호출을 하고, 그때마다 시스템 프롬프트와 도구 정의 수천~수만 토큰을 처음부터 다시 처리하는 것이 반복된다. 이 낭비를 없애는 대표적인 두 축이 **프롬프트 캐싱**과 **모델 라우팅**이다. 전자는 "같은 접두사를 다시 계산하지 않는 것", 후자는 "쉬운 질문에 비싼 모델을 쓰지 않는 것"이다. 이 글에서는 두 기법의 동작 원리, 공식 문서 기반 정확한 가격 구조, 그리고 실제 적용할 때 빠지기 쉬운 함정까지 정리한다.

## 1. 프롬프트 캐싱은 어떻게 동작하는가

LLM이 입력을 처리할 때 토큰을 한 번에 읽는 것이 아니라, 토큰마다 중간 계산 결과인 KV(Key-Value) 상태를 생성하면서 진행한다. 프롬프트 캐싱은 이 KV 상태를 재사용 가능한 형태로 저장해두는 기능이다. OpenAI 공식 문서도 명시하듯, 캐시에 저장되는 것은 토큰이 아니라 "KV 텐서"이며, 나중에 동일한 접두사를 가진 요청이 오면 저장된 상태를 그대로 이어받아 새 입력부터 처리한다([OpenAI Prompt Caching 문서](https://platform.openai.com/docs/guides/prompt-caching)).

핵심 조건은 **접두사 전체 일치**다. 캐시 재사용은 프롬프트 처음부터 브레이크포인트까지 전부 동일해야 한다. 도구 정의, 시스템 메시지, 대화 히스토리 순서가 조금이라도 바뀌면 그 지점 이후로는 캐시가 무효화된다. 그래서 프롬프트 캐싱은 "켜는 기술"이 아니라 **프롬프트를 캐시 친화적으로 재설계하는 기술**에 가깝다.

가격 구조는 제공사마다 다르지만, 공식 문서에서 확인되는 수치는 다음과 같다.

| 구분 | Anthropic (Claude) | OpenAI |
|------|------|------|
| 캐시 히트(읽기) | 기본 입력 단가의 **0.1배** | 최대 **90% 할인**된 캐시 입력 단가 |
| 캐시 쓰기(5분) | 기본 입력 단가의 **1.25배** | 별도 쓰기 프리미엄 없음 (기본 활성화) |
| 캐시 쓰기(1시간) | 기본 입력 단가의 **2배** | - |
| 최소 캐시 길이 | 모델별 상이 (문서 확인 필요) | **1,024 토큰** (GPT-5.6 이후 기준) |

Anthropic의 배수는 공식 문서에 명시되어 있다: 5분 캐시 쓰기는 1.25배, 1시간 캐시 쓰기는 2배, 캐시 읽기는 0.1배이며, 이 배수는 Batch API 할인 등 다른 가격 수정자와 누적된다([Anthropic Prompt Caching 문서](https://docs.anthropic.com/en/docs/build-with-claude/prompt-caching)). 즉 멀티턴 대화에서 캐시가 계속 히트하면, 같은 컨텍스트를 **10분의 1 가격**에 재사용하는 셈이다. OpenAI는 캐싱이 지원 모델에서 기본 활성화되어 있고, 캐시된 입력 토큰은 최대 90% 할인된 요율로 과금되며, Prompt Caching 대시보드에서 캐시 히트율을 모니터링할 수 있다.

## 2. 실전 적용: 자동 캐싱과 브레이크포인트 설계

Anthropic은 이제 요청 최상위에 `cache_control` 한 줄만 넣으면, 시스템이 마지막 캐시 가능 블록에 자동으로 브레이크포인트를 걸고 대화가 길어지면 앞으로 이동시켜 주는 **자동 캐싱**을 제공한다. 멀티턴 대화처럼 메시지 히스토리가 계속 자라는 패턴에 가장 적합하다.

```python
import anthropic

client = anthropic.Anthropic()

response = client.messages.create(
    model="claude-sonnet-4-5",
    max_tokens=1024,
    # 자동 캐싱: 마지막 캐시 가능 블록에 브레이크포인트 자동 적용
    cache_control={"type": "ephemeral"},
    system="당신은 사내 규정 질의응답 어시스턴트입니다. ... (수천 토큰의 규정 전문)",
    messages=[
        {"role": "user", "content": "연차 사용 규정을 알려줘"}
    ],
)
print(response.usage)
# cache_read_input_tokens / cache_creation_input_tokens 필드로 히트 여부 확인 가능
```

캐시가 잘 걸리고 있는지는 응답의 `usage` 필드에서 `cache_read_input_tokens`로 확인한다. 이 숫자가 0으로 유지된다면 캐시가 계속 깨지고 있다는 신호다.

OpenAI 쪽은 기본 활성화라 별도 코드가 필요 없지만, **최소 캐시 길이** 조건이 있다. 공식 문서 기준 최소 캐시 가능 프롬프트 길이는 1,024 토큰(GPT-5.6 이후 모델 기준)이며, OpenAI 제공 시스템 콘텐츠는 이 최소 길이에 포함되지 않는다. 짧은 프롬프트로 테스트하면 캐싱이 아예 동작하지 않으니, 검증할 때는 실제 서비스 수준의 긴 컨텍스트로 해야 한다.

## 3. 캐싱이 깨지는 대표적인 함정

가격 구조보다 실전에서 더 많은 비용을 만드는 것은 캐시 미스다. 다음 패턴을 점검하라.

**첫째, 접두사에 가변 요소를 넣지 마라.** 시스템 프롬프트 첫머리에 "오늘 날짜: 2026-08-31 14:20:33" 같은 초 단위 타임스탬프를 박아두면 모든 요청의 캐시가 즉시 무효화된다. 날짜·사용자명·요청 ID 같은 가변 값은 프롬프트 **끝부분**(마지막 사용자 메시지)에 배치한다.

**둘째, 도구 정의 순서를 고정하라.** Anthropic은 tools → system → messages 순으로 전체 접두사를 캐시한다. 도구 목록을 매번 다른 순서로 직렬화하면(예: 파이썬 set 순회) 히트율이 0으로 떨어진다. 정렬된 리스트로 고정하라.

**셋째, TTL의 기준을 이해하라.** Anthropic의 5분 캐시 수명은 요청의 **시작 시점**부터 측정된다. 응답 스트리밍에 4분이 걸리면 후속 요청은 응답 완료 후 약 1분 안에 시작되어야 같은 캐시를 재사용할 수 있다. 긴 응답이 잦은 워크로드라면 1시간 TTL(쓰기 2배)과 5분 TTL(쓰기 1.25배)의 손익분기를 계산해봐야 한다.

**넷째, 캐시 쓰기에만 반복적으로 돈을 쓰는 안티패턴을 경계하라.** 캐시 히트 없이 캐시 쓰기만 반복되면(요청마다 접두사가 조금씩 달라지는 경우) 일반 호출보다 1.25배 비싸게 쓰고 있는 것이다. `usage` 지표로 쓰기 대비 읽기 비율을 반드시 모니터링하라.

## 4. 모델 라우팅: 쉬운 질문에 비싼 모델을 쓰지 않기

캐싱이 "같은 것을 다시 계산하지 않는 것"이라면, 라우팅은 "모든 질문에 최상위 모델을 쓰지 않는 것"이다. 요청 분포를 보면 대부분의 쿼리는 단순한 형식 변환, 팩트 조회, 짧은 요약이다. 이런 쿼리까지 프론티어 모델로 보내는 것이 낭비의 핵심이다.

가장 검증된 근거는 UC Berkeley LMSYS의 **RouteLLM**이다. Chatbot Arena 사람 선호 데이터로 학습된 라우터를 적용하면 MT Bench 벤치마크에서 **최대 85% 비용 절감**을 GPT-4 성능의 **95% 유지**와 함께 달성했고, 상용 라우팅 서비스와 같은 성능을 내면서 40% 이상 저렴하다고 공식 리포지토리가 밝히고 있다([RouteLLM GitHub](https://github.com/lm-sys/RouteLLM), [논문 arXiv:2406.18665](https://arxiv.org/abs/2406.18665)). 논문 초록은 "특정 경우 2배 이상 비용 절감, 응답 품질 저하 없음"으로 요약한다.

라우팅 전략은 복잡도 스펙트럼 위에 있다. 실무에서는 단계적으로 쌓아 올리는 것이 정석이다.

1. **규칙 기반** — 쿼리 길이, 코드 블록 유무, 키워드 매칭으로 즉시 분기. 구현 비용은 거의 제로, 지연 sub-millisecond. 고객지원 트래픽처럼 분포가 안정된 워크로드에서만 룰만으로 대부분의 절감효과가 나온다.
2. **복잡도 기반** — 쿼리 난이도를 점수화해 티어를 결정. 규칙보다 정교하고 학습 데이터가 필요 없어 ROI가 높은 중간 단계다.
3. **캐스케이딩** — 싼 모델에게 먼저 시도하고, 품질 불합격(자체 검증기 또는 재시도 감지)시 상위 모델로 에스컬레이션. 품질 안전망이 내장된 구조다.
4. **학습형 라우터** — RouteLLM처럼 선호 데이터로 학습된 분류기. 수백만 쿼리/월 규모가 아니면 학습·운영 오버헤드 대비 이득이 작다.

학습형 라우터 전에 쓸 수 있는 현실적인 중간 단계가 게이트웨이 수준의 폴백 라우팅이다. LiteLLM 같은 오픈소스 게이트웨이에서는 설정 몇 줄로 "기본은 저가 모델, 특정 조건에서 상위 모델" 구조를 만들 수 있다.

```yaml
# litellm-config.yaml 예시: 기본 모델 + 폴백 체인
model_list:
  - model_name: agent-default        # 에이전트가 호출하는 논리명
    litellm_params:
      model: anthropic/claude-haiku-4-5   # 1차: 저가·고속 모델
      fallbacks: ["agent-escalation"]

  - model_name: agent-escalation
    litellm_params:
      model: anthropic/claude-sonnet-4-5  # 에스컬레이션용 상위 모델

router_settings:
  num_retries: 1
  timeout: 30
```

이 구조는 Rate limit 오류 시 상위 모델로 자동 폴백되는 신뢰성 계층 역할도 겸한다. LLM API 스팬의 오류 중 상당수가 레이트 리밋 때문이라는 업계 관측을 감안하면, 라우팅은 비용 문제이기 전에 가용성 문제이기도 하다.

## 5. 캐싱과 라우팅을 함께 쓸 때 주의할 점

두 기법은 상호작용한다. 캐싱은 **모델 단위**로 동작하므로, 라우터가 같은 대화의 턴마다 다른 모델로 보내면 각 모델에서 캐시가 따로 쌓이고 히트율이 반으로 줄어든다. 멀티턴 세션은 세션 단위로 모델을 고정하고, 라우팅은 세션 시작 시 한 번만 결정하는 구조가 캐시 히트율과 잘 맞는다. 반대로 캐스케이딩은 "싼 모델 실패 → 비싼 모델 재시도" 구조상 동일 접두사 재계산이 발생하므로, 에스컬레이션 빈도를 모니터링해 캐시 쓰기 비용이 역전하지 않는지 확인해야 한다.

또한 캐시 히트율·에스컬레이션율·모델별 지출은 별도 모니터링이 없으면 보이지 않는다. 최소한 ①캐시 읽기/쓰기 토큰 비율 ②모델별 호출 수와 지출 ③에스컬레이션율 세 가지 지표를 대시보드에 올려야 최적화 루프가 돌아간다.

## 결론

- 프롬프트 캐싱의 효율은 "켰는가"가 아니라 **"프롬프트 구조가 캐시 친화적인가"**가 결정한다. 가변 요소는 뒤로, 도구 순서는 고정, TTL 기준은 정확히 이해하라.
- Anthropic은 캐시 히트 시 입력 단가 0.1배, OpenAI는 최대 90% 할인 — 공식 문서 기준이며 Batch 할인과 누적된다.
- 모델 라우팅은 RouteLLM의 검증 수치(MT Bench 최대 85% 절감, GPT-4 성능 95% 유지)가 있지만, 대부분의 팀은 규칙+복잡도 기반만으로 충분한 절감을 먼저 얻을 수 있다.
- 두 기법은 모델 고정 여부에서 충돌하므로, 멀티턴 세션은 세션 단위 모델 고정 + 세션 시작 시 1회 라우팅이 실용적인 조합이다.

당장 할 수 있는 첫 단계는 간단하다. 오늘 배포된 서비스의 최근 API 호출 로그에서 응답 `usage`의 캐시 읽기 토큰 비율을 확인하라. 0이라면, 그것이 첫 번째 최적화 대상이다.
