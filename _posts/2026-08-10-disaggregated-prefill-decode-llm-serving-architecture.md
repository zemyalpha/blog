# 하나의 GPU가 두 가지 일을 동시에 못 하는 이유: 분리형 Prefill/Decode 서빙 설계

LLM 추론 요청 하나에는 성격이 완전히 다른 두 개의 작업이 섞여 있다. 첫 번째는 입력 프롬프트 전체를 한 번에 처리하는 **prefill** 단계이고, 두 번째는 토큰을 하나씩 순차적으로 생성하는 **decode** 단계다. 대부분의 프로덕션 환경은 이 두 작업을 하나의 GPU에서 번갈아 수행한다. 그런데 이 방식은 근본적으로 비효율적이다 — prefill은 컴퓨트 집약적(compute-bound)이고, decode는 메모리 대역폭 집약적(memory-bandwidth-bound)이기 때문이다. 서로 다른 물리적 한계에 부딪히는 두 작업을 같은 하드웨어에 욱여넣으면, 한쪽이 다른 쪽의 성능을 깎아먹는다.

이 글에서는 두 단계를 별도의 GPU 풀로 분리하는 **분리형 prefill/decode (disaggregated prefill/decode)** 아키텍처가 왜 2026년 LLM 서빙의 핵심 패러다임이 되었는지, 그리고 분리가 만드는 새로운 병목은 무엇인지 분석한다.

## 프레필과 디코드: 같은 모델, 다른 물리

LLM 추론이 두 단계로 나뉜다는 사실 자체는 새로운 것이 아니다. 하지만 두 단계가 GPU 자원을 어떻게 소비하는지 정확히 이해해야 분리의 당위성이 보인다.

**Prefill 단계** — 사용자가 입력한 프롬프트(수백~수천 토큰)를 한 번의 forward pass로 처리한다. 수천 개 토큰의 임베딩을 동시에 행렬 곱셈하므로, GPU의 Tensor Core가 포화 상태로 동작한다. 병목은 **FLOPS**, 즉 초당 부동소수점 연산량이다.

**Decode 단계** — prefill이 끝나면 첫 번째 토큰을 생성하고, 이후 매 스텝마다 이전 토큰들을 바탕으로 다음 토큰을 하나씩 만든다. 매 스텝에서 모델 전체 가중치와 KV 캐시를 HBM(고대역폭 메모리)에서 읽어와야 하므로, 연산량 자체는 적지만 **메모리 대역폭(GB/s)**이 병목이다. GPU의 SM(Streaming Multiprocessor)은 대부분 유휴 상태로 메모리 응답을 기다린다.

실제 프로파일링 수치로 이 비대칭을 확인할 수 있다. H100 SXM5에서 포화 상태로 추론 서버를 돌렸을 때, 한 엔지니어의 보고에 따르면 prefill 단계의 SM 활용률은 89%에 달한 반면, decode 단계의 SM 활용률은 12%에 불과했다. 대신 decode 단계에서 HBM 대역폭 활용률은 91%였다. 즉, 같은 GPU에서 prefill은 "연산을 최대한 끌어모으는" 작업이고, decode는 "메모리에서 데이터를 끌어오느라 연산 코어가 쉬고 있는" 작업이다. 이 둘을 같은 GPU에 섞으면, prefill의 대형 행렬 연산이 decode의 가벼운 루프를 밀어내고, decode가 prefill의 배치를 쪼개버린다.

## 통합 서빙이 부서지는 지점: 읽기-쓰기 비대칭

문제를 체감하려면 실제 트래픽 패턴을 봐야 한다. 채팅 플랫폼에서 실시간 답장 추천 서비스를 운영하는 사례를 보자. 사용자 메시지를 받으면 시스템은 크리에이터의 페르소나, 대화 규칙, 최근 10턴의 대화 맥락을 프롬프트에 포함해야 한다. 한 요청의 전형적인 토큰 분해는 다음과 같다:

| 구성 요소 | 토큰 수 |
|-----------|---------|
| 시스템 프롬프트 (페르소나, 규칙) | ~1,800 |
| 대화 기록 (최근 10턴) | ~400 |
| 현재 사용자 메시지 | ~10 |
| **총 입력** | **~2,210** |
| 생성할 답장 | ~30 |

2,210개 토큰을 읽고 30개 토큰을 쓴다. 읽기-쓰기 비율이 73:1이다. 그리고 이것이 이상 케이스가 아니라 **중앙값(median)**이라는 점이 핵심이다. 채팅, 코드 보조, RAG 검색 — 거의 모든 LLM 애플리케이션에서 입력이 출력보다 훨씬 길다. 200ms 이내에 첫 토큰(TTFT)을 내놓아야 하는 실시간 서비스에서, 긴 prefill이 짧은 decode를 기다리게 만드는 구조는 치명적이다.

통합 서빙 환경에서 무거운 prefill 요청이 도착하면, GPU 타임라인에 거대한 빈 구멍이 생긴다. prefill이 2,200개 토큰을 처리하는 동안(수십 ms), 그 GPU에서 진행 중이던 다른 요청의 decode가 블록된다. TTFT는 치솟고, 큐에는 요청이 쌓인다. GPU 활용률이 30~40%에 머무는 것이 "GPU가 부족해서"가 아니라 "GPU가 제 역할을 못 해서"라는 사실을 깨닫는 것이 분리형 아키텍처의 출발점이다.

## 분리형 아키텍처: 두 개의 전용 풀

분리형 prefill/decode 아키텍처의 핵심 아이디어는 단순하다 — GPU 플릿을 두 개의 전용 풀로 나눈다.

- **Prefill 풀**: 컴퓨트 최적화. 프롬프트 처리에 집중하여 TTFT를 최소화한다. H100/H200 같은 고성능 연산 GPU로 구성한다.
- **Decode 풀**: 메모리 대역폭 최적화. 토큰 생성에 집중하여 처리량(throughput)을 극대화한다. L40S나 A100처럼 대역폭이 충분한 GPU로 구성할 수 있다.

요청이 들어오면 prefill 풀이 전체 프롬프트를 처리하여 첫 토큰을 생성하고, KV 캐시를 RDMA(Remote Direct Memory Access) 등 고속 네트워크를 통해 decode 풀로 전송한다. decode 풀은 전달받은 KV 캐시로 이어서 토큰을 생성한다. 두 풀이 각자의 물리적 특성에 맞는 작업만 수행하므로, GPU 활용률이 크게 향상된다.

vLLM은 공식 문서에서 "Disaggregated Prefilling (experimental)" 기능을 제공하며, LMCache나 Mooncake 같은 KV 전송 커넥터와 함께 prefill 노드와 decode 노드를 분리해 구성한다. 개념적으로 두 노드의 역할은 다음과 같이 나뉜다:

```bash
# Prefill 노드: 프롬프트 처리 후 KV 캐시를 decode 노드로 전송 (producer 역할)
vllm serve meta-llama/Meta-Llama-3-70B-Instruct \
    --kv-transfer-config '{"role": "producer", "engine_id": 1, ...}' \
    --max-model-len 8192

# Decode 노드: 전송받은 KV 캐시로 토큰 생성 (consumer 역할)
vllm serve meta-llama/Meta-Llama-3-70B-Instruct \
    --kv-transfer-config '{"role": "consumer", "engine_id": 2, ...}' \
    --gpu-memory-utilization 0.95
```

> 위 설정은 분리형 서빙의 구조를 보여주는 개념적 예시다. 실제 vLLM 버전에 따라 커넥터 설정(LMCache, Mooncake, PyNccl 등)과 파라미터가 달라지므로 [공식 문서](https://docs.vllm.ai/en/stable/features/disagg_prefill/)를 참조할 것.

SGLang도 RadixAttention 기반의 유사한 분리 모드를 지원한다. 공통 요구사항은 두 노드 그룹 간 최소 100Gbps 이상의 InfiniBand 또는 RoCEv2 네트워크다 — KV 캐시 전송이 새로운 병목이 되기 때문이다.

## 분리가 만드는 새로운 병목: KV 전송과 큐잉

분리형 아키텍처는 만능이 아니다. 두 단계를 물리적으로 나누면, 이전에 없던 새로운 비용이 생긴다 — prefill 노드에서 decode 노드로 KV 캐시를 전송하는 비용이다.

2026년 7월 arXiv에 발표된 연구(arXiv:2607.02043)는 이 문제를 정량적으로 분석했다. A100 클러스터 2P2D(프레필 2노드, 디코드 2노드) 구성에서 프로덕션 수준의 트래픽을 실행한 결과, **prefill 실행 자체가 P95 TTFT의 2~23%에 불과**했다. 나머지 77~98%는 큐잉 대기 시간과 노드 간 KV 캐시 전송 시간이었다. prefill은 빨리 끝났지만, 그 결과를 decode 노드로 넘기는 과정에서 시간이 증발한 것이다.

버스트성(bursty) 트래픽에서는 더 심하다. 갑자기 요청이 몰리면 prefill 노드만 포화되고, decode 노드는 연산 능력이 남아도는 상태가 된다. 이 비대칭을 해결하기 위해 같은 논문은 **prefill deflection** 기법을 제안한다 — prefill 노드가 포화되면, 여유가 있는 decode 노드가 prefill 일부를 chunked-prefill 방식으로 대신 처리하는 것이다. decode 노드의 인플라이트 디코드 배치에 prefill 청크를 끼워 넣되, 디코드의 토큰 간 지연(TBT) SLO를 위반하지 않는 선에서 최대 청크를 탐색한다. 이 방식으로 KV 전송 자체를 없애고, P95 TTFT를 최대 81%까지 줄이며, SLO 달성률을 최대 79% 향상시켰다고 한다. 라우팅 비용은 요청당 1ms 미만이었다.

이 연구가 시사하는 바는 명확하다. 분리형 아키텍처는 prefill과 decode의 간섭을 없애지만, **로드 밸런싱과 KV 전송이라는 새로운 최적화 과제를 만든다**. 분리 자체가 목표가 아니라, 분리 위에서 트래픽 패턴에 맞게 동적으로 자원을 재배치하는 스케줄링이 완성된다.

## 언제 분리해야 하고, 언제 아닌가

분리형 아키텍처는 모든 상황에서 정답이 아니다. 다음 기준을 참고할 수 있다.

**분리가 효과적인 경우:**
- 읽기-쓰기 비율이 극단적인 서비스 (채팅, 코드 보조, RAG). 긴 입력에 짧은 출력이 반복될 때 prefill 병목이 심하다.
- 동시 사용자가 많아 TTFT SLO가 중요한 실시간 서비스
- 이기종 GPU 인프라를 보유한 경우 (고성능 연산 GPU와 대역폭 중심 GPU를 섞어 쓸 수 있음)

**통합 서빙이 나은 경우:**
- 입력과 출력 길이가 비슷한 워크로드 (예: 번역, 요약에서 입력→출력 비율이 1:1에 가까운 경우)
- 소규모 배포 (GPU 풀이 작아 분리의 오버헤드가 이득을 상회할 때)
- KV 캐시 전송을 위한 고속 네트워크(InfiniBand/RoCEv2)가 없는 경우. 이 경우 노드 간 전송이 치명적 병목이 된다.

중요한 점은 분리형으로 전환하기 전에 반드시 현재 스택을 프로파일링해야 한다는 것이다. GPU 활용률이 30~40%이고 prefill이 decode를 밀어내는 패턴이 확인되면, 분리의 이득이 크다. 반면 이미 GPU 활용률이 70% 이상이라면, 통합 서빙에서 chunked prefill이나 continuous batching을 먼저 최적화하는 것이 비용 효율적일 수 있다.

## 핵심 요약

- LLM 추론의 prefill은 컴퓨트 집약적, decode는 메모리 대역폭 집약적이다. 두 단계를 하나의 GPU에서 섞으면 서로의 성능을 갉아먹는다.
- 통합 서빙에서 무거운 prefill이 decode를 블록하면, GPU 활용률이 30~40%에 머물면서도 TTFT가 치솟는다. "GPU 부족"이 아니라 "활용 실패"가 원인이다.
- 분리형 아키텍처는 prefill 풀과 decode 풀을 물리적으로 나누어 각자의 물리적 특성에 맞는 작업만 수행하게 한다. vLLM, SGLang 모두 분리 모드를 지원한다.
- 분리는 새로운 병목을 만든다: 노드 간 KV 캐시 전송과 큐잉. 프로덕션 환경에서 이것이 P95 TTFT의 77~98%를 차지할 수 있다.
- prefill deflection, chunked prefill, 동적 스케줄링 등 분리 위에서 동작하는 2차 최적화가 실제 성능 향상을 결정한다.

분리형 prefill/decode는 "GPU를 더 사면" 해결되는 문제에 대한 근본적으로 다른 답이다. 하드웨어를 더 늘리기 전에, 같은 하드웨어에서 일을 어떻게 나눌 것인지부터 질문해야 한다.
