# AI 에이전트 메모리: 벡터 DB가 해결하지 못하는 것과 계층형 설계의 실전

2026년에 들어, 프로덕션 AI 에이전트의 가장 흔한 장애 모드는 추론 품질이 아니다. **메모리**다. 에이전트가 지난주에 무엇을 했는지 기억하지 못하고, 여러 세션에 걸친 정보를 종합하지 못하며, 사용자와 맺어온 문맥을 일관되게 유지하지 못한다. 이건 환각(hallucination) 문제가 아니라 아키텍처 문제다.

초기에는 "대화 내역을 전부 컨텍스트 윈도우에 넣자"가 정답이었다. 컨텍스트 윈도우가 커지면 해결될 것처럼 보였다. 하지만 1M 토큰 시대가 와도 문제는 사라지지 않았다. 왜일까? 이 글은 세 가지 질문에 답한다: 벡터 DB가 어디까지 해결하는가, 어디서부터 무력해지는가, 그럼 에이전트 메모리는 어떻게 설계해야 하는가.

## 메모리가 필요한 순간: "기억"이 아니라 "장애 모드"

메모리 설계는 "지능적으로 보이게" 하려고 시작하면 안 된다. 사용자에게 보이는 **구체적 장애**부터 출발해야 한다. 필자가 자주 마주치는 네 가지 실패 패턴은 이렇다:

1. **일시정지 후 재개** — 사용자가 분석 작업을 시작하고 노트북을 닫았다가 다음 날 돌아온다. 체크포인트된 상태가 없으면 에이전트는 처음부터 다시 시작한다.
2. **멀티턴 일관성** — 긴 대화에서 에이전트가 어떤 도구를 호출했고, 어떤 데이터를 모았고, 계획의 어디까지 마쳤는지 잊어버린다.
3. **개인화** — 돌아온 사용자는 에이전트가 자신의 위험 성향, 선호하는 분석 깊이, 과거 상호작용을 알고 있을 거라고 기대한다.
4. **인간 개입(HITL)** — 에이전트가 보고서 초안을 작성하고 승인을 기다린다. 이 "대기" 상태가 프로세스 재시작을 견뎌야 한다.

이 네 가지는 서로 다른 접근 패턴을 요구한다. 하나의 저장소로 전부 해결하려는 시도가 바로 "벡터 DB에 다 넣자"의 함정이다.

## CoALA 분류 체계: 여섯 가지 메모리 유형

에이전트 메모리를 체계적으로 논의하려면 2023년 Sumers, Yao 등이 제안한 **CoALA**(Cognitive Architectures for Language Agents) 프레임워크가 유용한 출발점이다. 인지과학의 기억 분류를 차용해 에이전트 메모리를 여섯 가지로 나눈다:

| 메모리 유형 | 범위 | 수명 | 예시 | 저장 패턴 |
|-----------|------|------|------|----------|
| 작업(Working) | 현재 단계 | 밀리초 | 도구 호출 인자, 현재 LLM 응답 | 인메모리(Python dict) |
| 단기(Short-term) | 현재 스레드 | 분~시간 | 대화 내역, 계획 진행 상황 | 체크포인트 스토어 |
| 에피소드(Episodic) | 스레드 간 | 일~월 | "지난주 사용자가 NVDA 실적을 물었다" | 벡터/KV 스토어 |
| 시맨틱(Semantic) | 스레드 간 | 월~영구 | "사용자는 보수적 투자를 선호한다" | 벡터/KV 스토어 |
| 문서(Document) | 스레드 간 | 일~영구 | 프로젝트 노트, 연구 요약 | 파일 스토어(Markdown/JSON) |
| 절차(Procedural) | 시스템 전체 | 영구 | "주식 분석 시 항상 SEC 공시 확인" | 설정/시스템 프롬프트 |

핵심은 이 여섯 가지가 **서로 다른 접근 패턴**을 갖는다는 점이다. 작업 메모리는 밀리초 단위로 사라지지만 가장 빠르다. 단기 메모리는 체크포인트로 일시정지/재개를 지원한다. 에피소드와 시맨틱 메모리는 세션을 넘어 회상해야 한다. 문서 메모리는 사람과 에이전트 모두가 검사하고 편집할 수 있어야 한다. 절차 메모리는 시스템 지시문에 고정된다.

구현 관점에서 이 여섯 가지는 **3계층**으로 압축된다:

- **핫(Hot) 메모리** — 현재 세션을 유지하는 체크포인트
- **콜드(Cold) 메모리** — 세션 간 회상을 지원하는 벡터/그래프/KV 스토어
- **문서(Document) 메모리** — 누적된 프로젝트 지식을 읽기 쉽고 편집 가능하게 보관

## 벡터 DB의 한계: "관계"를 표현하지 못한다

벡터 스토어(Pinecone, Weaviate, pgvector, Chroma)는 2026년 현재 가장 널리 쓰이는 메모리 패턴이다. 대화 내역과 추출된 팩트를 임베딩 벡터로 변환해 저장하고, 쿼리 시점에 의미적으로 유사한 청크를 검색한다.

강점은 확장성이다. 수십억 건의 레코드를 비용 증가 없이 처리하고, 검색 지연(latency)은 스케일이 커져도 100ms 이하를 유지한다.

약점은 **관계를 표현하지 못한다**는 것이다. 벡터 스토어는 "이 사용자가 Python을 언급했다"는 사실은 알려준다. 하지만 "이 사용자는 데이터 파이프라인에 Python을 쓰고, pandas와 dbt를 사용하며, Spark에서 마이그레이션 중"이라는 관계망은 표현할 수 없다.

이 한계는 벤치마크에서 수치로 드러난다. 그래프 기반 메모리 시스템은 복잡한 멀티홉 질문에서 **약 94.8% 정확도**를 기록한 반면, 동일한 작업의 플랫 벡터 방식은 **66~68%**에 그쳤다 (Deep Memory Retrieval 벤치마크 기준, Graphiti/Zep 관련 평가로 알려져 있다 — 독립 교차 검증이 아직 충분하지 않으므로 참고치로 볼 것). 특히 시간에 따른 관계 변화를 묻는 질문, 예를 들어 "정책이 바뀌기 전에 이 사용자는 X에 대해 어떻게 생각했나?"에서 그래프 구조의 우위는 결정적이다.

## 롱 컨텍스트가 메모리를 대체할 수 있는가

"컨텍스트 윈도우가 충분히 크면 그냥 다 넣으면 되지 않나?"라는 질문은 자연스럽다. 2026년 기준 주요 프론티어 모델(Claude Opus 계열, Gemini 2.5 Pro 등)은 1M 토큰 컨텍스트를 지원한다.

개념적으로 가장 단순한 접근이다. 검색 단계도 없고, 청킹 결정도 없고, 임베딩 모델 유지보수도 없다. 모델이 전부를 본다.

하지만 두 가지 현실이 걸린다.

**첫째, 비용이 선형으로 증가한다.** 컨텍스트를 두 배로 늘리면 첫 토큰까지의 시간과 요청당 비용이 대략 두 배가 된다. 200K 토큰 컨텍스트를 매번 로드하면, 입력 토큰 가격이 백만당 약 $0.49~$5 범위(2026년 프론티어 모델 대표 가격)라고 할 때 상호작용당 비용이 무시할 수 없는 수준이 된다. 대규모 트래픽에서는 연간 수십만 달러 규모로 불어난다.

**둘째, "Lost-in-the-Middle" 현상이 지속적으로 재확인된다.** 모델은 긴 컨텍스트의 중앙에 묻힌 정보를 회상하지 못한다. 한 분석에 따르면 확장 길이의 복잡한 검색 작업에서 Llama 4 Scout 기반으로 정확도가 **15.6%**까지 떨어졌고, 동일 작업에서 Gemini는 90% 이상 유지했다. 모델 간 차이는 크지만, "컨텍스트에 넣었으니 기억할 것"이라는 가정은 위험하다.

> 💡 Anthropic이 2026년 5월 Code with Claude 행사에서 "research preview"로 공개한 "Dreaming" 기능은 이 문제에 대한 한 응답이다 (출처: claude.com 공식 블로그). 세션 사이에 비동기로 실행되는 기억 통합 과정으로, 세션 기록을 검토해 패턴을 추출하고 중복을 병합하며 메모리를 재구성한다. 일부 보도에서는 법률 AI 기업 Harvey의 작업 완료율이 6배 상승했다고 전하나, 이는 Anthropic 공식 발표가 아닌 secondary 보도이므로 참고치로만 볼 것.

## 벤치마크가 말하는 것: LoCoMo와 LongMemEval

2026년 들어 에이전트 메모리 영역에 표준화된 벤치마크가 등장했다. 이제 "우리 시스템이 기억을 잘한다"는 자체 보고가 아니라, 서로 다른 아키텍처를 동일 평가 세트에서 비교할 수 있게 되었다.

**LoCoMo**는 최대 35세션, 300턴, 평균 9K 토큰의 대화 내역으로 구성된다. 질문 응답, 이벤트 요약, 멀티모달 대화 생성을 평가한다 — 실제 장기 실행 에이전트 환경을 직접 모델링한다.

**LongMemEval**은 수작업으로 만든 500개 질문으로, 정보 추출, 멀티세션 추론, 시간 추론, 지식 업데이트, 기답(정답이 없을 때 답하지 않는 능력) 다섯 가지 핵심 메모리 능력을 테스트한다.

주요 결과를 정리하면:

| 시스템 | 아키텍처 | LoCoMo | LongMemEval | 비고 |
|--------|---------|--------|-------------|------|
| MemMachine | 그래프 + 검색 | 91.7% | 91.7% | gpt-4.1-mini 백본 |
| Supermemory | 하이브리드 | — | 85.4% | 300ms 미만 회상 |
| Letta (파일시스템) | 에피소드(파일) | 74.0% | — | gpt-4o-mini |
| Mem0 | 벡터 + 그래프 | 92.5% | 94.4% | 2026년 알고리즘 (공급업체 보고) |
| 베이스라인 (원시 컨텍스트) | 롱 컨텍스트 | ~35% | ~40% | 메모리 계층 없음 |

(출처: agentmarketcap.ai 2026년 4월 벤치마크 정리 및 Mem0 공식 블로그 2026년 7월 보고. Mem0의 92.5/94.4는 자사 블로그에서 보고한 수치이므로 독립 검증이 필요하다. 다만 Mem0 연구진이 ECAI 2025에 발표한 논문(arXiv:2504.19413)이 10가지 메모리 접근법의 비교 기준을 마련한 것은 사실이다.)

가장 주목할 만한 발견은 **Letta의 "파일시스템이 전부를 이긴다"는 결과**다. gpt-4o-mini를 쓴 에이전트가 특수 검색 도구 없이 대화 내역을 파일에 저장하는 것만으로 LoCoMo 74.0%를 달성했다. 함의는 명확하다: 회상 품질은 **어떤 데이터베이스 기술을 쓰느냐**보다 **무엇을 저장하고 어떻게 조직하느냐**에 더 크게 좌우된다.

## 실전 설계: 3계층 메모리 패턴

위의 분석을 종합하면, 프로덕션 에이전트 메모리는 단일 스토어가 아니라 계층 구조로 설계해야 한다. LangGraph의 공식 패턴이 좋은 참고가 된다.

### 핫 메모리: 체크포인트 스토어

LangGraph는 매 노드 실행 후 전체 그래프 상태를 직렬화해 체크포인트로 저장한다. 이것이 일시정지/재개, 타임트래블 디버깅, HITL 워크플로우의 기반이다.

```python
from langgraph.checkpoint.postgres import PostgresSaver
from langgraph.graph import StateGraph
from psycopg_pool import ConnectionPool

# PostgreSQL 기반 체크포인트 (내구성 우선)
pool = ConnectionPool(
    conninfo="postgresql://user:pass@localhost/agent",
    max_size=20,
)
checkpointer = PostgresSaver(pool)
checkpointer.setup()  # 테이블 스키마 생성

graph = build_agent_graph()
app = graph.compile(checkpointer=checkpointer)

# thread_id로 스레드 구분 — 같은 thread_id면 이전 상태에서 재개
config = {"configurable": {"thread_id": "session-42"}}
result = app.invoke(
    {"messages": [("user", "저번에 하던 NVDA 분석에 경쟁사 추가해줘")]},
    config=config,
)
```

체크포인트 백엔드 선택은 접근 패턴에 달려있다. **PostgreSQL**은 ACID 트랜잭션, WAL, 복제를 제공해 내구성과 재현 가능한 디버깅이 우선일 때 적합하다. **Redis**는 낮은 지연과 짧은 수명 상태에 적합하지만, 지속성 설정과 메모리 사용량을 신경 써야 한다. 핵심 원칙은: 체크포인트는 감사 로그(audit log)가 아니다. 재개 지점이다.

### 콜드 메모리: 벡터 + 정확값 저장소 분리

가장 흔한 실수는 "모든 장기 메모리를 벡터 DB에 넣는 것"이다. 사용자 ID, 환율 설정, 구독 플랜 같은 **정확한 사실**은 퍼지 검색 시스템에 넣으면 안 된다. 어절 일치(match)가 필요한 데이터는 키-값 스토어나 관계형 DB에, 의미 검색이 필요한 데이터는 벡터 스토어에 저장한다.

```python
# 시맨틱 메모리: 벡터 스토어 (의미 검색)
from qdrant_client import QdrantClient

qdrant = QdrantClient(host="localhost", port=6333)
# "사용자는 보수적 투자 성향" → 임베딩 → Qdrant에 저장
# 의미적으로 유사한 기억을 회상할 때 사용

# 구조적 팩트: 키-값 (정확한 조회)
import sqlite3
kv = sqlite3.connect("facts.db")
# {"user_id": "u123", "risk_tolerance": "conservative",
#  "preferred_depth": "detailed", "currency": "KRW"}
# 정확한 일치 조회 — 퍼지 매칭 없이
```

### 문서 메모리: 파일 기반 지식

Claude Code, Cursor, Windsurf, Devin 같은 코딩 에이전트가 모두 프로젝트 파일을 영구 메모리로 로드한다는 점은 시사하는 바가 크다. 에이전트가 학습한 규칙, 프로젝트 컨벤션, 절차적 지식은 임베딩 서비스 없이 검사하고 버전 관리할 수 있는 파일로 저장하는 것이 종종 최선이다. Generative Agents 연구(Park et al., 2023)에서 시뮬레이션 에이전트가 자체 메모리를 저장·반성·검색한 것과 같은 패턴이다.

## 결정의 경제학: 언제 롱 컨텍스트가 이기는가

마지막으로 하나 더. 2026년에 메모리 아키텍처는 능력의 문제이기도 하지만, **경제의 문제**이기도 하다.

최신 프론티어 모델들이 1M 토큰 컨텍스트를 지원하면서, 일부는 200K 초과 시 추가 요금 없이 평등(flat) 가격을 책정하고 있다. 업계 보도에 따르면 Claude Opus 계열 최신 모델이 백만당 입력 $5, 출력 $25 수준의 평등 가격을 적용하고 있다 (정확한 버전명과 가격은 시점에 따라 변동이 있으므로 공식 가격 페이지를 확인할 것). 이런 조건이라면, 누적 내역이 대략 50만 토큰 미만이고 세션이 10개 미만인 단일 사용자 에이전트에서는, 롱 컨텍스트 방식이 Mem0 + Pinecone 스택을 운영하는 것보다 조작상 더 싸질 수 있다.

즉 "작은 규모에서는 그냥 컨텍스트에 밀어 넣는 것"이 정당화되는 구간이 존재한다. 하지만 이 교차점(crossover)을 넘어서면 — 사용자가 많아지거나, 누적 내역이 늘어나거나, 멀티홉 시간 추론이 필요해지면 — 계층형 메모리로 전환하지 않으면 비용이 통제 불능이 된다.

## 결론: 무엇부터 할 것

핵심을 요약하면:

- **벡터 DB는 메모리의 일부일 뿐 전부가 아니다.** 의미 검색에 강하지만 관계 표현과 정확한 팩트 조회에는 약하다. 그래프 메모리는 멀티홉·시간 추론에서 확실한 우위를 보인다 (94.8% vs 66~68%, 벤치마크 의존적).
- **기억은 계층으로 설계하라.** 작업(인메모리) / 단기(체크포인트) / 장기(벡터+KV+그래프) / 문서(파일)를 접근 패턴에 따라 분리하라. 하나의 스토어에 전부 넣는 것이 가장 흔한 실수다.
- **체크포인트와 회상을 혼동하지 마라.** 체크포인트는 재개 지점이지 감사 로그가 아니다. 벡터 회상은 의미 검색이지 정확값 조회가 아니다.
- **벤치마크를 기준점으로 쓰되, 맹신하지 마라.** LoCoMo와 LongMemEval이 비교 기준을 마련했지만, 공급업체 자체 보고 수치는 독립 검증이 필요하다.
- **LangChain 메모리는 더 이상 공식 지원되지 않는다.** 2026년 기준 `langchain.memory`의 `BufferMemory`, `ConversationBufferMemory` 등은 사용 중단(deprecated)되었다. LangGraph의 체크포인터 기반 단기+장기 메모리 패턴으로 마이그레이션해야 한다.

당장 시도해볼 첫 단계는 단순하다. 자신의 에이전트에서 "가장 최근에 겪은 메모리 실패"를 하나 고른다. 그것이 일시정지 후 재개 실패인지, 세션 간 망각인지, 관계 추론 실패인지 파악한다. 그 실패가 요구하는 접근 패턴에 맞는 저장소를 하나 추가한다. 벡터 DB부터 시작할 이유는 없다 — 아마도 체크포인트 스토어부터여야 한다.
