# A2A 프로토콜 1.0 실전 가이드 — 서로 다른 AI 에이전트를 연결하는 표준 기술

AI 에이전트를 만드는 일은 어려워지고 있지 않다. LangGraph, CrewAI, Azure AI Foundry 같은 프레임워크가 성숙하면서 개별 에이전트의 구현 난이도는 오히려 내려가는 추세다. 문제는 그다음이다. 내가 만든 에이전트와 다른 팀이, 다른 회사가 만든 에이전트가 함께 일하게 하려면 어떻게 해야 할까? 지금까지의 답은 대부분 "커스텀 API를 하나하나 연결하라"였고, 이는 에이전트 수가 늘어날수록 조합 폭발로 이어진다.

A2A(Agent2Agent) 프로토콜은 이 문제에 대한 업계의 답이다. Google이 2025년 4월 발표했고, 같은 해 6월 Linux Foundation에 기부되어 벤더 중립적 거버넌스 아래 관리되고 있다. 그리고 2026년 4월, 출시 1년 만에 버전 1.0이 안정 스펙으로 릴리스되었고 150개 이상의 조직이 참여했다. 이 글에서는 A2A가 무엇을 해결하는지, MCP와 어떻게 다른지, 그리고 실제로 에이전트를 노출하고 호출하는 코드 수준의 구조를 다룬다.

## A2A와 MCP는 경쟁이 아니라 분업이다

혼동이 가장 많은 부분부터 정리하자. A2A와 MCP(Model Context Protocol)는 같은 층위의 경쟁 표준이 아니다. 공식 문서는 이 둘을 "상호보완적(complementary)" 관계로 명확히 규정한다.

- **MCP**: 에이전트가 도구와 리소스에 연결되는 방식을 표준화한다. 데이터베이스 쿼리, API 호출, 파일 접근처럼 입력과 출력이 잘 정의된 프리미티브를 다룬다. 방향은 "에이전트 → 도구"다.
- **A2A**: 독립적인 에이전트끼리 피어로 협업하는 방식을 표준화한다. 상대 에이전트의 내부 메모리나 구현을 모른 채 태스크를 위임하고 결과를 받는다. 방향은 "에이전트 ↔ 에이전트"다.

공식 문서의 예시를 옮기면, 여행 에이전트가 항공사 에이전트, 호텔 에이전트, 액티비티 에이전트와 협업하는 구조가 A2A의 전형이다. 각 하위 에이전트는 내부적으로 자기 도구에 MCP로 연결되어 있을 수 있다. 즉, 하나의 시스템 안에서 MCP는 조직 내부의 신경계, A2A는 조직 간의 통신 규약에 가깝다.

이 구분이 실무적으로 중요한 이유는 설계 오류를 방지하기 때문이다. 단순 함수 호출로 해결될 일을 A2A로 감싸면 불필요한 복잡성이 생기고, 반대로 상대의 추론 과정 전체를 위임해야 할 일을 MCP 도구 호출로 구현하면 상태 관리가 지옥이 된다. "상대가 불투명한(opaque) 자율 시스템인가, 아니면 투명한 함수인가"가 선택 기준이다.

## 핵심 메커니즘 1: Agent Card — 에이전트의 명함

A2A의 첫 번째 축은 발견(discovery)이다. 에이전트는 자기 자신을 **Agent Card**라는 JSON 문서로 설명하며, 표준 위치는 다음 well-known URI다.

```
https://{host}/.well-known/agent-card.json
```

Agent Card에는 다섯 가지 정보가 담긴다.

1. **정체성**: 이름, 설명, 제공자
2. **서비스 엔드포인트**: A2A 서비스 URL
3. **기능(capabilities)**: 스트리밍, 푸시 알림 지원 여부
4. **인증**: 요구되는 보안 스킴 (Bearer, OAuth2 등) — 카드에서 필드명은 스펙 버전에 따라 달라질 수 있어 공식 스펙 문서를 참조할 것
5. **스킬(skills)**: 에이전트가 수행할 수 있는 작업 목록

실제 구조는 이런 형태다.

```json
{
  "name": "currency-agent",
  "description": "환율 조회와 환전 계산을 수행하는 에이전트",
  "version": "1.0.0",
  "url": "https://agents.example.com/a2a",
  "capabilities": {
    "streaming": true,
    "pushNotifications": false
  },
  "skills": [
    {
      "id": "exchange_rate",
      "name": "환율 조회",
      "description": "두 통화 간 현재 환율을 반환한다",
      "inputModes": ["text"],
      "outputModes": ["text"]
    }
  ]
}
```

핵심 통찰은 이것이다. Agent Card는 그냥 설명 문서가 아니라 **클라이언트가 요청을 구조화하고 보안을 협상하는 근거**다. 클라이언트 에이전트는 카드를 읽고 "이 에이전트는 스트리밍을 지원하는구나, OAuth2가 필요하구나"를 파악한 뒤 통신 방식을 결정한다. 인간이 API 문서를 읽고 SDK를 고르는 것의 자동화 버전이다.

공식 문서가 소개하는 발견 전략은 세 가지다. 공개 에이전트는 well-known URI, 기업 내부는 큐레이션 레지스트리, 폐쇄 환경은 직접 설정. 어떤 전략을 쓰든 Agent Card라는 공통 형식 덕분에 클라이언트 코드는 동일하게 유지된다.

## 핵심 메커니즘 2: 태스크 중심의 수명주기

두 번째 축은 통신 모델이다. A2A의 설계에서 눈여겨볼 점은 "챗봇 대화"가 아니라 **태스크(Task)** 를 중심 개념으로 삼는다는 것이다. 태스크는 생성되고(submitted), 진행되고(working), 완료되거나(completed) 실패하거나(failed) 취소된다. 스펙이 정의하는 핵심 오퍼레이션은 다음과 같다.

- 메시지 전송 (`message/send`) — 동기식 요청
- 스트리밍 메시지 전송 (`message/stream`) — SSE 기반 실시간 응답
- 태스크 조회 (`tasks/get`, `tasks/list`)
- 태스크 취소 (`tasks/cancel`)
- 푸시 알림 구독 설정

LLM 응답이 몇 분 걸릴 수 있는 에이전트 세계에서 이 구조는 필수적이다. 태스크 id로 언제든 진행 상황을 조회하고, 오래 걸리는 작업은 웹훅 푸시 알림으로 완료 시점을 받는다. REST API 설계자에게 낯익은 패턴을 에이전트 통신에 적용한 셈이다.

전송 계층은 평범한 웹 기술이다. HTTP 위에 JSON 기반 메시지를 주고받으며, 보안은 TLS, JWT, OpenID Connect, OAuth2 같은 이미 널리 쓰이는 표준으로 처리한다. 즉 기존 로드밸런서, 게이트웨이, 인증 인프라를 그대로 재활용할 수 있다. 이 "웹 친화적" 설계는 대규모 배포에서 강점이 된다.

실제 요청은 JSON-RPC 형태다.

```json
{
  "jsonrpc": "2.0",
  "id": "req-1",
  "method": "message/send",
  "params": {
    "message": {
      "role": "user",
      "parts": [
        { "kind": "text", "text": "USD to KRW 환율 알려줘" }
      ]
    }
  }
}
```

응답은 태스크 객체와 함께 오고, 결과물은 아티팩트(Artifact)로 전달된다. 텍스트뿐 아니라 파일 업로드/다운로드, 구조화 데이터 교환도 스펙에 포함되어 있다.

## 실전: Python SDK로 시작하기

공식 Python SDK로 시작하는 흐름을 정리하면 다음과 같다.

```bash
pip install --upgrade a2a-sdk
```

에이전트 서버 측에서는 Agent Card에 스킬을 정의하고, 각 요청을 처리할 **Agent Executor**를 구현한 뒤 서버를 띄운다. 공식 퀵스타트 튜토리얼이 이 과정을 단계별로 다룬다. 클라이언트 측에서는 상대의 well-known URI에서 카드를 가져와(`/.well-known/agent-card.json`) 능력과 인증 요구사항을 확인한 후 메시지를 보낸다.

버전 1.0에서 주목할 만한 신기능은 두 가지다.

1. **Signed Agent Cards** — 에이전트 카드에 암호학적 서명을 붙여 신원을 검증한다. 에이전트가 "나는 결제 에이전트다"라고 사칭하는 것을 어느 정도 막는 장치다.
2. **엔터프라이즈 멀티테넌시** — 하나의 A2A 서버가 여러 테넌트를 안전하게 격리해서 서비스할 수 있는 구조가 스펙에 반영되었다.

## 도입 시 고려할 점

장밋빛만 있는 건 아니다. 도입을 검토한다면 체크리스트는 이렇다.

**도입이 적합한 경우** — 조직 경계를 넘는 에이전트 협업, 프레임워크가 다른 에이전트들의 통합(LangGraph 에이전트와 CrewAI 에이전트의 협업 같은 시나리오는 공식 보도자료에도 명시되어 있다), 벤더 락인 회피가 목표일 때.

**신중해야 하는 경우** — 단일 프레임워크 내부 통신에는 오버엔지니어링일 수 있다. 같은 팀의 에이전트끼리는 프레임워크 네이티브 수단이 더 단순하다. 또한 아직 생태계 초기라 에이전트 레지스트리 운영, 카드 서명 키 관리 같은 운영 부담은 직접 떠안아야 한다.

보안 관점에서는 Agent Card의 신뢰성 확보가 첫 단추다. well-known URI는 가로채기에 취약할 수 있으므로, v1.0의 Signed Agent Cards와 TLS를 함께 쓰고, 카드 캐싱 정책(스펙 문서가 서버/클라이언트 양쪽 가이드를 제공한다)을 명확히 해야 한다.

## 결론

A2A가 노리는 지점은 명확하다. 에이전트의 가치는 협업 능력에 비례하는데, 협업이 커스텀 통신 코드에 갇혀 있으면 스케일할 수 없다. 표준 프로토콜로 이 병목을 없애는 것 — 1년 만에 150개 조직이 동참한 이유다.

- A2A는 에이전트 ↔ 에이전트 통신, MCP는 에이전트 → 도구 연결. 경쟁이 아닌 분업이다
- Agent Card(JSON) + well-known URI가 발견의 기본 단위다
- 통신은 태스크 중심 수명주기 + JSON-RPC + 웹 표준 보안(TLS/JWT/OIDC) 위에 있다
- v1.0은 Signed Agent Cards와 멀티테넌시로 엔터프라이즈 요구를 반영했다
- 첫 단계는 가볍다: 공식 a2a-sdk로 HelloWorld 에이전트를 띄우고, 내 에이전트의 Agent Card를 작성해보는 것부터
